# VisionFive 2 SD 卡 Linux A/B 启动方案

## 1. 目标

在现有 SPI NOR payload A/B 选择之后，让 U-Boot proper 使用同一份
`recovery` 元数据选择 SD 卡中成对的 Linux FIT 与 rootfs：

| bank | boot 分区 | 内容 | rootfs 分区 | 内容 |
| --- | ---: | --- | ---: | --- |
| A | SD 第 3 分区 | FAT/EFI，包含 `image.fit` | SD 第 4 分区 | `rootfs.ext4` |
| B | SD 第 5 分区 | FAT/EFI，包含 `image.fit` | SD 第 6 分区 | `rootfs.ext4` |

一次启动中的 NOR payload、Linux FIT 和 rootfs 必须来自同一 bank，不允许
`payload B + image.fit A + rootfs A` 之类的混合启动。

## 2. 现状与边界

### 2.1 现有链路

1. BootROM 从 SPI NOR 的 `spl_a` 启动 SPL。
2. `u-boot/common/spl/quard_bootctrl.c` 校验 NOR GPT 和 recovery。
3. recovery 有效时，SPL 读取 `target_bank`，将其同步到 `current_bank`，然后
   选择 `fw_payload_a/b`；recovery 无效时选 A。
4. U-Boot proper 目前仍使用固定的 `bootpart=3` 和 `rootpart=4`。
5. `conf/vf2_uEnv.txt` 从 `${bootpart}` 加载 FIT，并根据 `${rootpart}` 生成
   Linux `root=` 参数。

### 2.2 硬件所有权

FreeRTOS 启动后是物理 QSPI 控制器的唯一 owner。U-Boot proper 不得使用
`sf probe/read` 读 recovery，必须通过已有 mailbox-backed `quard-nor` MTD
驱动读取 `recovery` 分区。SPL 在 FreeRTOS 启动前使用 SPI flash 驱动的
现有路径保持不变。

## 3. 推荐总体方案

```text
SPI NOR recovery
       |
       +-- SPL: target_bank -> 更新 current_bank -> fw_payload_a/b
       |
       +-- U-Boot proper: 经 quard-nor MTD 只读 recovery
                              |
                              +-- 读 current_bank
                              |
                              +-- bank A -> SD boot 3 -> rootfs 4
                              |
                              +-- bank B -> SD boot 5 -> rootfs 6
```

不建议让 U-Boot proper 实现第二套 OTA 状态机。已确认的字段职责是：

- `target_bank` 是 SPL 的切换请求。
- SPL 将选择结果写入 `current_bank`。
- U-Boot proper 只使用 `current_bank` 选择 SD 系统。

本阶段 U-Boot proper 的基础规则为：

```text
recovery 有效: selected_bank = current_bank
recovery 无效: selected_bank = A
```

`usable_bank`、`successful_bank_mask`、`ota_state`、版本、rollback index 和重试次数
均不参与本步选择。如果以后恢复完整 OTA 回滚策略，应先抽出一个
纯决策函数供 SPL 和 U-Boot proper 共用，不能分别复制状态机。

## 4. U-Boot proper 设计

### 4.1 读取 recovery

新增 VisionFive2 专用的 U-Boot proper bootctrl helper，职责限定为：

1. 触发/确认 `quard-nor` MTD 设备已 probe。
2. 通过 `get_mtd_device_nm("recovery")` 按分区名获取 MTD。
3. 从分区 offset 0 读取 `sizeof(recovery_config_t)`。
4. 校验 magic、struct version、`current_bank/target_bank` 范围和 header CRC32。
5. 以 `current_bank` 作为 A/B 决策，然后释放 MTD 引用。

U-Boot proper 对 recovery 只读，不更新 `current_bank`、CRC 或其他字段。
`current_bank` 的写回仍只由现有 SPL 路径负责，避免两个启动阶段都擦写 NOR。

### 4.2 bank 到 SD 分区的唯一映射

建议用一个小型常量表集中表达映射，不要将 `3/4/5/6` 散落在
board code、environment 和 `vf2_uEnv.txt` 多处：

```c
static const struct quard_sd_slot quard_sd_slots[] = {
    [RECOVERY_BANK_A] = { .boot_part = 3, .root_part = 4 },
    [RECOVERY_BANK_B] = { .boot_part = 5, .root_part = 6 },
};
```

选择完成后设置运行时环境变量：

| 变量 | A | B | 用途 |
| --- | --- | --- | --- |
| `active_bank` | `a` | `b` | 日志与 Linux 可见状态 |
| `bootpart` | `3` | `5` | FAT 中 FIT 的加载分区 |
| `rootpart` | `4` | `6` | rootfs 分区 |
| `active_system` | `0` | `1` | 与现有 OTA 用户态约定对齐 |

这些值每次启动都从 recovery 重新派生，不执行 `saveenv`，因此不会用
旧环境覆盖 recovery 的真实状态。

### 4.3 rootfs 定位

推荐 Linux 命令行使用选中 rootfs 分区的 GPT PARTUUID，不直接假定
U-Boot `mmc 1` 在 Linux 中永远是 `/dev/mmcblk1`：

```text
part uuid mmc ${devnum}:${rootpart} rootuuid
root=PARTUUID=${rootuuid} rootwait rw
```

如果暂时保持现有 `conf/vf2_uEnv.txt` 的设备名方式，则 SD 启动时为：

```text
A: root=/dev/mmcblk1p4
B: root=/dev/mmcblk1p6
```

设备名方式改动小，但依赖 Linux MMC 控制器的 probe 顺序；PARTUUID
方式更适合长期使用。

### 4.4 FIT 加载与启动

保留现有 `conf/vf2_uEnv.txt` 的 FIT 解析、DTB fixup、initramfs 和 `booti`
流程，只将输入分区改为选中的 `${bootpart}`。概念命令如下：

```text
mmc dev ${sd_devnum}
part uuid mmc ${sd_devnum}:${rootpart} rootuuid
fatload mmc ${sd_devnum}:${bootpart} ${loadaddr} image.fit
setenv bootargs "... root=PARTUUID=${rootuuid} rootwait rw active_bank=${active_system}"
bootm start ${loadaddr}
... 保留现有 FIT 解包和 FDT fixup ...
booti ${kernel_addr_r} ${ramdisk_addr_r}:${filesize} ${fdtaddr}
```

FIT 和 rootfs 必须在调用 `bootm start` 前完成配对，不允许在后续脚本里
再改 `bootpart` 或 `rootpart`。

## 5. 建议的调用时机

推荐在 `board_late_init()` 中，完成 boot mode 识别后、执行 `bootcmd` 前，调用
bootctrl helper 覆盖 `bootpart/rootpart`。这样无论 NOR 中是编译默认环境还是
已保存的旧环境，本次启动的 bank 参数都由 recovery 覆盖。

已确认暂时保留 eMMC、NVMe 和 DHCP 的现有启动搜索。保留搜索会有一个
需要规避的影响：`bootmode=flash` 会先后尝试 SD、eMMC 和 NVMe，如果全局
`bootpart/rootpart` 已被 B 设为 `5/6`，后续 eMMC/NVMe 也会错误使用 `5/6`。

因此 A/B 分区号必须只在 SD 尝试分支内生效：

1. 进入 SD 分支时，根据 `current_bank` 设置 `bootpart=3/5`、`rootpart=4/6`。
2. SD 不存在时，可继续现有 eMMC/NVMe/DHCP 搜索。
3. 离开 SD 分支前恢复其他介质的原有默认值，或让每种介质使用独立变量。
4. SD 已存在但选中的 A/B 分区、`vf2_uEnv.txt` 或 `image.fit` 损坏时，
   不能将这种 bank 故障伪装成“SD 不存在”并静默跳到其他介质。

## 6. 失败策略

| 失败点 | 建议行为 | 原因 |
| --- | --- | --- |
| recovery magic/version/CRC 无效 | 选 A，打印明确日志 | 与现有 SPL 无效元数据时的 A 回退一致 |
| `target_bank` 越界 | 当作 recovery 无效，选 A | 与 SPL 校验一致 |
| mailbox/MTD probe 失败 | 停止自动启动，留在 U-Boot shell | 此时无法知道 SPL 已选 A 还是 B，盲目选 A 可能形成混合 bank |
| recovery MTD 短读 | 停止自动启动 | 属于传输故障，不等同于已确认的无效元数据 |
| 选中的 boot/rootfs 分区不存在 | 停止自动启动 | 避免 FIT/rootfs 跨 bank 拼接 |
| `image.fit` 不存在或 FIT 校验失败 | 停止自动启动 | 基础阶段不擅自切 bank，不修改 recovery |

还需修正现有 SPL 的一个一致性窗口：当 `target_bank != current_bank` 且
SPL 写回 `current_bank` 失败时，当前代码只打印 warning，仍继续启动
`target_bank` payload。但 U-Boot proper 按已确认的规则会读 `current_bank`，两者可能
不一致。推荐将 SPL 写回失败改为终止启动，不再继续加载 payload。
该策略与 U-Boot proper 的 mailbox/MTD 读取失败时“停止自动启动”保持一致。

如果产品要求“B 启动失败后自动回退 A”，必须连同启动计数、成功确认、
recovery 原子更新和 SPL payload 选择一起设计，不应只在 U-Boot 脚本中
`if fatload ... else ...` 临时切换。

## 7. 拟修改文件及职责

实施时建议保持最小改动：

1. `u-boot/board/starfive/visionfive2/quard_bootctrl.c`
   - U-Boot proper 专用。
   - 通过 MTD 读 recovery、校验 ABI/CRC、选 bank 并设置环境变量。
2. `u-boot/board/starfive/visionfive2/Makefile`
   - 在显式 Kconfig 开关打开时才编译 helper。
3. `u-boot/board/starfive/visionfive2/starfive_visionfive2.c`
   - 在 `board_late_init()` 的合适时机调用 helper；不在 board 文件内展开 recovery 解析。
4. VisionFive2 相关 Kconfig/defconfig
   - 新功能默认关闭，仅目标 VisionFive2 AMP 配置显式开启。
   - 依赖 U-Boot proper MTD、CRC32 和 `QUARD_NOR_CLIENT`，不编译进 SPL。
5. `u-boot/include/configs/starfive-visionfive2.h`
   - 使现有 SDK 启动流程消费动态 `bootpart/rootpart`，并避免 distro 路径再扫描到非选中分区。
6. `conf/vf2_uEnv.txt`
   - 将 `fitfile` 从现有 `starfiveu.fit` 改为 SD 卡实际文件名 `image.fit`。
   - 推荐增加 PARTUUID root 参数。
7. `conf/jh7110_uEnv.txt`
   - VisionFive2 的 SDK 自动路径实际加载 `vf2_uEnv.txt`，不加载此文件。
   - 鉴于它也被复制到 A/B boot 分区，建议同步将 FIT 文件名改为
     `image.fit`，并标明它不是 A/B 自动启动入口，避免手工调试时误用固定
     `partnum=3`/`root=/dev/mmcblk0p4`。

不建议直接扩展 `u-boot/common/spl/quard_bootctrl.c`给 U-Boot proper 使用。该文件
绑定 SPL `spi_flash` 路径，而 U-Boot proper 必须走 mailbox-backed MTD，两者只能
共享 recovery ABI 和纯决策规则，不能共享底层 Flash 访问。

## 8. 实施顺序

1. 确认 SD GPT 的 PARTUUID/分区名和当前 Linux 中 SD 设备名；已确认
   A/B 分区号为 `3/4` 和 `5/6`，boot 分区是 FAT，FIT 文件名是 `image.fit`。
2. 实现 U-Boot proper recovery 只读 helper 和错误分类。
3. 实现 bank -> `bootpart/rootpart` 映射，只先影响 SD 模式。
4. 将 rootfs 改为 PARTUUID 定位，核对 `image.fit` 文件名。
5. 做源码审查后，再按用户明确指令进行 U-Boot/完整 AMP 构建。
6. 板端先只读验证 A/B 映射，再分别启动 A 和 B。

## 9. 验收要点

- SPL 将 `target=A` 同步为 `current=A` 时，日志显示 SPL 加载 payload A，U-Boot 从 SD 3
  加载 FIT，Linux root 是 SD 4。
- SPL 将 `target=B` 同步为 `current=B` 时，日志显示 SPL 加载 payload B，U-Boot 从 SD 5
  加载 FIT，Linux root 是 SD 6。
- Linux 可见 `active_bank=0/1`，并能用 mount source/PARTUUID 证明实际 rootfs。
- 人为损坏 recovery CRC 时，SPL 和 U-Boot 都明确选 A。
- 断开 mailbox 或使 recovery MTD 短读时，U-Boot 不进行混合 bank 启动。
- 删除选中 FIT 或使 FIT 校验失败时，不静默跳到另一 bank。
- A/B 冷启动和软重启均保持 payload/FIT/rootfs 一致。

## 10. 已确认的实施决策

1. SD 3/5 为 FAT/EFI 分区，根目录放置 `image.fit`、`jh7110_uEnv.txt`
   和 `vf2_uEnv.txt`。
2. VisionFive2 自动启动使用 `vf2_uEnv.txt`，FIT 文件名统一为 `image.fit`。
3. SPL 读 `target_bank` 并更新 `current_bank`；U-Boot proper 只依据
   `current_bank` 选择 SD A/B。
4. 暂时保留 eMMC/NVMe/DHCP 搜索，但 SD A/B 分区变量不得泄漏到
   其他介质分支。
5. mailbox/MTD 无法读取 recovery 时停止自动启动。

尚需确认一项：当 SPL 将 `target_bank` 写入 `current_bank` 失败时，
是否同意改为立即终止启动，代替现有的“只打印 warning 并继续启动
target payload”行为？

## 11. 分阶段实施计划与代码设计

### 阶段一：U-Boot proper 只读 bootctrl

状态：已完成源码实现，尚未编译和测试。

- 新增 `quard_bootctrl.c/.h`，只通过 MTD 名称 `recovery` 读取
  `recovery_config_t`，不包含擦除、写入或 SPI flash 路径。
- 读取错误分成两类：MTD 获取/读取/短读属于传输错误并返回失败；magic、
  version、bank 范围或 CRC 错误属于元数据无效并回退 A。
- 环境变量采用“最后发布有效位”的事务式顺序：先写
  `active_bank/active_system/sd_bootpart/sd_rootpart`，最后才设置
  `sd_ab_enabled=1`，避免脚本消费半更新状态。
- `board_late_init()` 只在 `bootmode=flash/sd` 时读取 recovery。传输失败时设置
  本次运行时 `bootdelay=-1`，保留 U-Boot shell 和原 `bootcmd` 供人工诊断，
  不执行 `saveenv`。
- 用 `sd_ab_env_version` 管理本功能涉及的默认脚本变量。检测到 NOR 中是旧版
  已保存环境时，只从编译默认环境刷新 A/B 相关变量，不重置 MAC、网络参数等
  其他用户环境，也不自动写回 NOR。

### 阶段二：SD 槽映射与其他介质隔离

状态：已完成源码实现，尚未编译和测试。

- A/B 唯一映射集中在 C 常量表中：A 为 `3/4`，B 为 `5/6`。
- helper 导出专用 `sd_bootpart/sd_rootpart`；只有检测到 SD 设备且
  `sd_ab_enabled=1` 时，脚本才把它们复制到 `bootpart/rootpart`。
- eMMC 和 NVMe 分支在尝试前恢复 `default_bootpart/default_rootpart=3/4`，
  防止 B 槽的 `5/6` 泄漏到其他介质。
- helper 开始执行时也先把全局 `bootpart/rootpart` 恢复为 `3/4`；B 槽号只保存在
  `sd_bootpart/sd_rootpart` 中，直到真正进入 SD 分支才应用。
- 功能开关关闭时，SD 分支仍进入原有固定 `3/4` 的 legacy 流程，保证默认关闭
  配置不改变原行为。

### 阶段三：rootfs PARTUUID 与失败闭锁

状态：已完成源码实现，尚未编译和测试。

- `vf2_uEnv.txt` 使用 `part uuid` 在加载 FIT 前确认选中 rootfs 分区存在，
  Linux 命令行使用 `root=PARTUUID=...`。
- SD A/B 分支在导入 uEnv 后强制设置 `verify=yes`，使 FIT 的校验错误返回到
  闭锁路径；其他介质仍保持各自原有的 `verify` 设置。
- SD A/B 启动参数增加 `active_bank=${active_system}`，值为 A=`0`、B=`1`；
  U-Boot 环境中的 `active_bank` 保持 `a/b`，用于日志。
- FIT 文件名统一为 `image.fit`；`jh7110_uEnv.txt` 同步文件名，但明确仅用于
  手工/调试，不作为自动 A/B 入口。
- SD 控制器存在而选中 boot/rootfs、uEnv 或 FIT 失败时，设置
  `bootmode=ab-failed`，使后续 eMMC/NVMe/distro 搜索不再执行。SD 设备本身
  不存在时不设置该闭锁，保留原有其他介质搜索。
- 从 SD 导入 `vf2_uEnv.txt` 后再次应用已选择的分区号，避免 uEnv 内容覆盖
  recovery 派生出的槽映射。

### 阶段四：SPL 写回一致性窗口

状态：待确认后实施。

- 将 `recovery_sync_current_bank()` 的失败从 warning 改为向
  `quard_bootctrl_select_payload()` 返回错误，阻止继续加载 target payload。
- 不改变 recovery 无效时回退 A 的现有策略。
- 此项会改变底层启动失败语义，需确认第 10 节末尾问题后再修改。

### 阶段五：构建与板端验证

状态：未开始，需用户明确要求后执行。

1. 用目标 defconfig 检查新开关及依赖，只为 U-Boot proper 编译 helper。
2. 按仓库要求执行完整 `make ampfit RTOS=freertos -j$(nproc)`。
3. 部署并核对构建产物、TFTP 副本、模块 vermagic、时间戳和 SHA-256。
4. 依次验证 A、B、无效 CRC、MTD 故障、缺失 FIT，并证明 payload/FIT/rootfs
   不发生跨槽混用。
