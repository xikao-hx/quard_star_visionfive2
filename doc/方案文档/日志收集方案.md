# VisionFive2 SPL、OpenSBI、U-Boot 日志收集方案

## 1. 文档目的

本文基于以下内容给出 VisionFive2 的启动日志收集方案：

- `doc/日志落盘实现记录.md` 中记录的历史实现和问题；
- `~/quard_star_tutorial` 中 BL1、OpenSBI 0.9、U-Boot 2021.07 的参考代码；
- 当前仓库的 U-Boot SPL、OpenSBI 1.2、U-Boot、Linux `quard_log` 驱动和 `soc_logd` 实现。

本文只做设计和实施拆解，不直接修改固件代码。目标是在进入 Linux 后，将同一次启动中的 SPL、OpenSBI 和 U-Boot 串口输出按启动顺序保存到日志文件，同时不影响原有串口输出和启动流程。

## 2. 需求理解

### 2.1 目标

1. 收集以下三个阶段的控制台日志：
   - U-Boot SPL；
   - OpenSBI；
   - U-Boot proper。
2. 串口仍然正常输出，内存日志只是串口发送路径的旁路副本。
3. Linux 启动后读取保留内存，由 `soc_logd` 写入 `/opt/soc_log/linux_boot_log.log`。
4. 日志缓冲区写满后覆盖最旧数据，任何阶段都不能因为日志写入失败而阻塞启动。
5. 同一启动阶段即使串口被多次初始化，也不重复清空已经收集的日志。

### 2.2 非目标

- 本阶段不收集 BootROM 日志，因为 BootROM 不在本仓库控制范围内。
- 本阶段不改变 FreeRTOS/RT-Thread 实时日志协议。
- 本阶段不引入文件系统写入到 SPL、OpenSBI 或 U-Boot。
- 本阶段不把日志收集扩展到任意串口驱动，仅支持 VisionFive2 当前使用的 NS16550/8250 控制台路径。

## 3. 当前实现结论

### 3.1 启动链与代码入口

当前启动链为：

```text
BootROM
  -> U-Boot SPL
  -> OpenSBI 1.2 fw_payload
  -> U-Boot proper
  -> Linux
  -> quard_log 驱动复制保留内存
  -> soc_logd mmap 并写文件
```

对应的控制台字符输出入口为：

| 阶段 | 当前代码入口 | 设计插入点 |
| --- | --- | --- |
| SPL | `u-boot/drivers/serial/ns16550.c` | `ns16550_serial_putc()` 成功发送字符之后 |
| OpenSBI | `opensbi/lib/utils/serial/uart8250.c` | `uart8250_putc()` 成功发送字符之后 |
| U-Boot | `u-boot/drivers/serial/ns16550.c` | 与 SPL 共用插入点，通过 `CONFIG_SPL_BUILD` 选择缓冲区 |
| Linux | `bsp/ipi_mailbox/consumer/quard_log.c` | probe 时复制保留内存到内核页 |
| 应用 | `app/soc_log/soc_logd.c` | mmap 内核页并解析环形缓冲区后写文件 |

这里与参考工程的关键区别是：参考工程的 BL1 是独立源码；当前工程的 SPL 和 U-Boot proper 由同一套 U-Boot 源码构建。因此 SPL/U-Boot 应共用一套写入逻辑，通过编译阶段选择不同的物理缓冲区，不应复制两份近似实现。

### 3.2 已有物理内存布局

当前 `common_inc/bsp/quard_log.h` 和 Linux AMP DTS 已定义如下区域：

| 用途 | 起始地址 | 区域大小 | 内部布局 |
| --- | ---: | ---: | --- |
| MCU 日志 | `0x6e404000` | `0x2000` | 保持现状 |
| U-Boot 日志 | `0x6e406000` | `0x2000` | U-Boot 独占 |
| SPL/OpenSBI 日志 | `0x6e408000` | `0x2000` | SPL `0x000~0x3ff`；OpenSBI `0x400~0x13ff` |

Linux DTS 中三块区域均使用 `no-map`，并通过 `memory-region` 交给 `quard,log_device`。U-Boot AMP DTS 的 OpenSBI domain 配置把 `0x6e400000` 开始的 4 MiB 定义为共享区域。日志区不与 `0x6e500000` 的 NOR 共享区、`0x6e800000` 的 RTOS 代码区冲突。

建议本次沿用已有地址，避免重新调整多方内存布局。

### 3.3 当前已有基础

- `common_inc/bsp/quard_log.h` 已使用固定宽度 32 位字段定义 `struct ramlog_buffer`，避免了 32/64 位固件之间 `size_t` 和指针宽度不一致的问题。
- Linux AMP DTS 已保留三块物理内存并关联到日志设备。
- Linux 驱动已经在 probe 阶段把启动日志复制到普通内核页，避免后续固件或其他模块修改原始区域。
- `soc_logd` 已具备 mmap 和写入 `linux_boot_log.log` 的主流程。

### 3.4 当前必须修正的问题

1. `common_inc/bsp/quard_log.h` 当前通过 `BOARD_JH7110` 在 VisionFive2 的 `0x6e...` 地址和历史 QEMU 的 `0xbf...` 地址之间切换。当前仓库目标就是 VisionFive2/JH7110，不需要这个条件宏；继续保留反而可能因构建参数遗漏而选错地址。本次应删除该条件分支，公共头文件直接定义 `0x6e...` 布局。
2. `soc_logd` 当前跳过头部后仍按固定 payload 容量写文件，没有根据 `head/tail` 计算有效数据，也没有处理回卷后的两段数据。
3. `display_boot_log()` 按 `rb->size` 打印整个容量，同样忽略 `head/tail`，会输出未使用或旧数据。
4. `BL1/uart/ns16550.c` 使用 magic 判断缓冲区是否已经初始化，这个机制应继续沿用；同时追加路径仍需检查 `size/head/tail`，避免损坏的元数据引起除零或越界。
5. 参考 U-Boot 实现每输出一个字符刷新整个 `0x2000` 区域，开销过大。
6. 顶层 Makefile 对 U-Boot/OpenSBI 源文件的依赖不够精确，修改嵌套源码后可能复用旧产物。

因此，三个生产端和读取端应作为同一个端到端功能实施。只增加生产端不足以保证最终落盘结果正确。

## 4. 缓冲区 ABI

### 4.1 保持现有结构体

为减少 Linux 驱动、应用和固件之间的联动修改，建议保留现有 16 字节 ABI：

```c
struct ramlog_buffer {
    uint32_t magic;
    uint32_t head;
    uint32_t tail;
    uint32_t size;
};
```

约束如下：

- `magic`：固定为 `0x52414d4c`（ASCII `RAML`）；
- `size`：头部之后的数据容量，不是当前有效日志长度；
- `head`：最旧有效字符的索引；
- `tail`：下一个写入位置；
- 所有字段均按小端 32 位无符号数解释；
- 结构体禁止加入指针、`size_t`、`unsigned long` 或编译器相关位域；
- 头部大小必须在各构建中静态检查为 16 字节。

### 4.2 有效性判断

缓冲区只有同时满足以下条件才有效：

```text
magic == RAMLOG_MAGIC
size == region_size - sizeof(struct ramlog_buffer)
size > 1
head < size
tail < size
```

任意条件不满足时，生产端应无条件清空自己的区域并重新初始化，不能再次只检查 magic。

### 4.3 写入规则

每成功向串口发送一个字符后执行：

```text
payload[tail] = ch
提交 payload 写入
tail = (tail + 1) % size
如果 tail == head：head = (head + 1) % size
最后提交 head/tail 元数据
```

该实现牺牲一个字节来区分空和非空：

- `head == tail` 表示空；
- 最大有效日志长度为 `size - 1`；
- 写满后始终保留最近的 `size - 1` 个字符。

读取端有效长度计算：

```text
tail >= head: valid_len = tail - head
tail <  head: valid_len = size - head + tail
```

若发生回卷，先读取 `[head, size)`，再读取 `[0, tail)`。

## 5. 各阶段设计

### 5.1 U-Boot SPL 与 U-Boot proper

修改 `u-boot/drivers/serial/ns16550.c`，参考 `BL1/uart/ns16550.c` 的实现增加两个文件内私有函数：

- `ramlog_buffer_init()`：检查 magic；只有尚未初始化时才清空区域并写入合法头部；
- `ramlog_append()`：校验缓冲区并追加单个字符。

地址和区域大小仍然使用宏定义。由于 SPL 和 U-Boot proper 使用同一份驱动源码，通过 U-Boot 已有的 `CONFIG_SPL_BUILD` 编译期宏选择本阶段参数：

```c
#ifdef CONFIG_SPL_BUILD
#define RAMLOG_ADDR \
    (BL1_SBI_LOG_BUF_BASE_ADDR + BL1_LOG_BUF_OFFSET)
#define RAMLOG_REGION_SIZE BL1_LOG_BUF_SIZE
#else
#define RAMLOG_ADDR UBOOT_LOG_BUF_BASE_ADDR
#define RAMLOG_REGION_SIZE UBOOT_LOG_BUF_SIZE
#endif
```

这里保留的是 `CONFIG_SPL_BUILD`，它用于区分同一套 U-Boot 源码当前是在构建 SPL 还是 U-Boot proper；前文要求删除的是不再需要的 `BOARD_JH7110` 板型选择宏，两者用途不同。

初始化逻辑与 BL1 保持一致：

```c
static void ramlog_buffer_init(void)
{
    struct ramlog_buffer *rb =
        (struct ramlog_buffer *)(uintptr_t)RAMLOG_ADDR;
    uint32_t max_log_size =
        RAMLOG_REGION_SIZE - sizeof(struct ramlog_buffer);

    if (rb->magic != RAMLOG_MAGIC) {
        memset((void *)(uintptr_t)RAMLOG_ADDR, 0,
               RAMLOG_REGION_SIZE);
        rb->magic = RAMLOG_MAGIC;
        rb->size = max_log_size;
        rb->head = 0;
        rb->tail = 0;
    }
}
```

`ramlog_append()` 在写入前至少检查：

```text
magic == RAMLOG_MAGIC
size == RAMLOG_REGION_SIZE - sizeof(struct ramlog_buffer)
head < size
tail < size
```

若 magic 不正确，调用 `ramlog_buffer_init()`。若 magic 正确但其余元数据非法，应先使 magic 失效再重新初始化，或者调用一个无条件重置的内部小段逻辑；不能只调用上述 magic 初始化函数后继续使用损坏的 `size/head/tail`。

插入点放在 `ns16550_serial_putc()` 的 `serial_out()` 之后。该函数在 FIFO 未就绪时返回 `-EAGAIN`，此时不能写入 ramlog，否则 U-Boot serial uclass 重试会导致重复字符。

`ns16550_serial_probe()` 可以像 BL1 的 `uart_init()` 一样调用 `ramlog_buffer_init()`。串口即使多次 probe，只要 magic 仍然有效就不会清空已有日志。`ramlog_append()` 也保留校验，防止未经过预期 probe 或元数据被破坏时直接越界。

#### 缓存处理

JH7110 U-Boot 已实现 `flush_dcache_range()`，配置范围覆盖日志地址。不能像参考实现一样每字符刷新全部 8 KiB，建议：

1. 写 payload 字节；
2. 刷新该字节所在 cache line；
3. 执行写屏障；
4. 更新 `head/tail`；
5. 刷新 16 字节头部覆盖的 cache line。

初始化时才刷新整个所属小区域。SPL 阶段需要通过链接验证确认 cache API 可用；如果 SPL 中 cache 尚未开启，该调用仍应保持安全且不改变行为。

### 5.2 OpenSBI

修改 `opensbi/lib/utils/serial/uart8250.c`，在 `uart8250_putc()` 完成 `set_reg(UART_THR_OFFSET, ch)` 后追加字符。

OpenSBI 使用：

```text
base = 0x6e408000 + 0x400
region_size = 0x1000
```

使用 OpenSBI 自带的 `sbi_memset()` 或已有字符串接口，不在驱动内重新实现一个全局 `memset()`，避免符号污染。使用 `<sbi/riscv_barrier.h>` 提供的屏障宏保证先写 payload、后发布 tail。

需要注意：RISC-V `fence` 只保证访问顺序，不等价于 cache clean。当前方案基于 JH7110 启动链中该 DDR 区域对后继阶段可见；实机验证时必须先在 U-Boot 用 `md.b 0x6e408400` 检查。如果只能看到头部或旧数据，再增加 JH7110 平台级 cache line clean，不能用更多 `fence` 假装完成 cache 刷新。

### 5.3 初始化与跨阶段隔离

三个阶段统一通过各自缓冲区头部的 magic 判断是否已初始化，不增加 `static bool initialized`：

- magic 不正确：只清空本阶段区域，初始化 magic、size、head、tail；
- magic 正确：认为缓冲区已经初始化，不因串口重复 probe 再次清空；
- SPL 和 OpenSBI 共用一个 8 KiB 保留区，但各自只操作自己的子区域；
- U-Boot proper 操作独立的 8 KiB 区域。

各阶段严禁清空完整的 `BL1_SBI_LOG_BUF_SIZE`，否则 OpenSBI 初始化会抹掉 SPL 日志。

该 magic 方案解决的是“同一阶段重复初始化不丢日志”。如果 DDR 在热复位后仍保留有效 magic，旧日志也会继续保留并追加；纯 magic 无法识别是否已经进入一次新的启动。若产品要求热复位后严格只保留本次日志，需要另行增加 boot generation/boot ID 或由确定的最早阶段统一清除，不能用 `static bool` 代替跨启动标识。

## 6. Linux 与应用读取设计

### 6.1 Linux 驱动

保留 probe 时将三块 `no-map` 内存复制到内核普通页的总体设计，但修改 `display_boot_log()`：

1. 根据所选阶段得到子区域起点和实际区域大小；
2. 检查 magic、size、head、tail；
3. 只按 head 到 tail 输出有效内容；
4. 遇到非法头部立即返回 `-EINVAL`，不得越界读取；
5. 日志诊断打印使用有效长度，不把 capacity 当作日志长度。

复制原始保留内存前使用读屏障是合理的，但屏障不能代替生产端的 cache clean。

### 6.2 soc_logd

将固定长度写入改为统一的环形缓冲区解析函数，例如：

```text
append_ramlog_to_file(file, region_base, region_size)
```

函数职责：

- 校验头部；
- 计算有效长度；
- 按一段或两段顺序追加到文件；
- 使用有效长度参与日志轮转判断；
- 任意非法元数据只跳过当前阶段并记录错误，不影响其他阶段落盘。

最终写入顺序固定为 SPL、OpenSBI、U-Boot。建议在各阶段前加文本分隔标记，例如：

```text
===== SPL =====
===== OpenSBI =====
===== U-Boot =====
```

分隔标记由应用添加，不写入固件环形缓冲区，便于识别阶段且不占用早期日志空间。

当前 `write_to_file_direct()` 存在“跳过头部后仍写 payload 全容量”的越界风险，应在本功能中一并替换，而不是在旧接口上继续增加偏移。

## 7. 公共头文件与构建集成

### 7.1 公共 ABI

继续以 `common_inc/bsp/quard_log.h` 作为唯一 ABI 和内存布局定义，避免三个固件与 Linux 各自复制 magic、结构体和大小。

建议新增/调整：

- `RAMLOG_MAGIC`；
- `SPL_LOG_BUF_OFFSET/SIZE`，并暂时保留旧 `BL1_*` 名称作为兼容别名；
- 编译期结构体大小检查；
- 地址宏整体加括号；
- 删除 `BOARD_JH7110` 条件和历史 `0xbf...` 地址分支，直接使用当前仓库唯一的 VisionFive2/JH7110 `0x6e...` 布局。

U-Boot serial 目录通过 `ccflags-y` 增加 `common_inc/bsp` include path；OpenSBI 构建命令通过 CFLAGS 增加同一 include path。不再传入 `BOARD_JH7110` 或其他布局选择宏。不要在 C 文件中使用多层 `../../../` 相对路径引用公共头文件。

### 7.2 顶层 Makefile 依赖

为普通和 AMP 两套产物补充精确依赖：

- U-Boot/SPL 产物依赖 `u-boot/drivers/serial/ns16550.c` 和公共头文件；
- OpenSBI 产物依赖 `opensbi/lib/utils/serial/uart8250.c` 和公共头文件；
- AMP Linux DTB 继续显式依赖实际 Linux DTS；
- Linux 日志模块和 `soc_logd` 依赖公共头文件。

验收时必须同时构建 AMP 路径，因为当前部署使用：

```text
work/u-boot-amp-spl.bin.normal.out
work/visionfive2_fw_payload_amp.img
work/amp/image.fit
```

## 9. 分步实施计划

### Step 1：统一 ABI 和读取端

目标：先让 Linux/应用能够安全、准确地解析任意合法或非法 ramlog。

实施内容：

1. 整理公共头文件，加入 magic、SPL 命名和静态断言，删除 `BOARD_JH7110` 及历史 QEMU 地址分支；
2. 为内核和应用各自实现单入口解析；
3. 使用人工构造的空、未回卷、已回卷、满缓冲、非法 size、非法索引数据验证。

成功标准：读取端不越界；输出严格等于 head 到 tail 的有效字符；一个阶段损坏不影响另外两个阶段。

### Step 2：实现 SPL/U-Boot 生产端

目标：同一驱动代码在 SPL 与 U-Boot proper 写入不同区域。

实施内容：

1. 使用 `CONFIG_SPL_BUILD` 定义本阶段的地址和大小宏，加入 magic 初始化、严格校验和单字符追加；
2. 在成功串口输出后旁路调用；
3. 仅 clean 修改过的 cache line；
4. 验证串口多次 probe 不清空已有日志。

成功标准：SPL 与 U-Boot 串口内容保持不变；`md.l` 可看到两个合法且互不覆盖的头部；重复 probe 后 tail 只前进、不归零。

### Step 3：实现 OpenSBI 生产端

目标：OpenSBI 写入共享区的第二个子区域且保留 SPL 日志。

实施内容：

1. 接入公共 ABI；
2. 在 UART8250 成功发送后追加；
3. 使用 OpenSBI 屏障接口发布元数据；
4. 在 U-Boot 阶段检查原始内存可见性。

成功标准：进入 U-Boot 后，SPL 和 OpenSBI 两个头部均合法，SPL 内容未被 OpenSBI 初始化清除。

### Step 4：构建、打包和实机端到端验证

按仓库规则执行：

```bash
make ampfit AMP_RTOS=freertos -j$(nproc)
```

确认以下三个文件时间戳和哈希来自本次构建，再部署到 TFTP：

```text
work/u-boot-amp-spl.bin.normal.out
work/visionfive2_fw_payload_amp.img
work/amp/image.fit
```

实机验证分层进行：

1. U-Boot 中检查原始内存：

   ```text
   md.l 0x6e408000 4    # SPL header
   md.l 0x6e408400 4    # OpenSBI header
   md.l 0x6e406000 4    # U-Boot header
   ```

2. Linux 中确认 reserved-memory 和驱动 probe：

   ```bash
   dmesg | grep -E 'log shared memory|Driver initialized'
   echo 1 > /sys/kernel/soc_log/hunter_boot_log
   echo 2 > /sys/kernel/soc_log/hunter_boot_log
   echo 3 > /sys/kernel/soc_log/hunter_boot_log
   ```

3. 启动 `soc_logd` 后检查：

   ```bash
   test -s /opt/soc_log/linux_boot_log.log
   grep -aE 'U-Boot SPL|OpenSBI|U-Boot' /opt/soc_log/linux_boot_log.log
   ```

4. 连续热复位两次，确认 magic 保留策略的实际表现，并据此决定是否需要增加 boot generation；每轮可识别日志的阶段顺序应为 SPL、OpenSBI、U-Boot。

## 10. 风险与规避

| 风险 | 规避方式 |
| --- | --- |
| 条件宏遗漏导致选中错误物理地址 | 删除 `BOARD_JH7110` 和 `0xbf...` 分支，仓库内唯一布局固定为 `0x6e...` |
| 地址宏含加法且无括号 | 所有地址表达式整体加括号，先转 `uintptr_t` 再转指针 |
| 串口重复 probe 清空前半段日志 | 使用缓冲区 magic 判断是否已经初始化，magic 有效时不清空 |
| 热复位后 magic 和旧日志仍有效 | 明确这是 magic-only 方案的限制；若不允许跨启动保留，再设计 boot generation 或由最早阶段统一清除 |
| OpenSBI 清除 SPL | 只清理 OpenSBI 的 `0x1000` 子区域 |
| 固件与 Linux 结构体宽度不同 | ABI 只使用固定 32 位整数，静态检查头部大小 |
| head/tail 损坏导致 Linux 越界 | 使用 region size 作为硬上限，校验全部元数据后才读取 |
| cache 中有数据、Linux 看不到 | U-Boot 精确 clean；OpenSBI 先实机验证，必要时实现 JH7110 平台 clean |
| 每字符刷新整个缓冲区拖慢启动 | 只 clean payload line 和 header line |
| U-Boot FIFO 重试导致重复日志 | 只在实际 `serial_out()` 成功后追加 |
| 修改源码却复用旧固件 | 顶层 Makefile 添加文件级依赖并核对最终三个部署产物哈希 |

## 11. 验收标准

1. 串口日志与改动前内容一致，没有丢字符、重复字符或明显启动延迟。
2. 三个缓冲区头部 magic、size、head、tail 均合法，物理区域互不覆盖。
3. SPL、OpenSBI、U-Boot 任一日志超过容量时，仅丢弃该阶段最旧字符。
4. Linux 对空、正常、回卷和损坏缓冲区均不会越界或崩溃。
5. `linux_boot_log.log` 只包含有效字符，顺序为 SPL、OpenSBI、U-Boot，无 16 字节头部乱码和未使用区乱码。
6. 明确并验证热复位后的日志保留行为；若验收要求只保留本次启动，则在引入 boot generation 后验证新旧日志可以区分。
7. `make ampfit AMP_RTOS=freertos` 能从修改过的源文件可靠触发对应固件重建。

## 12. 待确认问题

实施前需要确认以下产品行为：

1. 是否同意把 Linux 驱动和 `soc_logd` 的环形读取修正纳入本次范围？本方案认为这是端到端正确落盘的必做项。
2. 最终文件是否继续合并为一个 `linux_boot_log.log`？本方案默认合并并加入三个阶段分隔标记；若现有日志分析工具依赖纯原始串口流，可不加分隔标记，或改为三个独立文件。
3. 日志容量是否沿用现状：SPL `0x400`、OpenSBI `0x1000`、U-Boot `0x2000`？SPL 可用正文只有约 1007 字节，若要求完整保留较长 SPL 日志，需要重新分配 `0x6e408000` 内的两个子区域。
4. 是否只要求 AMP/Freertos 构建链生效，还是普通 `make visionfive2` 产物也必须收集日志？本方案默认普通和 AMP 两套构建都生效，但只有 AMP Linux DTS 已配置日志消费端。
