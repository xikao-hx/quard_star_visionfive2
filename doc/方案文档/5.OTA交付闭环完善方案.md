# OTA 交付闭环完善方案

## 1. 背景与当前决策

VisionFive 2 的 SPI NOR `fw_payload_a/b` 与 SD
`boot_a/b`/`rootfs_a/b` 切换启动链路已经打通，
`ota_package` 已实现 manifest、payload SHA-256 和 RSA-2048 +
SHA-256 签名校验，stage1/stage2/boot_success 状态机也已有
基础实现。

本轮确认不再引入自定义 `binary_header`，不修改 SPL
为了跳过自定义镜像头而扩展 FIT 加载偏移。所有 OTA payload
继续保持当前存储格式：

| payload | 存储格式 |
| --- | --- |
| `fw_payload_a/b` | 原始 `visionfive2_fw_payload_amp.img` FIT |
| `boot_a/b` | 完整 `starfive-visionfive2-vfat.part`，根目录包含 `starfiveu.fit` 和 `vf2_uEnv.txt` |
| `rootfs_a/b` | 从分区 offset 0 开始的 ext4 镜像 |
| `spl_a/b` | BootROM 当前可识别的 SPL 格式 |

原自定义镜像头方案仅作为历史分析保留，不再执行其实施步骤。

### 1.1 当前签名到底保护什么

`tools/script/build_ota_package.py` 使用 OTA 私钥对签名输入执行
RSA-2048 + SHA-256 签名。签名输入由 `data.json` 和 manifest
声明的所有 payload 文件的 SHA-256 摘要组成。设备只保存
公钥，私钥只保存在宿主机或后续的离线签名环境。

设备在 `verify_stage1`/`verify_stage2` 中验证签名和 payload
摘要，因此可以拒绝：

- 不是由可信私钥生成的 OTA 包；
- 下载中损坏或被修改的 manifest/payload；
- 文件替换、缺失、长度异常和目标 bank 错误。

安全边界必须明确：这是“OTA 安装时验签”，不是 secure
boot。payload 写入存储后，SPL/U-Boot 目前不会在每次启动时
使用 OTA 公钥重新验证存储内容。本阶段接受该边界，不将
CRC32 或自定义镜像头误写为安全签名。

## 2. 目标、范围和不做的内容

### 2.1 P0 交付目标

1. 新增不属于 A/B 的 `userdata` ext4 分区，开机自动挂载
   `/userdata`。
2. 把 `/etc/version` 写入构建的 rootfs 镜像，保证 A/B
   两个 rootfs 均能独立提供版本信息。
3. 把 OTA 工具、动态库、客户端脚本、公钥和配置固化到
   rootfs，不再依赖 NFS `/mnt`。
4. 开机根据 recovery 状态恢复 stage2，健康检查通过后再
   执行 stage2 或 `boot_success`。
5. GPT PARTLABEL 统一为 `boot_a`/`rootfs_a`/`boot_b`/
   `rootfs_b`/`userdata`。

### 2.2 P1 目标

1. 当 rootfs ext4 小于所在 GPT 分区时，在该 rootfs 启动后
   幂等地扩容到完整分区。
2. boot payload 使用 SDK 已生成的完整 FAT 分区镜像
   `starfive-visionfive2-vfat.part`，使 `starfiveu.fit` 与
   `vf2_uEnv.txt` 作为同一签名 payload 更新。

### 2.3 安全与运维目标

1. 建立 OTA 公钥双钥迁移、撤销和 `key_id` 选钥规则。
2. 限制 `/userdata` 中的 OTA 包、临时文件和日志占用。
3. 按 `session_id` 长期保存失败现场，同时执行轮转和脱敏。

### 2.4 明确不做

- 不增加自定义镜像头；
- 不修改 SPL/FIT 加载 offset；
- 不在本轮实现 secure boot、FIT signature 或 dm-verity；
- 按当前决策，不修复 rootfs 在 stage1 中跳过 SHA-256
  precheck 的问题；
- 在 `boot_success` 之前不删除当前 session 的 OTA 包。

## 3. 目标分区和持久化边界

### 3.1 统一 PARTLABEL

| bank | boot | rootfs | 持久数据 |
| --- | --- | --- | --- |
| A | `boot_a` | `rootfs_a` | `userdata` |
| B | `boot_b` | `rootfs_b` | `userdata` |

`userdata` 不属于任何 bank，stage1/stage2 不允许将它列为
payload 目标。Linux 用户态优先使用：

```text
/dev/disk/by-partlabel/boot_a
/dev/disk/by-partlabel/rootfs_a
/dev/disk/by-partlabel/boot_b
/dev/disk/by-partlabel/rootfs_b
/dev/disk/by-partlabel/userdata
```

U-Boot 启动脚本在选定 bank 后可由 PARTLABEL 查询 PARTUUID，
内核 `root=` 最终使用 PARTUUID。`/dev/mmcblk1pN` 只作为
当前板端排查信息，不再作为新脚本的稳定接口。

当前实施选择固定 2 GiB 的 `userdata`，位于 A/B 固定分区之后，
使同一整盘镜像可用于 8 GB 及以上容量的 SD 卡。首次启动
扩展 `userdata` 到介质剩余空间不属于 Step 1，仍作为后续待办。

### 3.2 `/userdata` 目录规划

```text
/userdata/ota/
|-- download/                 # 压缩包和 .part 断点文件
|-- package/                  # 当前已解包 session
|-- state/                    # 客户端发布状态
|-- log/                      # 按 session_id 归档的日志
`-- lost+found/
```

挂载失败时，OTA 服务必须记录错误并退出，不得在
rootfs 上临时创建同名 `/userdata` 目录后继续 stage2，否则
会在 A/B 切换后丢失包和 session 状态。

## 4. 分步行动方案

### Step 0：冻结包格式和签名决策

1. 保持 `tools/script/build_ota_package.py` 的原始 payload 格式，
   删除后续开发计划中的 `binary_header` 生成、解析和 SPL
   适配任务。
2. 继续强制 `data.json`、`manifest.hash`、`signature.sig`
   和所有 payload 文件完整。
3. 包验签和版本门禁必须在任何分区写入之前通过。
4. 将“OTA 签名只保护下载和安装”写入交付说明。

验收标准：正常包验签通过；修改 manifest 或任一 payload
后必须验签失败；不产生带自定义头的 payload。

### Step 1：增加 `userdata` 和统一 PARTLABEL

计划修改：

- SD GPT/genimage 布局：为 A/B boot/rootfs 写入统一 label，
  增加 `userdata`；
- rootfs 的 `/etc/fstab` 或独立 SysV init 脚本：把
  `PARTLABEL=userdata` 挂载到 `/userdata`；
- 启动脚本和 OTA writer：优先解析 `/dev/disk/by-partlabel/*`，
  在迁移期间保留现有环境变量覆盖能力。

挂载参数建议以数据可恢复为先，首版可使用：

```fstab
PARTLABEL=userdata  /userdata  ext4  defaults,noatime  0  2
```

自动 stage2 服务必须排在 `userdata` 挂载之后。对现有
SD 卡修改 GPT 属于有风险操作，必须先备份用户数据，建议
优先用新生成的整盘镜像验证，不在 OTA 中在线重写整盘 GPT。

验收标准：A/B 两个 rootfs 启动后都能看到同一个
`userdata` PARTUUID，其中的测试文件和 OTA session 在两次
bank 切换中保持不变。

### Step 2：固化 rootfs 版本和 OTA 运行环境

以 `conf/amp_rootfs_post_build.sh` 作为 rootfs 的统一落盘入口，
计划完成：

1. 将受控的系统版本写入 `$TARGET_DIR/etc/version`；
2. 安装 `ota_info`、`ota_package`、`ota_client`、`libbh_ota.so*`
   和必要的 `libcrypto`；
3. 安装 `/usr/libexec/ota-client/` 和 `/lib/ota/` 脚本；
4. 安装 `/etc/ota/client.conf`、设备身份配置和
   `/etc/ota/keys/ota_public.pem`；
5. 私钥永远不得复制到 rootfs、NFS root 或 OTA 包。

`/etc/version` 必须与构建 OTA 包时的 `--sys-version` 来自
同一受控参数，不允许人工分别填写。如果二者不一致，
打包阶段应拒绝发布。

验收标准：不挂载 NFS 时，A/B rootfs 都能直接运行
`ota_info`、`ota_package` 和 `ota_client`，且包验签使用的公钥
哈希与发布公钥一致。

### Step 3：开机安全恢复 stage2 和 `boot_success`

本步骤已在源码中完成 `service_start` 的 rootfs 集成和健康门禁，尚未构建及
板端验证。持久 rootfs 由 `basic_middleware/ota_client/build.sh` 安装
`S95ota-stage2.sh`，该脚本在主要 SysV 服务启动后调用统一的
`ota-package service_start` 入口。

开机时序固定为：

```text
stage1_end，新 bank 启动
  -> userdata 挂载成功
  -> 核对 current_bank/target_bank/rootfs/PARTUUID
  -> 核对 /etc/version == manifest.sys_version
  -> 关键服务健康检查
  -> verify_stage2 -> apply_stage2 -> commit_stage2
  -> 重启到 stage2 更新后的另一 bank
  -> 再次执行 bank/rootfs/version/关键服务健康检查
  -> boot_success
```

禁止在用户态刚起来时立即无条件执行 stage2。stage2 会
覆盖原来可回退的 bank，因此第一次新 bank 健康检查是
保留回退能力的最后门禁。

服务必须具备：

- 单实例锁，避免 init 脚本与手工命令并发执行；
- 幂等恢复，对 `stage1_start`/`stage1_wrote`/
  `stage2_start`/`stage2_wrote` 只从已记录进度继续；
- 失败时保留 OTA 包、状态和日志，不自动清理；
- 只有 `boot_success` 成功后才将 session 标记为 complete。

当前健康门禁集中在 `lib/ota/health.sh`，会交叉核对：

- `/userdata` 的实际挂载源 PARTLABEL，防止在 rootfs 同名目录上继续；
- recovery `current_bank`/`target_bank` 与内核 `active_bank`；
- 根挂载设备的 `rootfs_a/b` PARTLABEL 和内核 `root=PARTUUID`；
- `/etc/version`、发布状态 `target_version` 和 manifest `sys_version`；
- `/etc/ota/health-check.d/` 下所有可执行的产品关键服务健康钩子。

迁移设备仅在根分区 GPT PARTLABEL 缺失时，允许从实际根块设备的 sysfs
分区号核对 A=p4、B=p6，并继续强制核对 `active_bank` 和 PARTUUID。若
PARTLABEL 已存在但不是预期的 `rootfs_a/rootfs_b`，不得降级到数字回退。

`unpack`、`install` 和 `service_start` 共用 `package` 锁。stage1/stage2 提交
bank 切换后由恢复服务执行重启；`complete(17)` 保留发布状态和包，清理策略
仍属于后续运维治理步骤。

验收标准：断电发生在任一 payload 后都可从记录位置
继续；健康检查失败时不写另一 bank；只有两个 bank 的
新版本均完成并实际启动后才进入 `complete(17)`。

### Step 4：完成 OTA 写入性能和进度透传

`basic_middleware/ota_package/lib/bh_ota_package_writer.c` 已计划并已
写入以下源码修改：

- boot/rootfs 取消每 64 KiB write 的 `O_SYNC`；
- boot/rootfs 块设备均改为缓冲写入；
- 整个文件或分区内容写完后统一 `fsync()`；
- 保留落盘后回读比较；
- 对 `write`/`zero-fill`/`verify` 输出 5% 颗粒度进度。

但 `ota_client` 的 `run_ota_step()` 目前使用：

```sh
output=$("$@" 2>&1)
```

这会在子进程结束后才一次性输出进度。计划改为实时
直通 stdout/stderr，同时将输出追加到当前 session 日志，并
保留 `ota_package` 的原始退出码。不能用一个会丢失左侧
进程退出码的简单 `command | tee` 替代。

验收标准：直接运行 `ota_package` 和通过 `ota_client`
运行时都能实时看到同样的进度，且写入失败时上层返回
非零状态。需要在同一张 SD 卡、同一份 payload 上记录
优化前后 stage 耗时，不只根据主观感受验收。

### Step 5：rootfs 首次启动自动扩容

Buildroot 当前通过 `BR2_TARGET_ROOTFS_EXT2_SIZE="500M"` 生成
500 MiB ext4 文件系统镜像。当它被写入 2 GiB rootfs 分区
时，块设备是 2 GiB，但 `df` 只能看到 ext4 自身的 500 MiB。

计划修改：

1. 在 `conf/buildroot_rootfs_config` 中启用目标机 `resize2fs`；
2. 增加早期 SysV init 脚本，用 `findmnt -n -o SOURCE /` 或
   `/proc/cmdline` 定位当前 rootfs；
3. 校验该设备的 PARTLABEL 必须是 `rootfs_a` 或 `rootfs_b`；
4. 在 ext4 支持的条件下执行在线 `resize2fs <device>`；
5. 已经扩到最大时作为幂等成功，失败时不推进 OTA
   健康门禁。

扩容只改变 ext4 文件系统的可用 block 数，不修改 GPT
分区起止位置。rootfs 发布镜像仍保持 500 MiB，避免把
2 GiB 镜像放入 OTA 包。

验收标准：A/B 两个 rootfs 各自首次启动后，`df`
显示的文件系统容量接近所在 GPT 分区容量；重复启动
不报错；扩容脚本不会对 `userdata` 或非 rootfs 设备执行。

### Step 6：boot bundle 同步更新 `vf2_uEnv.txt`

boot payload 使用 SDK 已生成的完整 FAT 分区镜像：

```text
starfive-visionfive2-vfat.part
|-- starfiveu.fit
`-- vf2_uEnv.txt
```

顶层 Makefile 在生成 AMP FAT 镜像时将当前 `work/amp/image.fit`
以 `starfiveu.fit` 的名称写入镜像，并将完整镜像发布到
`work/target/amp/starfive-visionfive2-vfat.part`。打包脚本把该
镜像作为单个 `boot_a/b` payload 参与摘要和签名；writer 从
boot 分区 offset 0 开始整镜像写入，统一 `fsync()` 后回读校验。
只有完整 FAT 镜像校验成功后才记录该 boot payload 成功。

FAT 不提供与日志型文件系统相同的掉电原子性，因此仍需
依赖 OTA 状态机和未提交 bank 防止启动写入不完整的 boot 分区。

验收标准：manifest 中完整 FAT 镜像的摘要与回读结果一致，挂载后
同时存在同一构建生成的 `starfiveu.fit` 和 `vf2_uEnv.txt`；整镜像
校验失败不推进 payload 计数；启动时 FIT/rootfs/bank 继续严格配对。

### Step 7：公钥轮换、包清理和失败日志

#### 7.1 公钥轮换

不直接用新公钥覆盖旧公钥。建议流程：

1. key-A 签名的过渡版本把 key-B 公钥安装到 A/B rootfs；
2. 过渡期信任 key-A 和 key-B；
3. manifest `key_id` 必须参与选钥，未知或已撤销
   `key_id` 直接拒绝；
4. 后续包改用 key-B 签名；
5. 确认设备群已迁移后，再由 key-B 签名的版本撤销 key-A。

撤销信息不能只放在会被 A/B 覆盖的单一 rootfs 中，需要
同时考虑 recovery 防回滚索引或受控的持久化策略。

#### 7.2 包清理

- 下载前检查 `/userdata` 可用空间；
- 仅清理不属于活跃 session 的过期 `.part` 和解包目录；
- `idle/complete` 可清理成功包，不在 stage1/stage2 未完成时
  删除当前包；
- 默认可保留最近一个失败 session 的 manifest、签名和
  日志，大 payload 按容量策略删除。

#### 7.3 长期失败日志

日志使用 `/userdata/ota/log/<session_id>.log`，至少记录：

- `current_bank`/`target_bank`、当前/目标版本；
- stage、payload、字节进度、耗时和错误码；
- recovery 状态变化、重启原因和健康检查结果；
- 公钥 `key_id` 和公钥指纹，不记录私钥或 API token。

在关键状态变化和失败记录后执行持久化同步，设置
总容量、单文件大小和保留 session 数上限。

## 6. 最终效果

所有步骤完成后，系统应达到：

1. A/B 两个 rootfs 都是可独立运行的 OTA 环境，不依赖
   `/mnt` 或临时版本文件。
2. `/userdata` 在 A/B 之间共享，包、session 和失败日志可
   跨重启、跨 bank 保留。
3. 一次 OTA 依次完成“更新非活动 bank—启动健康检查—
   更新另一 bank—再次启动确认—complete”，中断后可继续。
4. 用户可实时看到 boot/rootfs 写入、补零和回读进度，
   不再由每 64 KiB 同步写放大 SD 耗时。
5. 运行中的 ext4 rootfs 使用完整 GPT 分区容量，OTA
   发布镜像仍保持较小体积。
6. `starfiveu.fit` 与 `vf2_uEnv.txt` 通过完整 FAT 镜像作为
   同版本 boot payload 更新，避免新旧启动配置混用。
7. OTA 包继续由 RSA-2048 + SHA-256 签名保护，不增加
   自定义镜像头；公钥可通过双钥流程安全轮换。

## 7. 构建、部署与测试命令

以下是实施完成后应执行的验证方案。本轮源码和文档修改
尚未执行构建、测试或板端验证。

### 7.1 主机：构建和打包

```bash
cd /home/xikao/VisionFive2_6.6

export RVROOT=$PWD/work/buildroot_initramfs/host
export CROSS_COMPILE=$RVROOT/bin/riscv64-buildroot-linux-gnu-
export PATH=$RVROOT/bin:$PATH
export TRUSTED_CROSS_COMPILE=/opt/riscv/bin/riscv64-unknown-elf-

printf '1.2.4\n' > conf/ota/sys-version
./build.sh keygen
make ampfit RTOS=freertos -j$(nproc)
./build.sh ota all
./build.sh package \
  --rollback-index 10204 \
  --session-id ota-test-20260912-001 \
  --target-bank b \
  --include-stage2
```

`conf/ota/sys-version` 是 rootfs `/etc/version` 与 OTA manifest
`sys_version` 的唯一受控来源。打包命令仍兼容显式
`--sys-version`，但其值或待发布 rootfs 镜像内的 `/etc/version`
与受控文件不一致时会在签名前拒绝发布。
`keygen` 必须先于 rootfs 构建执行，使发布公钥进入镜像；`package`
只校验签名私钥与 `conf/ota/keys/ota_public.pem` 匹配，不会在打包时
生成或替换密钥，并会拒绝公钥与受控副本不一致的 rootfs 镜像。

主机静态检查：

```bash
grep -n '^BR2_PACKAGE_E2FSPROGS_RESIZE2FS=y' conf/buildroot_rootfs_config
debugfs -R 'cat /etc/version' work/target/amp/rootfs.ext4
find nfs_rootfs/bin nfs_rootfs/lib nfs_rootfs/etc/ota \
  -maxdepth 4 -type f -print | sort
openssl pkey -pubin -in nfs_rootfs/etc/ota/keys/ota_public.pem \
  -outform DER | sha256sum
grep -E '"sys_version"|"session_id"|"rollback_index"|"key_id"' \
  nfs_rootfs/ota_package/data.json
```

## 8. 风险与回退

| 风险 | 控制和回退 |
| --- | --- |
| 现有 SD GPT 与新 PARTLABEL 不一致 | 优先使用新卡/整盘镜像验证；在线改 GPT 前备份数据 |
| `/userdata` 挂载失败 | 禁止 stage2，保留当前 bank 和 recovery 状态 |
| 健康检查过早通过 | 将 rootfs/bank/version/关键服务列为必须项，支持延时和重试 |
| stage2 覆盖旧回退 bank | 只在新 bank 健康后执行，执行前保留 session 和日志 |
| rootfs 扩容选错设备 | 必须核对当前 `/` 源设备及 PARTLABEL，不使用写死分区号 |
| boot 分区镜像写入中掉电 | 整镜像回读 + 未提交 bank；恢复后重写当前 payload |
| 新公钥导致旧设备无法升级 | 必须经过 key-A/key-B 双钥过渡，不单次强制替换 |
| OTA 包/日志占满 `userdata` | 下载前空间门禁、活跃 session 保护、容量和数量轮转 |

如果新 rootfs 集成失败，回退时保留原 bank 的 rootfs/boot，
不执行 stage2；如果新整盘布局失败，使用事先备份的
整盘镜像恢复，不通过 OTA 包修复 GPT。
