# VisionFive2 Linux 与 FreeRTOS IPI Mailbox 实现方案

## 1. 文档目的

本文给出 VisionFive2 AMP 场景下 Linux hart1 与 FreeRTOS hart4 之间 IPI Mailbox 的实现方案，覆盖共享内存协议、OpenSBI 通知、Linux/FreeRTOS controller、业务 router、资源归属、异常恢复以及构建和验收方法。

本文是实施设计，不代表文中计划修改已经完成，也不代表完整 AMP 镜像或开发板已经验证。

## 2. 背景与现状

### 2.1 为什么使用 IPI Mailbox

本项目需要让 Linux、U-Boot proper 与 hart4 上的 FreeRTOS 服务通信。生产链路采用：

```text
共享内存保存 payload 和通道状态
OpenSBI AMP IPI 通知目标 hart
Mailbox router 按 service ID 分发业务
```

这样可以将职责分开：OpenSBI 不解析业务数据，mailbox controller 不识别服务，业务 consumer 不直接操作 IPI 共享内存。

### 2.2 当前已有基础

仓库已经包含以下实现基础：

- FreeRTOS IPI controller：`trusted_domain/driver/mailbox/ipi_mailbox.c`；
- FreeRTOS router：`trusted_domain/driver/mbox_router/`；
- Linux router 和 consumer：`bsp/ipi_mailbox/consumer/`；
- OpenSBI AMP IPI 扩展：`opensbi/lib/sbi/sbi_ipi.c`；
- Linux SBI/IPI 接入：`linux/arch/riscv/kernel/sbi.c`、`linux/arch/riscv/kernel/sbi-ipi.c` 和 `linux/arch/riscv/kernel/smp.c`；
- AMP 设备树：`linux/arch/riscv/boot/dts/starfive/jh7110-starfive-visionfive-2-amp.dts`；
- 共享 router 协议：`common_inc/bsp/quard_router_protocol.h`。

现有 DTS 已定义 `0x6E402000`、大小 `0x2000` 的 mailbox 保留内存，并将 hart4 从 Linux CPU 和 PLIC context 中排除；UART2 和 QSPI 也不交给 Linux。

### 2.3 实施前必须收敛的现状差异

当前 Linux 树中存在两个匹配 `starfive,ipi-amp-mailbox` 的 provider：

| 文件 | 当前协议 | 当前配置 |
| --- | --- | --- |
| `linux/drivers/mailbox/quard_ipi_mailbox.c` | 2 个 32 字节通道、28 字节 payload、三态 ACK | `CONFIG_QUARD_IPI_MBOX` |
| `linux/drivers/mailbox/starfive_ipi_mailbox.c` | 历史 queue/offset 布局 | `CONFIG_STARFIVE_IPI_MBOX` |

当前两个 VisionFive2 defconfig 启用的是 `CONFIG_QUARD_IPI_MBOX=y`，而生产约束指定 Linux controller 统一由 `starfive_ipi_mailbox.c` 和 `CONFIG_STARFIVE_IPI_MBOX` 提供。实施时必须先将已经使用的固定 28 字节协议和恢复逻辑收敛到唯一生产 provider，再完成配置切换；不能同时启用两个匹配同一 `compatible` 的驱动。

此外，当前 FreeRTOS 与 Linux 端分别维护了一套通道常量，router header 使用 C bit-field 表示。实施时应增加共享 ABI 头文件和编译期断言，避免两端布局静默漂移。

## 3. 目标、范围与非目标

### 3.1 目标

1. 在 Linux hart1 与 FreeRTOS hart4 之间提供可靠的双向、定长消息传输。
2. 使用 Linux mailbox framework 向 router 暴露标准 `mbox_chan` 接口。
3. 通过一个 router 复用物理双向通道，承载日志、vshell 和 NOR 三类服务。
4. 保证中断上下文只确认或复制消息并唤醒任务，业务处理全部下沉到任务或 workqueue。
5. 将共享状态作为事实来源，将 IPI 仅作为通知；通知被合并或丢失时能够恢复。
6. 保持 hart4、UART2 和物理 QSPI 由 FreeRTOS 独占。

### 3.2 本期范围

- 共享内存 mailbox ABI；
- Linux 和 FreeRTOS mailbox controller；
- OpenSBI AMP IPI 发送和清除路径；
- Linux 和 FreeRTOS router；
- service `0`、`1`、`2` 的注册和分发；
- DTS、Kconfig、Makefile 和顶层构建依赖；
- 连续双向通信、异常恢复和板端验收方案。

### 3.3 非目标

- 不使用 JH7110 物理 mailbox 外设；
- 不在本期引入 RPMsg、virtio 或 OpenAMP；
- 不支持一个方向多条未完成消息或无界队列；
- 不通过 28 字节 mailbox payload 搬运 NOR 大块数据；
- 不让 Linux 或 U-Boot proper 直接访问物理 QSPI；
- 不为调试客户端和生产 router 提供并发占用同一通道的能力。

## 4. 关键约束与资源归属

| 资源 | 所有者 | 约束 |
| --- | --- | --- |
| hart1 | Linux | Linux 侧 mailbox 和业务 consumer 运行位置 |
| hart4 | FreeRTOS | 不作为 Linux CPU，不向 Linux 暴露其 PLIC context |
| UART2 | FreeRTOS | 基址 `0x10020000`，PLIC IRQ 34；Linux DTS 删除该节点 |
| IPI mailbox 内存 | 双方共享 | 基址 `0x6E402000`，DTS 使用 `reserved-memory` 和 `no-map` |
| QSPI/NOR | FreeRTOS | Linux/U-Boot proper 只能调用 mailbox NOR agent |
| NOR bulk buffer | 双方共享 | `0x6E500000`，大小 `0x200000`，只传大块数据，不代替 mailbox 控制消息 |

生产环境必须保持以下组件禁用：

```text
amp-virtio-rpmsg
starfive_rpmsg
ipi-mailbox-test
CONFIG_STARFIVE_MBOX
CONFIG_STARFIVE_MBOX_TEST
CONFIG_STARFIVE_IPI_MBOX_TEST
```

直接测试客户端只能在停止或卸载生产 router 后单独使用，不能与 `quard_mbox_router` 同时申请 channel 0/1。

## 5. 总体架构

```text
Linux consumer
  log / vshell / NOR client
             |
             v
      quard_mbox_router
             |
             v
 starfive_ipi_mailbox controller
             |
      channel 1 request
      channel 0 response
             |
       共享内存状态机
             |
       OpenSBI AMP IPI
             |
             v
 FreeRTOS IPI controller
             |
             v
   FreeRTOS router queue/task
             |
       +-----+-----+
       |     |     |
      log  vshell  NOR agent
```

必须保持以下依赖方向：

```text
Linux NOR client -> Linux router -> Linux IPI controller
                                      |
                               共享内存 + SBI IPI
                                      |
FreeRTOS NOR agent <- FreeRTOS router <- FreeRTOS IPI controller
```

## 6. 共享内存与线协议

### 6.1 通道布局

共享区前 64 字节定义两个单向通道：

| 地址 | 通道 | 方向 | 内容 |
| --- | ---: | --- | --- |
| `0x6E402000` | 0 | FreeRTOS -> Linux | `payload[28]` + `state[4]` |
| `0x6E402020` | 1 | Linux -> FreeRTOS | `payload[28]` + `state[4]` |

每个通道的 ABI 为：

```c
struct quard_ipi_slot {
    uint8_t payload[28];
    uint32_t state;
};
```

实现必须对结构大小、`state` 偏移和 router 消息大小执行编译期断言：

```text
sizeof(quard_ipi_slot) == 32
offsetof(quard_ipi_slot, state) == 28
sizeof(quard_mbox_msg) == 28
```

DTS 保留 `0x2000` 是为了固定共享区域边界，不表示单条消息或 channel 可以使用全部空间。

### 6.2 Router 消息格式

28 字节 payload 分为 4 字节 header 和 24 字节参数：

```text
31                         24 23             16 15                0
+----------------------------+-----------------+-------------------+
| command                    | service ID      | CRC16/reserved    |
+----------------------------+-----------------+-------------------+
| params[0] ... params[5]                                           |
+--------------------------------------------------------------------+
```

字段定义：

| 字段 | 宽度 | 说明 |
| --- | ---: | --- |
| CRC16 | 16 bit | 当前协议保留为 0；启用前必须同时修改两端并增加兼容策略 |
| service ID | 8 bit | `0` 日志、`1` vshell、`2` NOR |
| command | 8 bit | 由具体 service 定义 |
| params | 6 x 32 bit | 固定宽度参数或共享内存描述符 |

共享头文件应使用 mask、shift 和 getter/setter 表达 header，不继续依赖跨编译器 bit-field 排布。线协议全部使用固定宽度整数，禁止使用指针、`size_t`、`unsigned long` 或编译器相关枚举大小。

### 6.3 通道状态机

```text
                 发送 payload + DATA_READY
          +------------------------------------+
          |                                    v
       IDLE(0)                            DATA_READY(1)
          ^                                    |
          |                                    | 对端复制 payload
          +------------------------------------+
                    ACK(2) -> IDLE
```

规则如下：

1. 发送端只允许在 `IDLE` 状态写入；否则返回 `-EBUSY`，不得覆盖旧消息。
2. 发送端先完整写 payload，执行写屏障，再写 `DATA_READY`，最后发送 IPI。
3. 接收端以 acquire/read barrier 读取 state；看到 `DATA_READY` 后先复制 28 字节到本地缓冲区。
4. 接收端复制完成后写 `ACK` 并通知发送端。
5. 发送端观察到 `ACK` 后写回 `IDLE`，再向 mailbox framework 或等待任务报告完成。
6. payload 在发送完成前归发送端所有；接收 callback 得到的是本地副本，不能保留指向共享 slot 的指针。

每个方向最多有一条在途消息。并发发送由 Linux router mutex 或 FreeRTOS channel mutex 串行化。

### 6.4 IPI 类型与通道方向

IPI 参数是 bit 编号，接收方取得的是 bitmask：

| IPI type | Linux 视角 | FreeRTOS 处理 |
| ---: | --- | --- |
| `0` | RX：FreeRTOS 发来的数据/ACK 通知 | FreeRTOS 自身 TX 完成 |
| `1` | TX：Linux 发出的数据/ACK 通知 | FreeRTOS RX 请求 |

例如 `sbi_send_ipi_amp(4, 1)` 会使 hart4 读取到 bit1，即 `msg_type & (1UL << 1)` 非零。实现和日志必须区分“type 编号 1”与“bitmask 值 0x2”。

## 7. OpenSBI AMP IPI 设计

### 7.1 接口职责

OpenSBI 扩展只管理目标 hart 的 AMP pending bitmap 和 SSIP：

- 发送：原子设置目标 hart 的 `msg_type` bit，再触发 supervisor software interrupt；
- 注册：Linux 提供 per-hart AMP bitmap 的物理地址；
- 清除：目标 hart 清除 SSIP，并原子取走自己的 AMP pending bitmap。

OpenSBI 不访问 mailbox payload，不解析 channel state，也不分发 service。

### 7.2 清除顺序

FreeRTOS 调度器 yield 与 mailbox 共用 SSIP，必须同时保留两类处理：

```text
FreeRTOS SSIP trap
  -> sbi_clear_ipi_amp() 读取 AMP bits
  -> sbi_clear_ipi() 清除调度器要求的标准 SSIP
  -> 再次读取并合并竞态窗口内到达的 AMP bits
  -> 按 bit 处理 mailbox
  -> trap 出口统一调度一次
```

OpenSBI 的扩展清除逻辑必须保持“先清 SSIP、再原子取走 AMP bit”的顺序。若先取 bit 再清 SSIP，新通知可能在两步之间到达，其 SSIP 随后被旧流程清掉，导致共享状态停在 `DATA_READY` 而不再产生通知。

## 8. Linux 侧设计

### 8.1 Provider 收敛

最终只保留一个匹配 `starfive,ipi-amp-mailbox` 的生产 provider：

```text
linux/drivers/mailbox/starfive_ipi_mailbox.c
CONFIG_STARFIVE_IPI_MBOX
```

计划将 `quard_ipi_mailbox.c` 中与本协议一致的能力迁入该文件：

- 两个 32 字节 channel；
- `IDLE/DATA_READY/ACK` 状态机；
- 28 字节固定复制；
- Linux mailbox framework 的 `send_data` 和 `last_tx_done`；
- 丢通知恢复、统计和 ratelimited 异常日志；
- remove 时注销 handler 并同步取消 delayed work。

完成迁移后，defconfig 应切换为：

```text
CONFIG_STARFIVE_IPI_MBOX=y
# CONFIG_QUARD_IPI_MBOX is not set
CONFIG_QUARD_MBOX_ROUTER=y
# CONFIG_STARFIVE_MBOX is not set
# CONFIG_STARFIVE_MBOX_TEST is not set
# CONFIG_STARFIVE_IPI_MBOX_TEST is not set
```

`STARFIVE_IPI_MBOX` 的 Kconfig 默认值保持关闭，仅由 AMP defconfig 明确启用。`QUARD_MBOX_ROUTER` 的依赖同步改为 `depends on STARFIVE_IPI_MBOX`。

### 8.2 发送路径

```text
consumer
  -> quard_mbox_send_msg()
  -> router mutex
  -> mbox_send_message()
  -> provider 检查 channel 1 == IDLE
  -> 复制 28 字节
  -> DATA_READY
  -> sbi_send_ipi_amp(hart4, type 1)
  -> mailbox core 轮询 last_tx_done()
  -> ACK -> IDLE
```

初次 SBI 发送失败时，只有在 state 仍为 `DATA_READY` 的情况下才回滚为 `IDLE`；若对端已经推进状态，不能覆盖对端结果。

### 8.3 接收路径

Linux IPI handler 只完成：

1. 检查 channel 0 的 `DATA_READY`；
2. 复制 28 字节到栈或预分配缓冲区；
3. 更新 `ACK`；
4. 调用 mailbox core callback；
5. 通知 hart4 回收 ACK。

router callback 只解析 header 并将消息放入对应 consumer 的 workqueue。日志、TTY 处理、NOR 请求完成等业务不得直接放在 IPI handler 中执行。

中断路径不得使用可能睡眠的分配。现有 `GFP_ATOMIC` 可作为过渡实现，正式实现优先使用预分配 work item 或固定深度 mempool，避免内存压力导致消息已经 ACK 却无法交付 consumer。

### 8.4 丢通知恢复

共享 state 是事实来源，IPI 只是通知。Linux provider 使用低频 delayed work：

- 发现 RX `DATA_READY` 时主动走接收复制流程；
- 发现 TX `DATA_READY` 时重新通知 hart4；
- 发现 RX 已为 `ACK` 且不在 callback 中时重新通知 hart4；
- mailbox core 通过 `last_tx_done()` 观察 TX `ACK` 并恢复 `IDLE`。

恢复周期是兜底机制，不代替正常 IPI。正常收发不逐条打印日志，只记录 `-EBUSY`、stale ACK、SBI 失败和 recovery kick 失败等异常计数。

### 8.5 初始化和卸载

- provider 必须先于 router 和 consumer probe；consumer 找不到 router 时返回 `-EPROBE_DEFER`；
- 共享 slot 只能在冷启动且业务尚未注册时初始化；模块重载不得无条件 `memset()` 活跃共享区；
- 若需要运行时重置，必须先停止两个方向的新发送，确认双方 quiesce，再同时重置 channel；
- provider remove 先阻止新 callback，再注销 IPI handler、取消 delayed work，最后释放 mailbox controller 资源。

## 9. FreeRTOS 侧设计

### 9.1 Controller

`trusted_domain/driver/mailbox/ipi_mailbox.c` 负责：

- 将 channel 0 配置为 FreeRTOS TX；
- 将 channel 1 配置为 FreeRTOS RX；
- 使用静态 mutex 串行化 TX；
- 使用静态 binary semaphore 等待 TX ACK；
- 发送超时返回 `-ETIMEDOUT`，通道非空闲返回 `-EBUSY`；
- 在 SSIP handler 中复制 RX、设置 ACK，或将 TX 的 `ACK` 恢复为 `IDLE` 并唤醒等待任务。

发送等待只允许在任务上下文发生。ISR 不得获取 mutex、阻塞或等待 ACK。

### 9.2 ISR 边界

FreeRTOS IPI/SSIP handler 只允许：

- 清除并合并 AMP IPI bits；
- 读取 channel state；
- 复制固定 28 字节消息；
- 更新 ACK/IDLE；
- 使用 `xQueueSendToBackFromISR()` 或 `xSemaphoreGiveFromISR()` 唤醒任务。

禁止在该上下文中：

- 调用日志系统或 Remote Shell 打印；
- 分发并执行 service callback；
- 访问 SPI NOR；
- 阻塞或等待；
- 再次调用 `portYIELD_FROM_ISR()`。

当前 RISC-V SSIP trap 出口已经调用 `vTaskSwitchContext()`；router RX callback 再请求切换会在一次 trap 内重复调度。

### 9.3 Router task

FreeRTOS router 根据 header 中的 service ID 找到唯一 consumer，把 ISR 复制的消息放入该 consumer 的静态 queue，由 `mbox_c0`、`mbox_c1`、`mbox_c2` 等任务调用业务 callback。

注册要求：

- service ID 必须小于 `QUARD_SERVER_ID_MAX`；
- 一个 service ID 只允许注册一次；
- consumer queue、stack 和 task control block 使用静态内存；
- 业务依赖的内部 queue 必须先创建，再注册 mailbox consumer；
- consumer queue 满或 service 未注册时只更新计数，ISR 路径不得通过 mailbox 日志后端报错。

### 9.4 错误日志防递归

日志和 vshell 本身经过 mailbox。底层发送失败时如果调用 `LOG_E()`，可能形成：

```text
mailbox 发送失败
  -> LOG_E
  -> mailbox log backend
  -> 再次发送失败
  -> 递归直至栈溢出
```

因此 controller/router 底层函数只返回错误码并更新内存计数。需要输出时，由不复用 mailbox 的上层或调试阶段轮询 UART 完成。

## 10. Router 与业务接口

### 10.1 服务表

| service ID | 服务 | Linux consumer | FreeRTOS consumer |
| ---: | --- | --- | --- |
| `0` | 日志 | `quard_log` | log backend/agent |
| `1` | vshell | `quard_remote_console` | shell agent |
| `2` | NOR | `quard_nor_client` | `quard_nor_agent` |

Linux consumer 通过 DTS 的 `mbox-router-server` phandle 绑定 service 节点；FreeRTOS consumer 通过 `server_to_router_map[]` 绑定到 router 0。

### 10.2 NOR 大块数据

28 字节消息只传递 `op_offset`、`op_len`、`status`、共享内存物理地址和 checksum。实际读写数据使用 `0x6E500000` 的 2 MiB 共享区：

```text
Linux NOR client
  -> 写 bulk buffer + wmb
  -> mailbox 发送控制消息
  -> FreeRTOS NOR task 校验参数和 checksum
  -> SPI NOR 操作
  -> mailbox 返回状态/checksum
```

NOR agent 必须在任务上下文访问 QSPI，并验证地址范围、长度、共享内存范围和对齐要求。mailbox ISR 不得直接执行 NOR 操作。

## 11. DTS 与配置设计

AMP DTS 保持以下结构：

```dts
reserved-memory {
    ipi_mailbox_reserved: ipi-mailbox@6e402000 {
        reg = <0x0 0x6e402000 0x0 0x2000>;
        no-map;
    };
};

ipimb: ipimb@0 {
    compatible = "starfive,ipi-amp-mailbox";
    reg = <0x0 0x6e402000 0x0 0x2000>;
    #mbox-cells = <2>;
    rtos-hart-id = <4>;
    status = "okay";
};
```

router 的 cell 语义为 `<type channel-index>`：

```dts
mboxes = <&ipimb 1 1>, <&ipimb 0 0>;
mbox-names = "router-tx", "router-rx";
```

同时必须满足：

- `amp-virtio-rpmsg` 和 direct test 节点为 `disabled`；
- `&U74_4` 为 `disabled`；
- Linux 删除 `serial@10020000`；
- `&qspi` 为 `disabled`；
- PLIC `interrupts-extended` 不包含 hart4 context；
- Linux 使用的 CPU intc 节点启用 AMP IPI 接收能力。

| `linux/arch/riscv/boot/dts/starfive/jh7110-starfive-visionfive-2-amp.dts` | 核对唯一 provider、通道映射和资源排除 | 固化硬件及共享内存归属 |

## 13. 实施步骤

1. 新增共享 mailbox ABI 头文件，先保持现有 wire 值不变，并给三端增加静态断言。
2. 将 Linux 正确的 28 字节 provider 行为收敛到 `starfive_ipi_mailbox.c`。
3. 修改 Kconfig、Makefile 和 defconfig，确保只能选中一个生产 provider。
4. 收紧 Linux RX 的中断边界和预分配策略，保留状态轮询恢复。
5. 让 FreeRTOS controller 使用共享 ABI，并移除 ISR 内所有日志和业务分发。
6. 核对 OpenSBI SSIP 清除顺序和 Linux AMP bitmap 注册路径，不改动业务协议。
7. 核对 DTS 通道映射、reserved-memory、hart4/PLIC/UART2/QSPI 归属。
8. 更新顶层构建依赖，使共享头、controller、router 和 DTS 变化能触发对应产物更新。
9. 完成静态检查后，再按用户明确要求执行完整构建、部署和板端验证。

## 14. 构建、部署与验证方案

以下内容是实施完成后的验证方法，本次编写方案文档不执行这些命令。

### 14.1 主机构建

使用项目指定工具链：

```bash
export RVROOT=$PWD/work/buildroot_initramfs/host
export CROSS_COMPILE=$RVROOT/bin/riscv64-buildroot-linux-gnu-
export PATH=$RVROOT/bin:$PATH
export TRUSTED_CROSS_COMPILE=/opt/riscv/bin/riscv64-unknown-elf-
make ampfit RTOS=freertos -j$(nproc)
```

若 router/NOR client 仍以外部模块交付，则基于本次内核输出构建：

```bash
make -C bsp/ipi_mailbox/consumer \
  KERN_DIR=$PWD/linux KBUILD_OUTPUT=$PWD/work/linux ARCH=riscv \
  CROSS_COMPILE=$PWD/work/buildroot_initramfs/host/bin/riscv64-buildroot-linux-gnu- \
  modules
```

构建后检查：

```bash
grep '^CONFIG_STARFIVE_IPI_MBOX=' work/linux/.config
grep -E '^CONFIG_(QUARD_IPI_MBOX|STARFIVE_MBOX|STARFIVE_MBOX_TEST|STARFIVE_IPI_MBOX_TEST)=' work/linux/.config
```

第一条必须为 `y` 或 `m`；第二条不应出现启用项。

### 14.2 产物与部署

只部署最近一次成功构建的准确产物：

```text
work/u-boot-amp-spl.bin.normal.out
work/visionfive2_fw_payload_amp.img
work/amp/image.fit
```

单独部署的 router、NOR 模块和测试程序统一放在 `work/amp/nor_modules/`。复制到 `/srv/tftp/` 后，必须比较工作区与 TFTP 副本的 SHA-256，并记录单独模块哈希。

U-Boot proper 阶段通过 mailbox-backed MTD 部署 SPL 和 payload：

```text
tftpboot 0xa0000000 u-boot-amp-spl.bin.normal.out
mtd erase spl_a 0x0 0x40000
mtd write spl_a 0xa0000000 0x0 $filesize
tftpboot 0xa0000000 visionfive2_fw_payload_amp.img
mtd erase fw_payload_a 0x0 0x600000
mtd write fw_payload_a 0xa0000000 0x0 $filesize
tftpboot ${loadaddr} image.fit
```

AMP U-Boot proper 禁止使用 `sf probe/read/update` 直接访问 QSPI。

### 14.3 板端加载顺序

如果 provider 内建则省略第一条：

```bash
modprobe starfive_ipi_mailbox
insmod /tmp/quard_mbox_router.ko
insmod /tmp/quard_nor_client.ko
```

不得同时加载旧 mailbox、测试客户端或 RPMsg transport。

### 14.4 验证分层

#### 配置和资源

- 核对运行内核 config；
- 核对 `/proc/iomem` 与 live DT 中的 mailbox reserved-memory；
- 确认 Linux 不拥有 UART2、QSPI 和 hart4 PLIC context；
- 确认模块 release、vermagic 和哈希与本次构建一致。

#### 启动证据

取得与以下内容等价的日志：

```text
FreeRTOS IPI mailbox init successful: base=0x6e402000
mailbox router ready
router server mbox_c2 started
registered 6 GPT partitions
```

并分别记录 FIT 创建时间、Linux release、FreeRTOS 构建时间，证明开发板运行的是本次产物。

#### 状态机和压力

1. 连续执行 Linux -> FreeRTOS 请求，确认 channel 1 重复完成 `IDLE -> DATA_READY -> ACK -> IDLE`。
2. 连续执行 FreeRTOS -> Linux 返回和异步日志，确认 channel 0 同样回到 `IDLE`。
3. 运行 remote shell 连续输入和回显，不出现 ACK timeout、长期 `-EBUSY` 或 SSIP 连续重入。
4. 人为延迟一次处理，确认 recovery 能重新通知，且不会重复交付同一 payload。
5. 检查异常计数；正常压力运行不应持续增加 `tx_busy`、`tx_ipi_error` 或 recovery failure。

#### NOR 服务

检查 `/proc/mtd`、NOR geometry 和 6 个 GPT 分区。破坏性测试只允许操作 `recovery` 分区前 4 KiB：测试前备份，完成读、写、擦除、非法请求后恢复，并逐字节比较一致。

### 14.5 验收标准

只有同时满足以下条件，才能报告 mailbox 完整链路已经验证：

- 所有受影响组件和完整 AMP 镜像构建成功；
- `CONFIG_STARFIVE_IPI_MBOX` 为 `y` 或 `m`，冲突 provider、测试客户端和 RPMsg transport 均禁用；
- 部署产物、模块版本、vermagic、时间戳和 SHA-256 与本次构建一致；
- 板端运行预期的 Linux、FIT 和 FreeRTOS；
- 双向状态机在连续通信后都能回到 `IDLE`，无 timeout 和持续 `-EBUSY`；
- router 三类服务正确分发，NOR client 注册 6 个 GPT 分区；
- 若执行 NOR 破坏性测试，`recovery` 前 4 KiB 已恢复且逐字节一致。

## 15. 异常处理

| 异常 | 处理 | 禁止行为 |
| --- | --- | --- |
| TX state 非 `IDLE` | 返回 `-EBUSY`，保留原消息 | 覆盖 payload |
| 等待 ACK 超时 | 返回 `-ETIMEDOUT`，保留诊断状态，由恢复机制处理 | 未确认对端状态即强制清零 |
| SBI IPI 发送失败 | state 仍为 `DATA_READY` 时回滚，否则保留对端状态 | 无条件写 `IDLE` |
| RX service ID 非法 | 丢弃本地副本、增加计数并完成 ACK | ISR 内打印或执行未知回调 |
| consumer queue 满 | 增加 drop 计数，保持中断路径有界 | 阻塞等待 queue |
| stale ACK | 仅在没有在途请求时回收为 `IDLE` | 与新请求并发重置 |
| 通知疑似丢失 | 根据共享 state 重新 kick | 把 IPI 到达次数当作消息计数 |
| UART2 IRQ34 fault | 按 FreeRTOS UART/异常路径排查 | 归因于 mailbox 前不核对故障源 |

## 16. 风险、兼容性与回退

### 16.1 风险

1. provider 重命名和 Kconfig 切换可能使旧 rootfs 中的模块名失效，需要同步模块安装和启动脚本。
2. router header 从 bit-field 改为 mask 时，如果任一端遗漏更新，会出现 service/command 解析错位。
3. 共享内存使用 `MEMREMAP_WB` 时，内存屏障和缓存属性必须在实板压力下验证。
4. 模块热重载若清零共享区，可能破坏对端在途消息，因此默认不承诺无协调热重载。
5. recovery 重发 IPI 必须保持消息幂等：它只能重新通知相同 state，不能再次写 payload 或重复推进业务。

### 16.2 兼容策略

- wire layout 和 service ID 保持不变；
- CRC 字段继续为 0，本期不单边启用；
- NOR bulk buffer 地址和 ABI version 保持不变；
- Linux/U-Boot proper 不同时运行，但使用相同的 channel 方向和 router 协议；
- RT-Thread 若复用协议，必须单独核对其 IPI 和调度中断处理，不能照搬 FreeRTOS SSIP 清除流程。

### 16.3 回退方式

回退以一组匹配的 Linux、OpenSBI、FreeRTOS、DTS 和模块产物为单位，不能只回退其中一个协议端。回退后重新核对配置、版本、时间戳和 SHA-256；若新旧 ABI 不一致，必须先停止业务并冷启动，禁止在活跃 channel 上混用两套实现。

## 17. 待确认事项

1. Linux router RX work 最终采用固定 mempool 还是每 consumer 预分配 ring，需要结合日志和 vshell 峰值确定深度。
2. 是否保留 `CONFIG_QUARD_IPI_MBOX` 作为迁移期兼容选项，或在生产 provider 收敛后直接删除。
3. 是否为共享 ABI 增加显式 version/magic；若增加，必须定义旧固件检测和拒绝策略。
4. recovery 周期是否继续使用 20 ms，需要在吞吐、功耗和故障恢复时间之间实测取值。
5. CRC16 是否有实际错误检测需求；启用前必须定义多项式、初值、字节序和覆盖范围。
