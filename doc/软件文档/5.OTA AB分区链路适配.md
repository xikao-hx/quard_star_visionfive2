# OTA A/B 分区升级

## 1. 功能概述

本次改动在 VisionFive 2 上实现了完整的 SD 卡 Linux A/B 启动链路。系统将 SPL、U-Boot、Linux rootfs 和 OTA 用户态工具串联起来，通过 SPI NOR `recovery` 分区中的 `current_bank`、`target_bank` 选择启动槽位，并在 SD 卡上加载与该槽位对应的 boot 和 rootfs 分区。

核心关系如下：

```text
OTA 写入非活动槽位
        |
        v
设置 recovery.target_bank
        |
        v
SPL 选择同槽位的 SPI fw_payload，并同步 current_bank
        |
        v
U-Boot proper 读取 current_bank
        |
        +-- A: SD p3(image.fit) + p4(rootfs)
        |
        `-- B: SD p5(image.fit) + p6(rootfs)
```

## 2. SD 卡分区约定

| 槽位 | boot 分区 | rootfs 分区 | Linux 根设备 |
| --- | --- | --- | --- |
| A | `PARTLABEL=boot_a`（兼容 p3） | `PARTLABEL=rootfs_a`（兼容 p4） | `root=PARTUUID=<rootfs_a-partuuid>` |
| B | `PARTLABEL=boot_b`（兼容 p5） | `PARTLABEL=rootfs_b`（兼容 p6） | `root=PARTUUID=<rootfs_b-partuuid>` |

非 A/B 的 p7 使用 `PARTLABEL=userdata`，格式为 ext4，开机挂载到
`/userdata`。当前整盘镜像为它预留固定 2 GiB，A/B 切换不会替换该分区。

boot 分区使用 FAT 文件系统，保存 `image.fit` 和 `vf2_uEnv.txt`；rootfs
分区使用 ext4 文件系统。新部署优先使用完整整盘镜像创建统一 PARTLABEL，
不通过 OTA 在线改写现有 SD 卡 GPT。

`PARTUUID` 是 GPT 分区项的唯一标识，由分区工具在创建分区时生成。U-Boot 根据当前选择的 rootfs 分区查询其 `PARTUUID`，再写入内核命令行，因此不依赖 Linux 设备名是否固定。

## 3. 改动内容分类

### 3.1 第一部分：SPL 支持 A/B 分区

参考提交：[`92260ab10c00c2f627c9ac673814561f31a3e15f`](https://github.com/xikao-hx/quard_star_visionfive2/commit/92260ab10c00c2f627c9ac673814561f31a3e15f)

#### 3.1.1 功能范围与 NOR 分区映射

SPL 是 A/B 启动决策的第一入口。FreeRTOS 尚未启动时，SPL 直接访问物理 QSPI，
根据 `recovery.target_bank` 选择 NOR 中的 `fw_payload_a` 或 `fw_payload_b`，再将
实际启动 bank 同步到 `recovery.current_bank`。

这里的“SPL 支持 A/B 分区”是指 SPL 选择两份 `fw_payload`，不是在 `spl_a` 与
`spl_b` 之间选择 SPL 自身镜像：

| bank | SPL 加载分区 | offset | size |
| --- | --- | ---: | ---: |
| A（`0`） | `fw_payload_a` | `0x00100000` | `0x00600000` |
| B（`1`） | `fw_payload_b` | `0x00700000` | `0x00600000` |

`recovery` 分区位于 `0x000C0000-0x000FFFFF`。SPL 只使用其中的
`target_bank` 和 `current_bank` 完成启动选择，其他 OTA 状态字段保持不变。

#### 3.1.2 GPT 和 recovery 校验

`u-boot/common/spl/quard_bootctrl.c` 在选择 payload 前执行以下校验：

- 校验 protective MBR、GPT signature、revision、header size 和 header CRC；
- 校验 128 项分区表 CRC，未使用的分区项必须为全零；
- 核对 `spl_a`、`spl_b`、`gpt`、`recovery`、`fw_payload_a`、
  `fw_payload_b` 六个分区的名称、顺序、GUID、offset、size 和 attributes；
- 确认 Flash 容量不小于公共布局定义的 16 MiB；
- 校验 recovery magic、结构版本、`current_bank`/`target_bank` 范围及 CRC32。

公共头文件 `common_inc/bsp/quard_recovery_config.h` 同时适配 U-Boot、Linux
内核和用户态类型，并使用 `_Static_assert` 固定关键字段 offset、CRC offset 和
200 字节结构大小，保证各阶段使用相同的 recovery ABI。

#### 3.1.3 选择、同步和回退

SPL 的执行顺序如下：

1. GPT 和 recovery 均有效时，以 `target_bank` 作为本次启动 bank；
2. `current_bank` 不一致时，对 recovery 所在 4 KiB 擦除块执行整块读、修改
   `current_bank` 和 CRC、擦除、整块回写及读回比较；
3. 从所选 `fw_payload_a` 或 `fw_payload_b` offset 继续原有 SPI load 流程；
4. GPT 无效时回退到固定布局的 `fw_payload_a@0x00100000`；GPT 有效但 recovery
   读取或校验失败时也回退 A bank；
5. `current_bank` 回写失败时继续加载已选择的 payload，但打印 warning。此时
   U-Boot proper 可能仍读到旧 bank，必须将该日志视为 A/B 链路异常。

B bank 选择路径的预期日志格式如下（对应源码打印内容）：

```text
SPL bootctrl: target=b current=a
SPL bootctrl: use slot b
SPL bootctrl: selected payload slot b @ 0x700000
```

出现 `GPT invalid` 或 `recovery metadata is invalid` 表示 SPL 已进入 A bank
回退路径，不能作为成功选择目标 bank 的证据。

#### 3.1.4 构建接入与关键文件

- `u-boot/common/spl/Kconfig`：新增 `SPL_QUARD_BOOTCTRL`，依赖
  `SPL_SPI_LOAD` 和 `SPL_SPI_FLASH_SUPPORT`；
- `u-boot/common/spl/Makefile`：仅在该选项启用时编译 `quard_bootctrl.o`；
- `u-boot/common/spl/quard_bootctrl.c`、`quard_bootctrl.h`：实现 GPT/recovery
  校验、payload 选择和 `current_bank` 同步；
- `u-boot/common/spl/spl_spi.c`：在加载下一阶段镜像前更新 `payload_offs`；
- `u-boot/configs/starfive_visionfive2_defconfig`：默认启用
  `CONFIG_SPL_QUARD_BOOTCTRL=y`。

### 3.2 第二部分：U-Boot proper 支持 A/B 分区

参考提交：[`4d5f4ad6851b24ff905f544f05c58200904d95c2`](https://github.com/xikao-hx/quard_star_visionfive2/commit/4d5f4ad6851b24ff905f544f05c58200904d95c2)

#### 3.2.1 功能范围与 SD 分区映射

U-Boot proper 不重新决定 NOR payload bank，而是通过 mailbox-backed NOR
MTD 读取 SPL 已同步的 `recovery.current_bank`，再把 bank 映射为 SD 卡上的
Linux boot/rootfs 分区：

| `current_bank` | `active_bank` | `active_system` | SD boot 分区 | SD rootfs 分区 |
| ---: | --- | ---: | ---: | ---: |
| `0` | `a` | `0` | `3` | `4` |
| `1` | `b` | `1` | `5` | `6` |

该逻辑只在 `bootmode=flash` 或 `bootmode=sd` 时启用。NVMe 和其他 MMC 设备
继续使用原有 p3/p4 映射，不继承 SD A/B 分区选择结果。

#### 3.2.2 U-Boot proper 选择流程

`board_late_init()` 调用 `quard_bootctrl_apply()`，执行以下步骤：

1. 根据 `sd_ab_env_version` 刷新由代码管理的默认启动脚本，避免旧的持久化
   environment 覆盖新版 A/B 逻辑；
2. 经 `quard-nor -> quard_nor_client -> mailbox router -> FreeRTOS NOR agent`
   读取名为 `recovery` 的 MTD 分区；
3. 校验 recovery magic、结构版本、bank 范围和 CRC32；
4. 根据 `current_bank` 导出 `active_bank`、`active_system`、`sd_bootpart` 和
   `sd_rootpart`，所有映射完成后才设置 `sd_ab_enabled=1`；
5. recovery 内容无效时回退 A bank；mailbox/MTD 访问失败时将 `bootdelay` 设为
   `-1`，停止自动启动并留在 U-Boot shell，不盲目选择任一 bank。

SPL 使用 `target_bank` 选择 NOR payload，然后同步 `current_bank`；U-Boot proper
只读取 `current_bank`。因此同一次启动的 NOR payload、SD boot 和 SD rootfs
应属于同一个 bank。

#### 3.2.3 Linux 自动启动与失败处理

SD A/B 路径从所选 boot 分区加载 `vf2_uEnv.txt` 和 `image.fit`。启动脚本通过
`part uuid` 获取所选 rootfs 的 PARTUUID，并生成：

```text
root=PARTUUID=${rootuuid} rw active_bank=${active_system}
```

PARTUUID 避免启动流程依赖可能变化的 `/dev/mmcblkXpN` 名称；
`active_bank=0/1` 将实际 bank 传递给 Linux 用户态。A/B 路径同时启用
`verify=yes`，检查环境导入、FIT 加载、`bootm start` 和 `bootm loados` 的结果。

如果所选 slot 缺少 `vf2_uEnv.txt`、环境导入失败或启动流程返回，脚本设置
`sd_ab_failed=1` 和 `bootmode=ab-failed`，并停止继续扫描。当前实现不会自动
跨 bank 回退，也不会转入 legacy/NVMe 启动，以免 FIT、rootfs 与 recovery
记录的 bank 不一致。

#### 3.2.4 构建接入与关键文件

- `u-boot/board/starfive/visionfive2/quard_bootctrl.c`、
  `quard_bootctrl.h`：读取 recovery、校验元数据并导出 SD A/B 环境变量；
- `u-boot/board/starfive/visionfive2/starfive_visionfive2.c`：在
  `board_late_init()` 中接入选择逻辑；
- `u-boot/board/starfive/visionfive2/Kconfig`、`Makefile`：新增并接入
  `QUARD_BOOTCTRL`，仅编译进 U-Boot proper；
- `u-boot/include/configs/starfive-visionfive2.h`：提供分区映射、启动脚本和
  失败停止逻辑；
- `conf/vf2_uEnv.txt`：根据 rootfs PARTUUID 生成 bootargs 并加载 `image.fit`；
- `u-boot/configs/starfive_visionfive2_defconfig`：默认启用
  `CONFIG_QUARD_BOOTCTRL=y`。该功能依赖 `QUARD_NOR_CLIENT`、`MTD`、
  `CMD_PART` 和 `CMD_FAT`。

#### 3.2.5 两阶段启动核对

以 B bank 为例，应同时取得 SPL 与 U-Boot proper 的关键日志：

```text
SPL bootctrl: target=b current=a
SPL bootctrl: use slot b
SD bootctrl: current=b target=b
SD bootctrl: slot b uses SD boot 5, rootfs 6
```

进入 Linux 后还应确认 `/proc/cmdline` 中的 rootfs PARTUUID 对应 SD p6，并包含
`active_bank=1`。不能只依据最终挂载设备判断整个 A/B 链路正确。

### 3.3 U-Boot 环境：加载 FIT 并生成 bootargs

主要改动文件：

- `conf/vf2_uEnv.txt`
- `conf/jh7110_uEnv.txt`
- `u-boot/include/configs/starfive-visionfive2.h`

主要内容：

- 自动启动入口保持为 `run sdk_boot_env; run distro_boot_env`；
- 从 `sd_bootpart` 指定的 p3 或 p5 加载 `image.fit`；
- 使用 `part uuid` 查询 `sd_rootpart` 对应分区的 `PARTUUID`；
- 动态生成 `root=PARTUUID=${rootuuid} rootwait rw`；
- 向 Linux 传递 `active_bank=${active_system}`；
- SD A/B 变量与 eMMC、NVMe 的默认分区变量隔离，避免影响其他启动介质。

正常自动启动需要清除历史固定的 `bootargs`：

```bash
setenv bootcmd 'run sdk_boot_env; run distro_boot_env'
setenv bootargs
saveenv
reset
```

简要说明：不能长期把 `root=/dev/mmcblk1p6` 写死在 `bootargs` 中。动态查询 `PARTUUID` 后，同一套脚本可以随 bank 自动选择 p4 或 p6。

### 3.4 initramfs：支持 PARTUUID 根文件系统

主要改动文件：

- `buildroot/system/skeleton/init`
- `buildroot/package/util-linux/Config.in`
- `buildroot/package/util-linux/util-linux.mk`
- `conf/buildroot_initramfs_config`
- `conf/buildroot_initramfs_config_debug`

主要内容：

- `/init` 使用 `blkid -t "PARTUUID=..." -o device` 将 PARTUUID 解析为真实块设备；
- 等待目标块设备出现后再挂载 `/rootfs`；
- 增加仅安装 `blkid` 所需能力的 Buildroot 配置，避免无目的地启用整套 util-linux；
- 切换根文件系统时避免重复移动 `/dev/shm`、`/dev/pts` 等 `/dev` 子挂载点。

简要说明：内核虽然接收了 `root=PARTUUID=...`，但本项目由 initramfs 的 `/init` 手工挂载最终 rootfs，因此 `/init` 也必须主动解析 PARTUUID。修复后已观察到 B 槽 PARTUUID 被解析为 `/dev/mmcblk1p6` 并成功挂载。

### 3.5 rootfs：网络、NFS 和 SSH 支持

主要改动文件：

- `conf/buildroot_rootfs_config`
- `conf/amp_rootfs_post_build.sh`
- `conf/busybox-nfs.config`

主要内容：

- 为 ext4 rootfs 配置网卡和 Dropbear SSH；
- 增加 NFS 客户端和启动挂载脚本；
- NFS 失败时在后台重试，不阻塞 SysV `rcS`，保证 getty 和 SSH 能继续启动；
- 默认配置板端 `eth0=192.168.5.9`，将 `192.168.5.11:/home/xikao/VisionFive2_6.6/nfs_rootfs` 挂载到板端 `/mnt`，具体地址可按现场网络修改。

简要说明：A/B 切换后两个 rootfs 都必须包含相同的基础网络能力，否则某个槽位可能可以挂载根文件系统，却无法进入 shell 或通过 SSH 维护。

### 3.6 OTA 元数据与镜像写入

主要改动目录和文件：

- `basic_middleware/ota_info/`
- `basic_middleware/ota_package/`
- `basic_middleware/ota_client/`
- `tools/script/build_ota_package.py`
- `tools/script/build.sh`

主要内容：

- `ota_info` 读写 recovery 中的 `current_bank`、`target_bank` 等元数据，并适配 MTD 设备几何信息；
- `ota_package` 校验 manifest、SHA-256、RSA 签名、版本和目标槽位，将 payload 写入非活动槽位；
- stage1 完成镜像写入和校验后才提交 `target_bank`，避免半包状态被选中启动；
- stage2 在新槽位启动后完成版本确认和升级收尾；
- `ota_client` 提供注册、检查、下载、解包、安装和状态管理入口，串联 `ota_info` 与 `ota_package`；
- 打包脚本根据当前 bank 生成写往另一槽位的 SPL、fw_payload、boot 和 rootfs payload。

简要说明：OTA 写入始终面向非活动槽位，最后一步才修改启动目标。这样升级中途断电时，原活动槽位仍保持可启动状态。

### 3.7 构建、产物发布与 SD 卡制作

主要改动文件：

- 顶层 `Makefile`
- `tools/image/build.sh`

主要内容：

- 为 initramfs 配置、`/init`、post-build 脚本和 util-linux 配置补充构建依赖；
- 统一发布 SPL、fw_payload、`image.fit` 和 rootfs 镜像；
- 保证打包和烧写使用同一次构建生成的配套产物；
- A/B 两个 boot 分区分别部署 `image.fit` 和 `vf2_uEnv.txt`，两个 rootfs 分区分别部署 ext4 rootfs。

建议在部署前记录并核对以下文件的 SHA-256：

```text
work/u-boot-amp-spl.bin.normal.out
work/visionfive2_fw_payload_amp.img
work/amp/image.fit
work/buildroot_rootfs/images/rootfs.ext4
```

简要说明：A/B 功能跨越多个启动阶段，单独替换 U-Boot、FIT 或 rootfs 都可能造成版本不匹配，因此必须以一组配套产物发布。

### 3.8 OTA 写入性能与进度显示

主要修改文件：

- `basic_middleware/ota_package/lib/bh_ota_package_writer.c`

原 boot/rootfs writer 每次以 64 KiB 分块写入，目标文件或块设备
同时使用 `O_SYNC`；boot FAT 还使用 `MS_SYNCHRONOUS` 挂载。这会使
每个分块都等待 SD 卡落盘，对数百 MiB rootfs 会产生大量小块
同步 I/O。

调整后的写入语义为：

1. boot FIT 使用普通 FAT 挂载和缓冲写入，不再使用
   `MS_SYNCHRONOUS` 和 `O_SYNC`。
2. rootfs 块设备使用缓冲写入，不再对每个 64 KiB 块执行
   `O_SYNC` 语义。
3. payload 和必要的尾部补零全部写完后，统一调用 `fsync()`
   等待数据落盘，boot FAT 不再执行第二次目录
   `fsync()`，后续正常卸载文件系统。
4. `fsync()` 成功后仍从头回读 payload 并逐字节比较，性能优化
   不降低已有写入完整性要求。
5. 分块写入和补零逻辑处理 short write，只有完整写入当前分块后
   才继续。

进度输出按 5% 限频，每条都是可保存的完整日志行，不依赖
终端的回车覆盖：

```text
[OTA_Package][PROGRESS] partition='rootfs_b' phase='write' [###############---------------]  50% (.../... bytes)
[OTA_Package][PROGRESS] partition='rootfs_b' phase='zero-fill' [######################--------]  75% (.../... bytes)
[OTA_Package][PROGRESS] partition='rootfs_b' phase='verify' [##############################] 100% (.../... bytes)
```

`write` 表示 payload 写入，`zero-fill` 表示 rootfs 恢复裁剪掉的零尾，
`verify` 表示落盘后的回读比较。进度输出受 `BH_OTA_LOG_LEVEL`
控制，`INFO` 和 `DEBUG` 模式显示，`WARN`/`ERROR` 模式隐藏。每次输出后
立即 `fflush(stdout)`，直接执行 `ota_package apply_stage1/apply_stage2`
时可以实时看到进度。

当前字节级进度覆盖 boot/rootfs 路径。`fw_payload` 和 `spl`
仍通过 `bh_hal_ota_flash_fsi_image()` 一次性调用 NOR HAL，HAL 尚未
提供擦除/写入进度回调，因此这两类 payload 目前只有开始、
完成及 stage payload 计数日志，没有伪造中间百分比。

当前修改已写入源码，尚未构建、未执行 host 测试，也未重新进行
板端性能对比。

## 4. 启动与升级流程

### 4.1 正常启动

1. SPL 读取 `target_bank`，选择相同 bank 的 SPI fw_payload，并同步 `current_bank`。
2. U-Boot proper 读取 `current_bank`，生成 A=`3/4` 或 B=`5/6` 的 SD 分区映射。
3. `vf2_uEnv.txt` 从对应 boot 分区加载 `image.fit`，查询对应 rootfs 的 PARTUUID。
4. 内核启动 initramfs，`/init` 将 PARTUUID 解析为 `/dev/mmcblk1p4` 或 `/dev/mmcblk1p6`。
5. initramfs 挂载 ext4 rootfs、执行 `switch_root`，随后启动网络、NFS、串口登录和 SSH。

### 4.2 OTA 升级

1. 读取当前活动槽位，确定另一个槽位为升级目标。
2. 校验升级包签名、manifest、版本及各 payload 哈希。
3. 写入目标槽位对应的 SPL、fw_payload、boot 和 rootfs 分区。
4. 回读或校验写入结果。
5. 最后设置 `target_bank` 并重启。
6. 新槽位启动成功后执行 stage2 确认；失败时保留原槽位数据用于恢复。

手工切换到 B 槽可使用：

```bash
ota_info write target_bank b
ota_info read target_bank
reboot
```

重启日志应同时满足：

```text
SPL bootctrl: use slot b
SD bootctrl: current=b target=b
SD bootctrl: slot b uses SD boot 5, rootfs 6
find PARTUUID=<p6-partuuid> as /dev/mmcblk1p6: 0
```

## 5. 修改总结

本次实现不是简单增加 p5、p6 两个分区，而是完成以下闭环：

- **槽位决策**：recovery 元数据决定目标 bank，SPL 负责选择并同步实际 bank；
- **分区映射**：U-Boot proper 将 bank 映射到 SD p3/p4 或 p5/p6；
- **可靠寻址**：U-Boot 动态生成 rootfs PARTUUID，initramfs 负责解析并挂载；
- **安全写入**：OTA 只写非活动槽位，完整校验后才提交 `target_bank`；
- **系统可维护性**：两个 rootfs 均提供网络、NFS、串口 shell 和 SSH；
- **产物一致性**：构建系统统一管理各启动阶段的依赖与发布文件。
