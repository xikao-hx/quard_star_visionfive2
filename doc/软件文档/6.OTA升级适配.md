# OTA 升级适配

## 1. 功能概述

本文总结 VisionFive 2 AMP 工程中为远程 OTA 升级闭环所做的软件适配。适配目标是在已有
A/B 启动链路基础上，将设备侧 OTA client、OTA 包执行工具、recovery 状态工具、rootfs
启动脚本、Linux mailbox/NOR 驱动和服务端静态发布能力整理到统一构建流程中。

整体关系如下：

```text
OTA server
  |
  | manifest / package / register / report
  v
ota_client
  |
  +-- register / check / download
  +-- unpack / install
  `-- service_start
        |
        +-- ota_info    读取和更新 recovery 状态
        +-- ota_package 校验、刷写和提交 OTA 包
        `-- rootfs 启动脚本在开机后自动恢复 stage2 / boot_success
```

本次适配不改变 SPL 和 U-Boot proper 的 A/B 启动职责。SPL/U-Boot 仍负责根据
recovery 元数据选择 bank；Linux rootfs 侧负责在系统启动后完成 OTA 状态恢复、健康检查、
上报和成功清理。

## 2. rootfs 安装内容

### 2.1 安装入口

rootfs 的 OTA 内容由 `conf/amp_rootfs_post_build.sh` 在 Buildroot post-build 阶段安装。
该脚本会把受控配置、启动脚本、用户态工具和运行库安装到目标 rootfs。

主要输入目录：

- `target_root_script/`：rootfs 内置脚本和默认配置；
- `basic_middleware/ota_info/`：recovery 状态读写工具；
- `basic_middleware/ota_package/`：OTA 包校验、刷写和提交工具；
- `basic_middleware/ota_client/`：远程 OTA client 编排入口；
- `target_root_script/etc/ota/keys/ota_public.pem`：rootfs 内置 OTA 公钥；
- `target_root_script/etc/ota/sys-version`：rootfs 版本来源。

主要安装结果：

| rootfs 路径 | 来源 | 作用 |
| --- | --- | --- |
| `/bin/ota_info` | `basic_middleware/ota_info` | 读取和更新 SPI NOR `recovery` 分区中的 OTA 状态 |
| `/bin/ota_package` | `basic_middleware/ota_package` | 校验 OTA 包签名、写入 inactive bank、提交 stage1/stage2/boot_success |
| `/bin/ota_client` | `basic_middleware/ota_client/ota_client.sh` | 设备侧 OTA 统一入口 |
| `/usr/libexec/ota-client/*` | `basic_middleware/ota_client/libexec/` | `register/check/download/unpack/install/service_start` 的内部实现 |
| `/lib/ota/*` | `basic_middleware/ota_client/lib/ota/` | 配置、日志、锁、状态、网络、API 和健康检查公共库 |
| `/etc/init.d/S94ota-prepare.sh` | `target_root_script/etc/init.d/S94ota-prepare.sh` | 开机准备 MTD by-name 链接和 active/inactive 链接 |
| `/etc/init.d/S95ota-stage2.sh` | `target_root_script/etc/init.d/S95ota-stage2.sh` | 开机自动执行 `ota-package service_start` |
| `/usr/sbin/create_link.sh` | `target_root_script/usr/sbin/create_link.sh` | 根据 `/proc/mtd` 创建 `/dev/mtd/by-name` 链接 |
| `/usr/sbin/ota-test.sh` | `target_root_script/usr/sbin/ota-test.sh` | 等待 `recovery` MTD 就绪并调用 `create_link.sh` |
| `/etc/ota/client.conf` | `target_root_script/etc/ota/client.conf` | OTA client 默认服务端、下载目录、公钥和 token 配置 |
| `/etc/ota/device_identity.conf` | `target_root_script/etc/ota/device_identity.conf` | EEPROM 身份缺失时的设备身份兜底配置 |
| `/etc/ota/keys/ota_public.pem` | `target_root_script/etc/ota/keys/ota_public.pem` | OTA 包签名验签公钥 |
| `/etc/version` | `target_root_script/etc/ota/sys-version` | 当前系统版本 |

### 2.2 rootfs 配置文件

默认客户端配置位于：

```text
target_root_script/etc/ota/client.conf
```

当前关键字段：

```ini
server_url=http://192.168.5.11:18080
manifest_url=http://192.168.5.11:18080/ota/manifests/quard-star.json
download_dir=/userdata/ota/download
log_path=/userdata/ota/log/ota_client.log
public_key_path=/etc/ota/keys/ota_public.pem
network_iface=eth0
health_check_dir=/etc/ota/health-check.d
api_token=ota-demo-token
```

`api_token` 必须与 `ota_server/config/ota_server.conf` 中的 `api_token` 一致。否则
FastAPI 的 `register`、`check` 和 `report` 接口会返回 `401 Unauthorized`。

默认设备身份配置位于：

```text
target_root_script/etc/ota/device_identity.conf
```

它仅作为 EEPROM 身份不可用时的兜底来源。量产场景不应在 rootfs 中预置多台设备共用的
唯一 `device_id`。

### 2.3 启动脚本顺序

rootfs 中新增两个 SysV 启动脚本：

```text
S94ota-prepare.sh -> S95ota-stage2.sh
```

`S94ota-prepare.sh` 执行流程：

1. 调用 `/usr/sbin/ota-test.sh`；
2. 等待 `/proc/mtd` 中出现 `"recovery"` 分区；
3. 调用 `/usr/sbin/create_link.sh`；
4. 创建 `/dev/mtd/by-name/<分区名>`；
5. 根据 `ota_info read current_bank` 创建 `spl_active`、`spl_inactive`、
   `fw_payload_active` 和 `fw_payload_inactive` 链接。

`S95ota-stage2.sh` 执行流程：

1. 检查 `/usr/libexec/ota-client/ota-package` 是否存在；
2. 从 `/etc/ota/client.conf` 读取 `server_url` 或 `manifest_url`；
3. 等待 `network_iface` 拿到 IPv4 地址，并确认 `ip route get <server>` 成功；
4. 输出 `Starting OTA recovery service`；
5. 执行 `ota-package service_start`；
6. 将返回码向 SysV init 传递。

`service_start` 是幂等恢复入口，会根据 recovery 中的 `ota_state` 决定是否继续
stage1、stage2、`boot_success` 或跳过。

### 2.4 `/userdata` 运行目录

`/userdata` 作为 OTA 运行期持久目录，rootfs 通过 `/etc/fstab` 挂载：

```text
PARTLABEL=userdata  /userdata  ext4  defaults,noatime  0  2
```

主要运行目录：

| 路径 | 作用 |
| --- | --- |
| `/userdata/ota/download` | 保存下载的 OTA 压缩包、`current_release.env` 和阶段指标 |
| `/userdata/ota/ota_package` | 保存解压后的 OTA 包和 `.ota_remote_release.env` |
| `/userdata/ota/log` | 保存 OTA client 持久日志 |

`basic_middleware/ota_client/lib/ota/state.sh` 中的默认解包目录已对齐为：

```sh
DEFAULT_PACKAGE_DIR=${OTA_CLIENT_PACKAGE_DIR:-/userdata/ota/ota_package}
```

升级成功并完成 `boot_success` 后，`ota-package service_start` 会清理：

```text
/userdata/ota/download
/userdata/ota/ota_package
/userdata/ota/package
```

这样可以避免多次升级后下载包和解压包长期占用 `/userdata` 空间。清理动作只在
`boot_success` 成功或状态已经为 `complete(17)` 时执行，不在 stage1/stage2 中途执行，
避免失败升级时丢失恢复和排查所需材料。其中 `/userdata/ota/package` 是旧默认解包目录，
保留在清理列表中用于清除历史版本残留。

## 3. OTA client 适配内容

### 3.1 命令入口和职责

公开入口：

```bash
ota_client <command>
```

命令按职责分发到三个内部进程：

| 命令 | 内部入口 | 作用 |
| --- | --- | --- |
| `identity`、`config`、`state` | `ota-device` | 查询身份、配置和本地发布状态 |
| `register`、`check`、`download` | `ota-remote` | 与 OTA server 交互和下载 OTA 包 |
| `unpack`、`install`、`service_start` | `ota-package` | 解包、本地刷写和开机恢复 |

`ota_client` 不直接实现刷写逻辑，实际刷写仍由 `ota_package` 执行；`ota_client`
负责远程请求、状态文件、互斥锁、日志、健康检查和阶段上报。

### 3.2 远程升级流程

手工触发完整升级的核心流程：

```bash
ota_client register
ota_client check
ota_client download
ota_client unpack
ota_client install
```

阶段含义：

1. `register`：向 server 登记设备身份；
2. `check`：读取 manifest 或调用服务端 API，判断是否存在可升级 release；
3. `download`：下载 `<release_id>.tar.gz`，并校验 SHA-256；
4. `unpack`：解压 OTA 包，校验 `data.json`、`manifest.hash`、`signature.sig` 和 payload 文件；
5. `install`：执行 `verify_stage1 -> apply_stage1 -> commit_stage1`，成功后重启；
6. 开机后 `S95ota-stage2.sh` 自动进入 `service_start`，继续 stage2 或 `boot_success`。

### 3.3 service_start 健康检查

`service_start` 在推进 stage2 或 `boot_success` 前会进行关键健康检查：

- `/userdata` 必须挂载到独立 `userdata` 分区；
- recovery 中的 current/target bank 必须与当前启动 bank 一致；
- Linux `/proc/cmdline` 中的 `active_bank` 必须与 recovery bank 一致；
- 当前根文件系统必须属于对应的 `rootfs_a` 或 `rootfs_b`；
- 当前 `/etc/version` 必须与发布状态和 OTA 包中的目标版本一致；
- `health_check_dir` 下的可执行健康检查脚本必须全部返回成功。

根分区识别以实际根设备的 `PARTLABEL` 为主，并可结合 PARTUUID、bank 和设备分区号做一致性判断。
如果 PARTLABEL 缺失或错误，应优先修复 GPT 分区标签，而不是长期依赖手工创建链接绕过。

## 4. Linux 驱动编译进入内容

### 4.1 IPI mailbox 和 router

Linux 内核侧新增 Quard IPI mailbox 控制器和 mailbox router：

| 文件 | 作用 |
| --- | --- |
| `linux/drivers/mailbox/quard_ipi_mailbox.c` | Linux 到 FreeRTOS 的 AMP IPI mailbox 控制器 |
| `linux/drivers/mailbox/quard_mbox_router.c` | Quard 服务消息路由层 |
| `linux/include/linux/quard_mbox_router.h` | router 对内核客户端暴露的接口 |

Kconfig/Makefile 接入：

```text
CONFIG_QUARD_IPI_MBOX
CONFIG_QUARD_MBOX_ROUTER
```

```make
obj-$(CONFIG_QUARD_IPI_MBOX) += quard_ipi_mailbox.o
obj-$(CONFIG_QUARD_MBOX_ROUTER) += quard_mbox_router.o
```

`QUARD_MBOX_ROUTER` 依赖 `QUARD_IPI_MBOX`。该链路对应的运行方向是：

```text
Linux NOR client -> Linux router -> Linux IPI controller
                                      |
                               共享内存 + SBI IPI
                                      |
FreeRTOS NOR agent <- FreeRTOS router <- FreeRTOS IPI controller
```

### 4.2 mailbox-backed NOR client

Linux MTD 侧新增 mailbox-backed NOR client：

| 文件 | 作用 |
| --- | --- |
| `linux/drivers/mtd/devices/quard_nor_client.c` | 通过 Quard mailbox router 访问 FreeRTOS 暴露的 NOR 服务 |

Kconfig/Makefile 接入：

```text
CONFIG_MTD_QUARD_NOR_CLIENT
```

```make
obj-$(CONFIG_MTD_QUARD_NOR_CLIENT) += quard_nor_client.o
```

该驱动注册后，Linux 可看到 NOR 分区，并由 rootfs 脚本基于 `/proc/mtd` 创建
`/dev/mtd/by-name` 链接。OTA 的 `ota_info` 依赖这些 MTD 设备访问 `recovery` 分区。

高频读写路径中的 NOR 调试日志已经下调为 debug 级别，避免启动或 OTA 执行过程中持续打印
`from ... len ...`、`rx msg comes`、`Rx checksum pass` 等重复日志。

### 4.3 defconfig 适配

以下 defconfig 已启用 Quard IPI/router/NOR 链路：

```text
linux/arch/riscv/configs/starfive_jh7110_defconfig
linux/arch/riscv/configs/starfive_visionfive2_defconfig
```

关键配置：

```text
CONFIG_QUARD_IPI_MBOX=y
CONFIG_QUARD_MBOX_ROUTER=y
CONFIG_MTD_QUARD_NOR_CLIENT=y
```

同时禁用旧的或测试用途的链路：

```text
# CONFIG_STARFIVE_IPI_MBOX is not set
# CONFIG_STARFIVE_IPI_MBOX_TEST is not set
# CONFIG_STARFIVE_MBOX is not set
# CONFIG_STARFIVE_MBOX_TEST is not set
# CONFIG_RPMSG_STARFIVE is not set
```

这样 rootfs 不再需要通过 `insmod starfive_ipi_mailbox.ko`、
`insmod quard_mbox_router.ko`、`insmod quard_nor_client.ko` 手工加载这三类核心驱动。
外部安装脚本只保留仍需单独加载的辅助模块，例如 remote console 和 log 设备。

### 5.2 快速刷写验证

通过 NFS 挂载目录直接刷写 inactive bank 时，应先确认当前根分区，避免写正在运行的
rootfs：

```bash
awk '$2=="/"{print $1}' /proc/mounts
```

如果当前运行在 A bank（通常是 `/dev/mmcblk1p4`），可以刷写 B：

```bash
dd if=/mnt/starfive-visionfive2-vfat.part of=/dev/disk/by-partlabel/boot_b bs=1M conv=fsync
sync
dd if=/mnt/rootfs.ext4 of=/dev/disk/by-partlabel/rootfs_b bs=4M conv=fsync
sync
```

如果当前运行在 B bank（通常是 `/dev/mmcblk1p6`），应刷写 A：

```bash
dd if=/mnt/starfive-visionfive2-vfat.part of=/dev/disk/by-partlabel/boot_a bs=1M conv=fsync
sync
dd if=/mnt/rootfs.ext4 of=/dev/disk/by-partlabel/rootfs_a bs=4M conv=fsync
sync
```

禁止向当前正在挂载为 `/` 的 rootfs 分区执行 `dd`，否则 ext4 可能出现脏元数据或目录损坏。

## 6. OTA server 适配内容

`ota_server/` 提供远程 OTA 最小闭环服务，职责包括：

- 设备注册：`POST /api/v1/devices/register`；
- 升级检查：`POST /api/v1/ota/check`；
- 阶段上报：`POST /api/v1/ota/report`；
- 发布记录和设备记录持久化；
- Nginx 静态 manifest 和 OTA 包发布。

服务端默认配置：

```text
ota_server/config/ota_server.conf
```

关键字段：

```ini
api_token=ota-demo-token
public_base_url=...
package_root=...
```

FastAPI 接口通过 `X-OTA-Token` 做最小鉴权。设备侧 `/etc/ota/client.conf` 的
`api_token` 必须与服务端一致。

静态发布流程由以下脚本完成：

```bash
bash ota_server/scripts/publish_static_release.sh \
  --source-dir <ota_package_dir> \
  --release-id <release_id> \
  --board-type quard-star \
  --public-base-url http://<server-ip>:18080

sudo bash ota_server/scripts/deploy_nginx_http.sh --listen 18080 --server-name _
sudo systemctl reload nginx
./ota_server/scripts/run_server.sh
```

静态发布结果：

```text
<ota-root>/
  manifests/
    quard-star.json
  packages/
    <release_id>/
      <release_id>.tar.gz
      release.json
```

设备侧 `ota_client check/download` 优先使用 `manifest_url`；如果 manifest 流程不可用，
且配置了 `server_url`，再回落到 FastAPI `/api/v1/ota/check`。

## 7. 验证方法和成功判据

### 7.1 rootfs 内容检查

板端检查：

```bash
ls /etc/init.d/S94ota-prepare.sh /etc/init.d/S95ota-stage2.sh
ls /usr/sbin/create_link.sh /usr/sbin/ota-test.sh
ls /bin/ota_client /bin/ota_info /bin/ota_package
ls /usr/libexec/ota-client/ /lib/ota/
grep -E 'server_url|manifest_url|api_token' /etc/ota/client.conf
cat /etc/ota/device_identity.conf
cat /etc/version
```

预期结果：

- `api_token` 与服务端一致；
- `/etc/version` 与构建时 `target_root_script/etc/ota/sys-version` 一致；
- `/etc/init.d/S94ota-prepare.sh` 早于 `S95ota-stage2.sh` 执行。

### 7.2 Linux 驱动检查

板端检查：

```bash
grep -E 'QUARD_IPI_MBOX|QUARD_MBOX_ROUTER|MTD_QUARD_NOR_CLIENT' /proc/config.gz 2>/dev/null
cat /proc/mtd
ls -l /dev/mtd/by-name
dmesg | grep -E 'quard|mailbox|nor-client'
```

预期结果：

- Quard IPI mailbox、router 和 NOR client 已随内核启用；
- `/proc/mtd` 中存在 `spl_a`、`spl_b`、`gpt`、`recovery`、
  `fw_payload_a`、`fw_payload_b`；
- `/dev/mtd/by-name/recovery` 可用；
- 高频 NOR 读写不再持续输出 info 级调试日志。

### 7.3 OTA 流程检查

手工检查命令：

```bash
ota_client identity
ota_client register
ota_client check
ota_client download
ota_client unpack
ota_client install
```

升级后自动启动阶段预期日志：

```text

Current active bank: <a|b>
MTD links created in /dev/mtd/by-name
Partition symlinks updated successfully...
Starting OTA recovery service
[OTA_Client][INFO] ===== stage=service_start started =====
...

[OTA_Client][INFO] stage=service_start event=success
```

```bash

```

```text
download

```

## 8. 注意事项和已知限制

- `api_token` 是服务端鉴权配置，不会从设备自动读取；rootfs 默认配置或产线初始化脚本必须写入正确值。
- `Starting network: OK` 不代表路由和服务器已经可达。`S95ota-stage2.sh` 已增加
  有界网络等待，减少开机早期上报出现 `No route to host` 的概率。
- `401 Unauthorized` 表示网络已到达服务端但 token 不匹配，不是 OTA 刷写失败。
- `S95ota-stage2.sh` 只负责调用 `service_start`，实际阶段判断由 `ota-package` 完成。
- 使用 `dd` 快速刷写时只能写 inactive bank。
- 仅重新打包 FIT 或 VFAT 不一定代表 Linux `Image` 已重新链接；涉及内核驱动修改时必须确认
  板端 `dmesg | grep 'Linux version'` 与本次构建一致。
- 本文记录的是当前源码适配结果；本次文档更新未执行完整 SDK 构建和板端 OTA 验证。
