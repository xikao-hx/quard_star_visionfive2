# 启动流程

**启动模式设置：**

| index | 启动模式 | RGPIO_1 | RGPIO_0 |
| :--- | :--- | :--- | :--- |
| 1 | 1-bit QSPI Nor Flash | `0` (L) | `0` (L) |
| 2 | SDIO3.0 | `0` (L) | `1` (H) |
| 3 | eMMC | `1` (H) | `0` (L) |
| 4 | UART | `1` (H) | `1` (H) |

QSPI Flash（在SPL + OpenSBI + U-Boot层）+ SD Card/eMMC/NVMe（在Kernel + File System层和后续层）

![启动流程](img/启动流程.png)

**SPL 不是在 SPI NOR 中原地运行，而是：**

SPI NOR @ 0x000000
  → BootROM 读取 spl_a
  → 搬运到片内 SRAM @ 0x08000000
  → 跳转到 0x08000000 执行 SPL

**一般启动流程：** `上电流程：BootROM --> SPL + OpenSBI() + U-Boot --> Kernel + File System > Boot Complete`

![一般启动流程](img/启动流程.png)

**AMP 启动流程：** `上电流程：BootROM --> SPL（从 SPI NOR）--> 加载 fw_payload 到 0x40000000 --> OpenSBI 做域隔离、把 hart1 释放给 RT-Thread --> U-Boot 跑在其余核 --> 从 TF/TFTP 加载 image.fit --> AMP Linux 与 RT-Thread 通过共享内存 + mailbox 通信`

**内存地址范围：**

| RT-Thread 端 | 范围 | 内存大小 | 是否 Linux kernel 回收 |
| :--- | :--- | :--- | :--- |
| OpenSBI | `0x40000000` - `0x401fffff` | 2M | 一直保留 |
| U-Boot (S Mode) | `0x40200000` - `0x4032ffff` | 1.19M | 启动后 Linux kernel 会被回收 |
| RT-Thread | `0x6e800000` - `0x6effffff` | 8M | U-Boot-SPL 第一次把 RT-Thread 加载到内存中，起始地址为 `0x40330000`，然后迁移到 `0x6e800000` 地址，`0x40330000` 的地址会被回收 |


| Linux 端 | 范围 | 内存大小 |
| :--- | :--- | :--- |
| 共享内存 | `0x6e400000` - `0x6e7fffff` | 4M |
| RT-Thread 代码，栈空间 | `0x6e800000` - `0x6effffff` | 8M |
| RT-Thread 堆空间 | `0x6f000000` - `0x6fffffff` | 16M |

# 中断使能

## 问题

在 `trusted_domain` 的 PLIC 初始化代码中，只能看到具体中断源和
`sie.SEIE` 的使能，没有显式调用下面的全局中断使能函数：

```c
intr_on(); /* 设置 sstatus.SIE */
```

这并不表示当前 FreeRTOS 中断不需要 `sstatus.SIE`。实际上，
`sstatus.SIE` 由 FreeRTOS 的 RISC-V port 在调度器启动第一个任务时统一打开，
因此 PLIC 初始化代码不需要重复设置它。

## S 模式中断的多级使能条件

以 PLIC 外部中断为例，一个中断最终进入 S 模式，需要相关条件同时满足：

1. 中断已被上级固件委托给 S 模式。
2. PLIC 中对应中断源的 priority 非零。
3. 当前 hart 的 PLIC source enable 位已置位。
4. 中断源优先级高于当前 hart 的 PLIC threshold。
5. `sie.SEIE` 已置位，允许 S 模式外部中断。
6. 当前在 S 模式运行时，`sstatus.SIE` 已置位，允许 S 模式全局中断。

其中，`sie` 控制某一类中断是否允许进入，`sstatus.SIE` 是 S 模式的全局开关：

```text
PLIC source enable ─┐
PLIC priority       ├── sie.SEIE ── sstatus.SIE ──> S-mode trap handler
PLIC threshold      ┘
```

Timer 和 Software 中断不经过 PLIC，但同样分别需要 `sie.STIE`、
`sie.SSIE` 以及全局的 `sstatus.SIE`。

## 当前代码的实际启动顺序

### 1. 启动阶段关闭各类 S 模式中断

`startup.S` 启动时清空 `sie` 和 `sip`：

```asm
csrw sie, 0
csrw sip, 0
```

位置：`trusted_domain/startup.S`。

此时即使设备产生中断，也不会通过相应的 S 模式中断类型使能位进入处理器。

### 2. PLIC 初始化外部中断路径

`plicinithart()` 完成以下操作：

- 使能 UART2 和 Mailbox 等 PLIC source；
- 将当前 hart 的 PLIC threshold 设置为 0；
- 设置 `sie.SEIE`。

相关代码：

```c
*(uint32_t *)(PLIC_SENABLE(hart) + (UART2_IRQ / 32) * 4) |=
    (1U << (UART2_IRQ % 32));

*(uint32_t *)PLIC_SPRIORITY(hart) = 0;

w_sie(r_sie() | SIE_SEIE);
```

位置：`trusted_domain/driver/plic/plic.c`。

这里只打开外部中断的局部路径，没有打开 `sstatus.SIE` 全局开关。

### 3. FreeRTOS 调度器使能 Timer 和 Software 中断

`xPortStartScheduler()` 配置 tick timer 后，设置：

```c
csr_set(CSR_SIE, SIP_STIP);
csr_set(CSR_SIE, SIP_SSIP);
```

位置：`trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/port.c`。

这一步使能 `sie.STIE` 和 `sie.SSIE`，但注释也明确说明，此时还不会立即响应
S 模式中断，全局开关将在 `xPortStartFirstTask()` 中打开。

### 4. 启动第一个任务时设置 `sstatus.SIE`

`xPortStartFirstTask()` 首先将 `stvec` 设置为 FreeRTOS trap handler，恢复第一个
任务的上下文，然后设置 `sstatus.SIE`：

```asm
la    t0, freertos_risc_v_trap_handler
csrw  stvec, t0

/* 恢复任务上下文 */

load_x x5, 29 * portWORD_SIZE(sp)
ori    x5, x5, 0x2
csrrw  x0, sstatus, x5
```

位置：`trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/portASM.S`。

`0x2` 就是 `SSTATUS_SIE`。执行 `csrrw` 后，全局中断正式打开。

因此整体时序为：

```text
startup.S
  sie = 0
     |
     v
plicinithart()
  PLIC source enable
  PLIC threshold = 0
  sie.SEIE = 1
     |
     v
xPortStartScheduler()
  sie.STIE = 1
  sie.SSIE = 1
     |
     v
xPortStartFirstTask()
  stvec = freertos_risc_v_trap_handler
  恢复首个任务上下文
  sstatus.SIE = 1
     |
     v
开始响应 S 模式中断
```

## 中断进入和返回时如何维护 `SIE`

中断进入 S 模式 trap 时，RISC-V 硬件自动完成：

```text
sstatus.SPIE <- sstatus.SIE
sstatus.SIE  <- 0
```

这样默认不会在处理当前中断时继续接受新的 S 模式中断。

FreeRTOS trap handler 保存任务上下文，其中包含 `sstatus`。恢复上下文后通过
`sret` 返回：

```asm
load_x t0, 29 * portWORD_SIZE(sp)
csrw   sstatus, t0

/* 恢复其余寄存器 */

sret
```

执行 `sret` 时，硬件将先前保存在 `SPIE` 中的状态恢复到 `SIE`，所以任务恢复
执行后，中断也会恢复为进入 trap 之前的使能状态。

新任务的初始上下文也会设置 `SPIE` 和 `SPP`：

```asm
addi t1, x0, 0x120  /* SPIE | SPP */
or   t0, t0, t1
```

这保证通过异常返回路径切换到新任务时，中断状态能够正确建立。

## FreeRTOS 临界区对 `SIE` 的使用

当前 port 直接通过 `sstatus.SIE` 实现全局关中断和开中断：

```c
#define portDISABLE_INTERRUPTS() __asm volatile("csrc sstatus, 2")
#define portENABLE_INTERRUPTS()  __asm volatile("csrs sstatus, 2")
```

位置：`trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/portmacro.h`。

因此 `sstatus.SIE` 不仅在调度器启动时使用，也是 FreeRTOS 临界区机制的一部分。

## 为什么不在 `plicinithart()` 中提前设置

`plicinithart()` 只负责建立 PLIC 和 `sie.SEIE` 层面的外部中断路径。全局中断
开关由 FreeRTOS port 管理，可以保证打开全局中断之前已经完成：

- FreeRTOS trap handler 的安装；
- 第一个任务上下文的恢复；
- ISR 栈和调度器状态的准备。

如果在 `plicinithart()` 中提前设置 `sstatus.SIE`，设备已经存在 pending 中断时，
CPU 可能在 `stvec` 尚未切换到 FreeRTOS trap handler、调度器尚未准备完成之前
进入中断，从而产生启动时序问题。

## 结论

当前实现仍然需要 `SSTATUS_SIE`，只是无需在每个设备或 PLIC 初始化函数中单独
使能。其职责划分如下：

- 设备驱动/PLIC：配置中断源、优先级、threshold 和 source enable；
- PLIC hart 初始化：设置 `sie.SEIE`；
- FreeRTOS scheduler：设置 `sie.STIE`、`sie.SSIE`；
- FreeRTOS port：在首个任务启动时设置 `sstatus.SIE`，并在临界区和上下文切换中
  维护该状态。

所以，“当前 FreeRTOS 中断不需要使能 `SSTATUS_SIE`”这一说法并不准确；更准确的
描述是：**`SSTATUS_SIE` 已由 FreeRTOS port 在正确的启动阶段统一使能。**


# 镜像说明

## AMP 模式下打包为三个镜像

| 位置 | 刷什么 | 作用 |
| :--- | :--- | :--- |
| SPI NOR `0x0` | `u-boot-spl.bin.normal.out` | SPL |
| SPI NOR `0x100000` | `visionfive2_fw_payload_amp.img` | AMP 核心：OpenSBI + U-Boot + RT-Thread |
| TF 卡分区1 / TFTP | `image.fit` | AMP Linux（内核 + dtb + initramfs） |

**U-Boot：** 起来后执行类似 bootm <addr> 加载 image.fit，它会按 ITS 里 config-1 的编排把内核、dtb、initramfs 分别载到上表地址，然后跳进内核启动 Linux。所以：

**image.fit：** 是一个 U-Boot FIT（Flattened Image Tree）格式的启动镜像——由 mkimage 按 conf/visionfive2-fit-image.its 的编排把 3 样东西打包在一起：

| 组件 | 内容 | 加载地址 |
| :--- | :--- | :--- |
| vmlinux | `work/linux/arch/riscv/boot/Image`（AMP 内核，`CONFIG_RISCV_AMP=y`） | `0x40200000` |
| fdt | `jh7110-visionfive-v2.dtb`（VisionFive2 设备树） | `0x46000000` |
| ramdisk | `work/initramfs.cpio.gz`（buildroot 编的 initramfs 根文件系统） | `0x46100000` |

**visionfive2_fw_payload_amp 打包内容：**
```text
RT-Thread (scons) ──► work/rtthread.bin
    │  [Makefile:338-341] 拼进 U-Boot 尾部偏移 2MB
    ▼
U-Boot + RT-Thread ──► work/u-boot-rtthread.bin
    │  [Makefile:59] opensbi 以 FW_PAYLOAD_PATH 打包
    ▼
OpenSBI + U-Boot + RT-Thread ──► work/opensbi/.../fw_payload.bin (FW_TEXT_START=0x40000000)
    │  [Makefile:357] mkimage 包装成 FIT
    ▼
SPL 的 FIT 镜像 ──► work/visionfive2_fw_payload_amp.img  ← 刷进 SPI NOR 0x100000
```
