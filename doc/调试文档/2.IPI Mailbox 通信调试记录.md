## 根因

**测试驱动 `file->private_data` 使用错误：**

第一次执行：

```sh
echo 0x1234 > /dev/starfive_ipi_mailbox
```

在 `mbox_send_message()` 入口崩溃，传入的 channel 指针类似：

```text
dead4ead00000000
```

原因是 miscdevice 的 `open()` 后，`file->private_data` 默认指向 `struct miscdevice`，测试驱动却直接把它当成自己的设备结构使用。

修复方式：

```c
struct miscdevice *misc = file->private_data;
file->private_data = container_of(misc, struct starfive_ipi_test, misc);
```

## 解决

测试设备 `open()` 没有将 `file->private_data` 从 `miscdevice` 转换为测试结构体，`write()` 使用了错误指针。

修复：

```c
struct miscdevice *misc = file->private_data;
file->private_data = container_of(misc, struct starfive_ipi_test, misc);
```

## 根因分析

**32/64 位消息宽度错误：**

第二类崩溃发生在 `ipi_mb_send_data()`，典型日志：

```text
value=0x3231783000011234
queue=27594025598976
slot=0000c89e0f002400
badaddr=ffffff9e0f002400
```

测试模块发送的是 32 位变量，provider 却按 `unsigned long *` 在 RV64 上读取 64 位，越过变量边界，把相邻栈内容一起当成消息，最终计算出非法共享内存地址。

这也解释了为什么 RT-Thread 版本此前可以工作：RT-Thread 端消息布局和读取宽度匹配，而当时 Linux 测试驱动与 provider 的 ABI 不匹配。

早期直测通过统一消息宽度和增加 idx/queue 范围检查解决；最终 router 协议则统一固定复制 28 字节结构，不再解析不可靠的指针宽度。

**物理地址与映射后虚拟地址混用：**

错误实现曾在已经映射的 `tx_mbase` 上又拼接物理地址偏移，或者把地址值截断后再扩展，导致：

```text
正常映射：ffffffd82e402400
错误 slot：0000c89e0f002400
访问地址：ffffff9e0f002400
```

最终实现只对 `devm_memremap()` 返回的映射基址做小范围字节偏移：

```c
channel = mbase + idx * IPI_MB_CHAN_STRIDE;
```

## 解决

日志曾出现：

```text
value=0x3231783000011234
queue=27594025598976
```

测试模块传递 `u32`，provider 却按 `unsigned long *` 读取。在 64 位 RISC-V 上发生栈越界读取，后续非法 queue 访问共享内存外地址。

修复：测试模块发送 `unsigned long`，provider 增加 queue 范围检查。RT-Thread 可用是因为其消息宽度和 provider 读取方式匹配。

# 问题三：Remote shell 接入问题

## 初始化顺序

FreeRTOS 必须先初始化 mailbox router，再注册 shell consumer：

```c
init_quard_mbox_router();
userShellInit();
```

`userShellInit()` 中必须先创建 `shell_rx_queue`，再调用 `remote_shell_agent()` 注册 consumer，最后创建 shell task。否则 Linux 发来的第一个字符可能在 queue 尚未建立时进入回调。

## minicom 按回车无反应

Linux 虚拟 UART 最初的 `get_mctrl()` 返回 0，而 minicom 2.8 默认可能启用 RTS/CTS 和 carrier 检测。Linux serial core 看不到 CTS 后会设置 `hw_stopped`，用户按键不会进入 `start_tx()`。

修复包括两层：

1. 虚拟 UART 始终上报已连接：

```c
return TIOCM_CTS | TIOCM_DSR | TIOCM_CAR;
```

2. `minicom-start.sh` 明确关闭流控和 DCD：

```text
pu hasdcd No
pu rtscts No
pu xonxoff No
```

minicom 状态栏显示 `OFFLINE` 不一定代表 mailbox 不通；关键是按键是否进入 Linux TX worker，以及 FreeRTOS 是否收到 VSHELL 数据。

## UART 环形缓冲区只发送一段

旧 TX worker 只处理一次 `CIRC_CNT_TO_END()`，没有继续处理环形缓冲区绕回后的第二段，并且忽略 mailbox 发送错误，可能丢失连续字符和回车。

修复后 TX worker：

- 循环排空 UART circular buffer；
- 只按成功发送的字节数推进 tail；
- mailbox 发送失败时保留尚未发送的数据；
- 输出 `remote shell mailbox TX failed` 供诊断。

## FreeRTOS SSIP 重复调度问题

### 现象

关闭 minicom 流控问题后，Linux 输入已经到达 FreeRTOS router：

```text
Consumer 0x6e828358, cb 0x6e803e0c
Unhandled Exception 1: Instruction Access Fault
```

通过当前构建产物反汇编确认：

```text
0x6e803e0c = shell_agent_recv_cb
```

所以 callback 地址本身合法，不是野指针。

### 根因

`router_rx_notify()` 的确运行在中断上下文。普通 PLIC ISR 在唤醒高优先级任务后通常应该调用：

```c
portYIELD_FROM_ISR(high_pri_task_ready);
```

但 mailbox 使用的是 SSIP。当前 RISC-V 汇编路径已经固定执行：

```asm
jal vPortClearIpiInterrupt
jal vTaskSwitchContext
```

同时当前 port 的 `portYIELD_FROM_ISR()` 不是简单设置 pending 标志，而是直接调用：

```c
if (xSwitchRequired)
    vTaskSwitchContext();
```

因此原流程在一次 mailbox IPI 中可能执行两次调度：

```text
router_rx_notify()
  -> portYIELD_FROM_ISR()
      -> vTaskSwitchContext()       第一次

SSIP 汇编返回路径
  -> vTaskSwitchContext()           第二次
```

### 解决

`router_rx_notify()` 当前只执行 `xQueueSendToBackFromISR()`，不再手工调用 `portYIELD_FROM_ISR()`：

```text
SSIP
  -> mailbox handler
      -> router 消息入队并唤醒 consumer
      -> 写 ACK
  -> SSIP trap 尾部统一执行一次 vTaskSwitchContext()
  -> consumer task 运行
```

同时 consumer task 增加了 queue 接收结果和 callback 非空检查。

该修改已写入源码，但按照调试要求尚未重新编译和上板验证。下一次 FreeRTOS 构建应执行：

```sh
make ampuboot_fit -j$(nproc)
```

然后只更新：

```text
work/visionfive2_fw_payload_amp.img
```

# 调试原则总结

1. mailbox provider 只管理固定大小 channel、共享内存、IPI 和 ACK，不解析字符串业务。
2. `idx` 选择物理 channel，方向由上层 client 配置，不能把 idx 当作 payload 内 queue。
3. 双向通信使用两个独立 channel，不能让 TX/RX 争用同一 idx。
4. IPI type 是编号，接收端 `msg_type` 是 bitmask，两者不能混淆。
5. ISR 中只做最少工作，业务回调通过 queue/workqueue 转移到任务上下文。
6. 是否调用 `portYIELD_FROM_ISR()` 必须结合具体 port 的 trap 汇编，不能只套用通用模板。
7. 直测模块只验证底层，不应与正式 router/consumer 同时加载。
8. 更新产物前先确认改动属于 FreeRTOS payload、Linux KO，还是 FIT 内的 kernel/DT/initramfs。
9. 判断是否使用新产物，应核对版本、时间戳、BuildID/hash 和运行日志，不能只看复制命令成功。
