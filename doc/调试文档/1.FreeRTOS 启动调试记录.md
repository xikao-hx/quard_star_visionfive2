# VisionFive2 FreeRTOS AMP 启动问题总结

# 问题1：启动失败，UART没有输出

OpenSBI 可以打印完整启动信息，且显示 RT-domain 已分配给 HART4：

```text
Domain2 Name              : rt-domain
Domain2 Boot HART         : 4
Domain2 HARTs             : 4*
Domain2 Next Address      : 0x000000006e800000
Domain2 Next Mode         : S-mode
```

但是 OpenSBI 之后没有 FreeRTOS 输出。此时不能仅凭 OpenSBI 启动成功判断 FreeRTOS 已经正常运行，因为 OpenSBI 只是完成了域配置和跳转准备。


## 根因分析

### Hart 判断错误

检查启动流程

### FreeRTOS 链接脚本段布局错误

原链接脚本同时将 ROM 和 RAM 设置为 `0x6e800000`，但 `.data` 使用了独立的 RAM 起始地址，导致：

```text
.text  从 0x6e800000 开始
.data  也从 0x6e800000 开始
```

启动代码执行 `.data` 拷贝时覆盖 `.text`，最终导致启动流程中断。

### UART时钟配置错误

随后对比 RT-Thread 的 JH7110 UART 初始化代码，确认以下差异：

1. JH7110 UART2 的时钟和复位需要由 `0x13020000` 的系统时钟寄存器显式配置；
2. JH7110 UART 寄存器使用 32 位访问，寄存器偏移是 `reg << 2`，不能沿用普通 QEMU 16550 的 8 位连续访问方式；
3. UART2 的波特率时钟为 24 MHz，115200 波特率对应的分频值为 13；
4. 原有 IER 位定义与实际使用不一致，需要按 NS16550 约定修正 RX/TX 使能位；
5. 在启动早期，FreeRTOS 任务、队列、PLIC 和中断还没有初始化，不能依赖任务发送函数验证 UART。

### 镜像打包地址和opensbi跳转地址不对应

最终启动链路为：

```text
SPI
  -> SPL
  -> OpenSBI fw_payload
  -> 嵌入的 AMP U-Boot
  -> 嵌入的 FreeRTOS
```

由于 `fw_payload.bin` 在 U-Boot 前增加了 `0x200000`，RTOS 在最终 payload 中不能继续使用原始 U-Boot 镜像中的 `0x330000` 偏移，而应使用 `0x530000`。

NOR Flash 中的布局为：

| NOR 地址 | 内容 | 来源 |
| --- | --- | --- |
| `0x000000` | AMP SPL | `u-boot-amp-spl.bin.normal.out` |
| `0x000000 + 0x26858` 之后 | 空闲区域 | 预留至 `0x100000` |
| `0x100000` | AMP FIT 固件包 | `visionfive2_fw_payload_amp.img` |
| `0x100000 + 0x545005` | payload 结束 | 当前镜像结束 |

## 问题定位过程

**先确认 OpenSBI 的跳转地址和 AMP 内存区域：**

根据 OpenSBI 输出确认：

```text
rt-domain Boot HART = 4
rt-domain Next Address = 0x6e800000
```

因此 FreeRTOS 必须链接到 `0x6e800000`，并且启动入口必须为 `_start`。同时，FreeRTOS 使用的代码区、堆区和 RPMsg 共享内存必须与 DTS 中的 AMP 域保持一致。

**通过启动阶段标记确定故障位置：**

在 FreeRTOS `startup.S` 中加入分阶段串口标记：

```text
FreeRTOS startup.S UART OK (hart4)
FreeRTOS startup data OK
FreeRTOS startup bss OK
FreeRTOS startup libc OK
```

实际观察到：

```text
FreeRTOS startup.S UART OK (hart4)
FreeRTOS startup data OK
```

这说明：

- 入口 `_start` 已执行；
- 串口轮询输出已经工作；
- `.data` 初始化代码已执行；
- 故障发生在 BSS 清零阶段之前或过程中；
- 问题不再是“串口驱动完全不能输出”。

**检查 ELF 链接地址和段地址：**

通过 `nm` 检查 FreeRTOS ELF 符号，发现原来的链接结果中：

```text
_start       0x6e800000
_data        0x6e800000
```

`.data` 与代码入口使用同一个地址，说明启动时复制 `.data` 会覆盖正在执行的代码。该现象正好解释了为什么能够看到 `startup data OK`，但后续在 BSS 初始化阶段停止。

修复后的链接结果为：

```text
_start       0x6e800000
_data        0x6e811888
__bss_start  0x6e8149c0
__bss_end    0x6e82b520
_sp          0x6f000000
```

此时 `.data` 已经位于代码之后，不会覆盖 `.text`。

### FreeRTOS 链接脚本段布局错误

修改文件：

```text
trusted_domain/startup.S
trusted_domain/main.c
```

增加：

- 进入 `_start` 后立即初始化 UART 并输出；
- `.data` 初始化完成后输出；
- BSS 清零完成后输出；
- C 库初始化完成后输出；
- `main()` 中输出 HART4 和 VisionFive2 启动信息。

这些标记保留后，后续如果启动异常，可以快速确定是入口、段初始化、C 库初始化还是任务调度阶段的问题。


### UART时钟配置错误

UART 问题不是单一原因，而是原有 FreeRTOS/QEMU 串口实现与 JH7110 硬件寄存器配置不一致造成的。

首先，OpenSBI 能够通过 `uart8250` 输出，说明板卡物理串口和调试终端的波特率基本正确；但 FreeRTOS 没有输出，说明故障在 FreeRTOS 自己的 UART 初始化或访问方式，而不是终端连接问题。

随后对比 RT-Thread 的 JH7110 UART 初始化代码，确认以下差异：

1. JH7110 UART2 的时钟和复位需要由 `0x13020000` 的系统时钟寄存器显式配置；
2. JH7110 UART 寄存器使用 32 位访问，寄存器偏移是 `reg << 2`，不能沿用普通 QEMU 16550 的 8 位连续访问方式；
3. UART2 的波特率时钟为 24 MHz，115200 波特率对应的分频值为 13；
4. 原有 IER 位定义与实际使用不一致，需要按 NS16550 约定修正 RX/TX 使能位；
5. 在启动早期，FreeRTOS 任务、队列、PLIC 和中断还没有初始化，不能依赖任务发送函数验证 UART。

因此增加了不依赖 FreeRTOS 的轮询输出路径。`startup.S` 在数据段初始化之前直接执行：

```text
jh7110_uart_clock_init()
uart_poll_init()
uart_poll_puts(...)
```

实测输出：

```text
FreeRTOS startup.S UART OK (hart4)
```

这证明 HART4 已执行 FreeRTOS 入口、UART 时钟已打开、寄存器访问方式正确且串口发送轮询可以工作。之后再用 `startup data/bss` 标记继续定位到了链接脚本的段覆盖问题。

### 镜像打包地址和opensbi跳转地址不对应

修改文件：

```text
u-boot/board/starfive/visionfive2/spl.c
```

增加 RTOS 复制信息：

```text
AMP RTOS: base=...
AMP RTOS: offset=...
AMP RTOS: image_size=...
AMP RTOS: copy ... -> ..., size=...
```

该信息用于确认 SPL 实际读取的位置、目标地址和复制长度。

**检查 RTOS 镜像在 AMP 镜像中的偏移：**

FreeRTOS 被追加到 U-Boot 镜像末尾，U-Boot 原始镜像填充到 `0x330000`：

```text
U-Boot raw image offset = 0x330000
```

但是 OpenSBI `fw_payload.bin` 会在嵌入的 U-Boot 前增加 `0x200000`，因此 FreeRTOS 在最终 `fw_payload.bin` 中的偏移是：

```text
0x200000 + 0x330000 = 0x530000
```

曾经使用 `0x330000` 作为 DTS 中的 RTOS 偏移，导致 SPL 从错误位置复制数据。通过比较 `trusted_fw.bin` 和 `fw_payload.bin` 中的指令头，确认正确偏移为 `0x530000`。

## 解决

### 链接脚本
修改文件：

```text
trusted_domain/link-jh7110.lds
```

主要修改：

- 入口设置为 `_start`；
- ROM 起始地址设置为 `0x6e800000`；
- `.data` 改为放在代码之后的连续区域；
- `.bss` 放在 `.data` 之后；
- 栈放在 `0x6f000000` 附近的高地址区域；
- 避免 `.data`、`.bss` 和栈覆盖 `.text`。

### VisionFive2 UART 初始化

修改文件：

```text
trusted_domain/board/jh7110.c
trusted_domain/driver/serial/ns16550.c
trusted_domain/driver/serial/uart.h
```

主要修改：

- 使用 VisionFive2 的 UART2；
- 初始化 JH7110 UART2 的 APB 和 CORE 时钟；
- 解除 UART2 复位；
- 使用 32 位寄存器访问；
- 使用寄存器偏移左移 2 位；
- 设置 115200 波特率，24 MHz UART 时钟对应分频值 13；
- 修正 IER 的 RX/TX 使能位；
- 增加启动早期轮询发送接口，避免依赖中断、PLIC 或 FreeRTOS 调度器。

UART2 的关键初始化内容如下：

```text
系统时钟基址       0x13020000
UART2 APB 时钟偏移 0x254，设置 bit31
UART2 CORE 时钟偏移 0x258，设置 bit31
UART2 复位寄存器   0x300，清除 bit23/bit24
UART2 波特率       115200
UART 时钟          24 MHz
分频值             13
寄存器访问         32 bit
寄存器地址步长     4 bytes
```

UART 驱动在 `BOARD_JH7110` 下使用：

```c
#define Reg(reg) ((volatile uint32_t *)(UART2 + ((reg) << 2)))
```

这部分是解决“OpenSBI 有串口输出、FreeRTOS 没有串口输出”的关键修改。



### AMP DTS 和 RTOS 偏移

修改文件：

```text
u-boot/arch/riscv/dts/starfive_jh7110-amp.dts
u-boot/arch/riscv/dts/starfive_jh7110-amp-u-boot.dtsi
```

AMP DTS 中配置：

```text
rt-domain      -> HART4
rtcode         -> 0x6e800000
rtheap         -> 0x6f000000
rpmsg_shmem    -> 0x6e400000
```

U-Boot 专用 DTSI 中配置：

```dts
amp,rtos-offset = <0x530000>;
amp,rtos-code-base = <0x6e800000>;
```

# 问题3：启动失败，互斥量为 NULL，直接使用

**日志落盘缓冲区共享内存当前不可用**

#### 现象

启动过程中出现 `flush_mutex`、`mst_cb` 或其他 RTOS 对象为 `NULL`，随后继续调用其成员或执行加锁、释放操作，最终触发异常或启动停止。

#### 根因

FreeRTOS 的 mutex、semaphore、queue 和 task control block 都属于运行时对象。对象为 `NULL` 通常表示以下任一问题：

1. 创建函数失败；
2. 静态对象的存储区没有正确初始化；
3. 初始化顺序错误，在创建对象前就使用对象；
4. 堆空间不足；
5. Shell 命令表、Shell 对象或任务栈被越界写坏；
6. `.bss` 未正确清零或链接脚本导致对象区域被覆盖。

`NULL` mutex 本身不会自动产生 HardFault，但对 `NULL` handle 继续调用 FreeRTOS API 或访问其成员会导致非法访问。此前出现的 `Load Access Fault`、`Instruction Access Fault`，还可能是 Shell 表、函数指针或任务返回地址被破坏后的结果。

## 问题定位过程

开启 ASSERT 会有打印出现 

## 解决

创建对象后必须立即检查返回值：

```c
mutex = xSemaphoreCreateMutex();
if (mutex == NULL) {
    LOG_E("create mutex failed");
    return;
}
```

使用静态对象时，要保证控制块和 buffer 的生命周期覆盖整个任务运行期，并检查：

```c
configSUPPORT_STATIC_ALLOCATION
configTOTAL_HEAP_SIZE
configCHECK_FOR_STACK_OVERFLOW
```

同时对 Shell 任务、mailbox 任务和日志任务检查剩余栈空间，避免栈溢出覆盖相邻的命令表、函数指针或 RTOS 对象。启动阶段应保持以下顺序：

```text
时钟/复位初始化
  -> UART 初始化
  -> PLIC 初始化
  -> 驱动对象创建
  -> Shell 初始化
  -> 任务创建
  -> 开启外部中断
  -> vTaskStartScheduler()
```

不能在对象创建成功前注册回调，也不能在调度器启动前使用依赖任务、队列或信号量的异步接口。

# 问题4：出现中断风暴，Shell 输出一部分后卡顿

## 现象

启动后 Shell 只能输出一部分，随后系统卡顿；PLIC IRQ 计数持续增加，或者同一个 IRQ 被反复进入。

## 根因

中断风暴通常表示中断源没有被正确清除，或者共享 IRQ 的处理函数在没有消息时仍然返回错误状态。当前 mailbox 和 UART 需要分别处理各自的硬件状态：

1. PLIC 只负责 claim/complete，不会自动清除 UART 或 mailbox 外设状态；
2. mailbox handler 必须读取命令寄存器并写 CLR 寄存器清除当前通道；
3. UART handler 必须读取并清除 UART 的 pending 状态；
4. 共享 IRQ handler 在没有对应消息时应返回 `IRQ_NONE` 或直接退出；
5. 不能在硬中断上下文中执行大量日志输出、阻塞等待或获取 mutex。

此前 mailbox ISR 遍历并清除了发送通道和接收通道，既可能丢失发往 Linux 的消息，也可能造成状态机异常。修复后 FreeRTOS ISR 只处理 channel 1，Linux RX 负责处理并清除 channel 0。

## 问题定位过程


## 解决

中断处理函数应遵循：

```text
读取外设状态
  -> 判断是否属于当前通道
  -> 读取消息
  -> 清除外设 pending
  -> 保存少量调试状态
  -> 唤醒任务或调用非阻塞回调
  -> 返回并 complete PLIC IRQ
```

不要在 ISR 中直接打印完整日志。应在 ISR 中保存计数和寄存器快照，再由普通任务输出，例如：

```text
irq_count
last_irq
pending_before
pending_after
cmd0/cmd1
irq0/irq1
handled
```

如果 IRQ 计数持续增加但 `cmd` 为 0，优先检查 UART 状态清除和共享 IRQ 注册；如果 `cmd` 非 0 但 `pending_after` 不清零，检查 mailbox CLR 寄存器写入方式。




# 问题5：Linux 启动后 FreeRTOS 串口敲击回车没有反应

## 现象

FreeRTOS 单独启动时 UART2 Shell 正常。Linux 启动后，FreeRTOS 仍能周期性输出，但在 UART 终端敲击回车没有 Shell 响应。

## 根因

Linux 启动时会根据时钟框架关闭未被 Linux 使用的 unused clock。如果 Linux DTS 中仍声明或管理 UART2，Linux 可能在启动后关闭 UART2 的时钟或重新配置 UART2，导致 FreeRTOS 的 UART 接收中断和寄存器访问失效。

此时 FreeRTOS 的任务和 PLIC 可能仍然正常运行，因此可以看到：

```text
Hello from FreeRTOS!
PLIC IRQs 持续增加
```

但 UART2 的 RX 中断不再产生，回车自然无法进入 Shell。

## 问题定位过程

FreeRTOS 单独启动时可以进入 Shell，但 Linux 启动后只能继续看到周期日志，例如：

```text
Hello from FreeRTOS! Count: 12, PLIC IRQs: 11, Last IRQ: 34
```

此时 FreeRTOS 任务和 UART2 的部分输出仍然存在，但敲击回车没有 Shell 回显，说明问题集中在 UART2 RX 路径，而不是 FreeRTOS 调度器完全停止。

Linux 启动日志中反复出现：

```text
clk u0_mipitx_dphy_clk_txesc already disabled
```

结合 Linux 启动后 UART2 RX IRQ 不再增加，使用以下 U-Boot 参数验证：

```text
setenv bootargs "${bootargs} clk_ignore_unused"
```

加入后 FreeRTOS Shell 恢复，证明 Linux 的 unused clock 管理会影响 AMP 侧仍在使用的 UART2 时钟。`clk_ignore_unused` 只是验证和临时规避方法，最终方案是 Linux AMP DTS 禁用 UART2，避免 Linux 驱动、时钟或 reset controller 接管 FreeRTOS 使用的 UART2。

该问题还需要区分 UART IRQ34 和 mailbox IRQ26：

```text
IRQ34：UART2，负责 Shell 输入
IRQ26：mailbox，负责 Linux/FreeRTOS mailbox 通信
```

看到 PLIC 计数增加或 mailbox IRQ26 正常，并不能证明 UART2 RX IRQ34 仍然可用。

## 解决

AMP 模式下应明确 UART2 的所有权。若 UART2 由 FreeRTOS 使用，Linux DTS 不应启用或管理该 UART，避免 Linux 关闭其时钟、复位外设或注册 UART 驱动。

临时验证方法是在 U-Boot 中加入：

```text
setenv bootargs "${bootargs} clk_ignore_unused"
```

如果加入该参数后 FreeRTOS Shell 恢复，基本可以确认是 Linux 关闭了 UART2 的 unused clock。但这只是验证和临时规避方案，长期方案应修改 Linux AMP DTS，移除或禁用 UART2 节点，并确保 Linux 不拥有 UART2 的时钟和复位资源。

**Linux 驱动层正式修改：**

只在 DTS 中禁用 UART2 还不够。UART2 节点被移除后，Linux 串口驱动确实不会 probe，也不会直接操作 UART2 寄存器和 reset；但这也意味着 Linux 时钟框架看不到 UART2 的 consumer。在内核 late init 的 unused-clock 检查中，`uart2_apb` 和 `uart2_core` 仍可能因为引用计数为零而被关闭。

因此正式方案同时修改 AMP DTS 和 JH7110 Linux 时钟驱动。

1. 在 Linux AMP DTS 中删除 UART2 节点

文件：

```text
linux/arch/riscv/boot/dts/starfive/jh7110-starfive-visionfive-2-amp.dts
```

配置为：

```dts
/* UART2 (0x10020000, IRQ34) is owned by the FreeRTOS AMP image. */
&{/soc} {
    /delete-node/ serial@10020000;
};
```

这里使用 `/delete-node/`，而不是只写 `status = "disabled"`，目的是让 AMP DT 明确表示 Linux 完全不拥有 UART2，避免串口驱动绑定以及 clocks、resets、pinctrl 等资源被 Linux UART 设备管理流程引用。

2. 在 Linux 时钟驱动中保护 UART2 时钟

文件：

```text
linux/drivers/clk/starfive/clk-starfive-jh7110-sys.c
```

AMP 配置下为 UART2 两个 gate 增加 `CLK_IS_CRITICAL`：

```c
#ifdef CONFIG_RISCV_AMP
#define JH7110_UART2_CLK_FLAGS CLK_IS_CRITICAL
#else
#define JH7110_UART2_CLK_FLAGS 0
#endif
```

并应用到 UART2 APB 和 CORE 时钟：

```c
JH71X0_GATE(JH7110_SYSCLK_UART2_APB, "uart2_apb",
            JH7110_UART2_CLK_FLAGS, JH7110_SYSCLK_APB0),
JH71X0_GATE(JH7110_SYSCLK_UART2_CORE, "uart2_core",
            JH7110_UART2_CLK_FLAGS, JH7110_SYSCLK_OSC),
```

`CLK_IS_CRITICAL` 告诉 Linux common clock framework：即使 Linux 本身没有 UART2 consumer，也不能在 unused-clock 清理阶段关闭这两个 gate。该修改只在 `CONFIG_RISCV_AMP` 下生效，普通 Linux 配置仍保持原来的时钟管理行为。

3. 从 Linux PLIC 描述中移除 hart4 context

同一个 AMP DTS 还将 `&plic` 的 `interrupts-extended` 限制为 Linux 使用的 hart0～hart3 context，不再暴露 hart4 context。这样 Linux PLIC 驱动不会初始化或重配置 FreeRTOS 使用的 hart4 中断上下文，UART2 IRQ34 继续由 FreeRTOS 独占处理。

最终资源归属为：

```text
UART2 寄存器和复位：FreeRTOS 管理
UART2 APB/CORE gate：FreeRTOS 使用，Linux AMP 时钟驱动保持开启
UART2 IRQ34 / hart4 PLIC context：FreeRTOS 管理
Linux UART 驱动：不注册 UART2
```

完成上述修改后，启动参数中不再需要全局 `clk_ignore_unused`。该参数会阻止 Linux 关闭所有未使用时钟，只适合定位问题；驱动层的 `CLK_IS_CRITICAL` 只保护 AMP 对端实际占用的 UART2 时钟，影响范围更准确。

同时需要确认：

```text
UART2 基地址：0x10020000
UART2 IRQ：34
UART2 时钟和复位已在 FreeRTOS 初始化
Linux PLIC/DTS 没有重新接管 UART2
```

如果 Linux 必须使用 UART2，则不能让 Linux 和 FreeRTOS 同时独占同一个 UART，应改用不同 UART、虚拟串口或明确的 AMP 消息通道。
