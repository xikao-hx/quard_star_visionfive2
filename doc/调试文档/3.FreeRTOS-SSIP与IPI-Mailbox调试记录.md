# FreeRTOS SSIP 与 IPI Mailbox 调试记录

## 总结

这个问题是突然出现，理论上啥也没改，突然出现的这个问题也很奇怪，不够沉着冷静分析问题和用AI解决问题：
* 用AI解决问题还是不要让他直接根本问题改代码，还是要让它去增加调试来分析和定位问题

## 01. 问题背景

VisionFive 2 AMP 系统中，Linux 运行在主域，FreeRTOS 运行在 hart4。两侧通过共享内存保存 mailbox 数据，并使用 OpenSBI IPI 通知对端。

FreeRTOS RISC-V port 本身也使用 Supervisor Software Interrupt（SSIP）完成 `portYIELD()` 和任务上下文切换。因此，接入 IPI mailbox 后存在两类共用同一 SSIP 中断入口的事件：

1. FreeRTOS 调度器产生的任务切换 IPI。
2. Linux 发给 FreeRTOS 的 mailbox IPI。

## 2. 故障现象

FreeRTOS 可以完成硬件和 mailbox 初始化，并能输出调度器启动前的同步日志：

```text
I/MAB_ROUTER  init_quard_mbox_router enter
I/IPI_MAILBOX FreeRTOS IPI mailbox init successful: base=0x6e402000
D/MAB_ROUTER  Router mbox init done.
I/MAIN        Hello FreeRTOS on VisionFive 2 (hart4)
```

但之后没有 Letter Shell banner、`letter:/$` prompt，也没有 `router server mbox_c1 started`。

这些日志只能证明 `userShellInit()` 已经返回并执行到 `vTaskStartScheduler()` 之前，不能证明 UART TX、router consumer 或 Shell 任务已经运行。

## 3. 排查过程

### 3.1 排除 Shell 创建失败

检查 `userShellInit()` 后确认：

- Shell RX queue 已创建。
- remote-shell mailbox consumer 已注册。
- Shell task 使用静态栈和静态 TCB 创建。
- `main()` 已继续执行到调度器启动前。

因此问题不在 Letter Shell 初始化函数本身。

### 3.2 排除 log/NOR 服务影响

调试过程中曾怀疑新增的共享内存日志定时器、log agent 和 NOR agent 影响任务启动，因此临时取消了这些服务的自动启动。

检查最终 `trusted_fw.elf` 和 `main.o` 后确认，故障镜像中已经没有调用：

```c
log_rb_backend_init();
soc_log_agent();
init_quard_nor_agent();
```

故障仍然存在，因此这些服务不是根因。

### 3.3 排除 timer daemon 栈大小

`configTIMER_TASK_STACK_DEPTH` 长期配置为 110，曾被怀疑为最高优先级 timer daemon 的栈不足。

但该配置在此前可工作版本中已经存在，而且调整后故障现象不变，因此恢复原配置，不将其作为本次问题的修复项。

### 3.4 增加启动阶段探针

第一阶段的目标是确认程序停在以下哪个边界：

```text
vTaskStartScheduler()
  -> xPortStartFirstTask()
  -> 第一个任务开始运行
  -> 第一次 SSIP
  -> vTaskSwitchContext()
  -> UART/Shell 等普通任务运行
```

此时不能使用 `LOG_I()` 或 `uart_puts()` 作为关键探针，因为它们在调度器启动后依赖 UART TX queue 和 `UART_TX` task。如果 UART task 本身没有运行，这些日志也不会输出，容易把“日志发送任务未运行”误判为“探针代码未执行”。

因此临时使用 `uart_poll_puts()`。该函数位于：

```text
trusted_domain/driver/serial/ns16550.c
```

它直接轮询 UART LSR 的 `LSR_TX_IDLE` 位并写 THR，不依赖 FreeRTOS queue、信号量或 UART TX task。

#### 3.4.1 调度器首次任务恢复前

文件：

```text
trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/port.c
```

函数：

```c
BaseType_t xPortStartScheduler(void)
```

在 `xPortStartFirstTask()` 前临时加入：

```c
uart_poll_puts("[DBG] FreeRTOS starting first task\r\n");
xPortStartFirstTask();
```

该日志出现，说明：

- idle task 和 timer daemon 创建成功。
- `vTaskStartScheduler()` 已进入 RISC-V port。
- timer 中断和 SSIP 使能代码已经执行。
- 下一步即将从 `pxCurrentTCB` 恢复首个任务上下文。

#### 3.4.2 第一次 SSIP 清除完成后

同一文件中的：

```c
void vPortClearIpiInterrupt(void)
```

临时加入只执行一次的探针：

```c
static BaseType_t first_ssip = pdTRUE;

quard_ipi_mailbox_handle();

if (first_ssip != pdFALSE) {
    first_ssip = pdFALSE;
    uart_poll_puts("[DBG] FreeRTOS first SSIP handled\r\n");
}
```

只打印一次是为了避免 SSIP 异常时在中断上下文中无限刷日志，进一步改变故障时序。

#### 3.4.3 UART TX task 入口

文件：

```text
trusted_domain/driver/serial/ns16550.c
```

函数：

```c
void uart_tx_task(void *pvParameters)
```

在任务循环前临时加入：

```c
uart_poll_puts("[DBG] UART TX task started\r\n");

while (1) {
    /* 原 UART TX queue 处理过程 */
}
```

该探针不通过该任务负责消费的 `uart_tx_queue` 输出，否则无法证明任务入口是否真正执行。

#### 3.4.4 Shell task 入口

文件：

```text
trusted_domain/driver/shell/src/shell_port.c
```

为了避免直接修改 Letter Shell 通用源码，临时增加包装函数：

```c
static void userShellTask(void *param)
{
    uart_poll_puts("[DBG] Shell task started\r\n");
    shellTask(param);
}
```

并临时将任务创建入口从：

```c
xTaskCreateStatic(shellTask, ...);
```

改为：

```c
xTaskCreateStatic(userShellTask, ...);
```

探针完成后仍调用原始 `shellTask(param)`，不改变 Shell 的读取、解析和回显逻辑。

#### 3.4.5 第一阶段结果

实际只得到：


```text
[DBG] FreeRTOS starting first task
[DBG] FreeRTOS first SSIP handled
```

没有出现 UART TX 和 Shell 入口日志。这说明：

- `xPortStartFirstTask()` 已成功恢复首个任务，而不是停在调度器初始化阶段。
- CPU 已进入并执行 `vPortClearIpiInterrupt()`。
- 问题位于第一次 SSIP 清除之后，包括 `vTaskSwitchContext()`、`processed_source` 上下文恢复或 SSIP 持续 pending。

### 3.5 跟踪 SSIP 类型和任务选择

第一阶段只能证明 SSIP 后没有运行普通任务，不能区分以下情况：

1. `vTaskSwitchContext()` 没有返回。
2. 调度器一直选择同一个任务。
3. 调度器选择正确，但 `sret` 后立即再次进入 SSIP。

因此第二阶段继续增加以下探针。

#### 3.5.1 临时返回 SSIP 消息类型

文件：

```text
trusted_domain/driver/mailbox/ipi_mailbox.c
```

函数：

```c
quard_ipi_mailbox_handle()
```

调试阶段临时把返回类型从 `void` 改为 `unsigned long`，返回 OpenSBI 写入的 `msg_type`：

```c
unsigned long quard_ipi_mailbox_handle(void)
{
    unsigned long msg_type = 0;
    int ret;

    ret = sbi_clear_ipi_amp(&msg_type);
    if (ret != 0) {
        sbi_clear_ipi();
        return ~0UL;
    }

    /* 根据 msg_type 处理 mailbox。 */
    return msg_type;
}
```

调试返回值约定如下：

| 返回值 | 临时日志 | 含义 |
|---|---|---|
| `0` | `scheduler yield` | 没有 AMP mailbox 消息位，是 FreeRTOS 自身调度 SSIP |
| `~0UL` | `AMP fallback` | AMP clear ecall 失败，已回退标准 IPI 清除 |
| 其他非零值 | `mailbox` | 收到了 Linux 发来的 AMP mailbox 类型位 |

这个返回值仅用于定位 SSIP 来源，正式代码不需要向 port 层暴露 `msg_type`。

#### 3.5.2 输出前八次 SSIP 类型

文件：

```text
trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/port.c
```

在 `vPortClearIpiInterrupt()` 中临时记录前八次 SSIP：

```c
static unsigned int ssip_trace_count;
unsigned long msg_type;

msg_type = quard_ipi_mailbox_handle();

if (ssip_trace_count < 8U) {
    ssip_trace_count++;
    if (msg_type == 0UL)
        uart_poll_puts("[DBG] SSIP cleared: scheduler yield\r\n");
    else if (msg_type == ~0UL)
        uart_poll_puts("[DBG] SSIP cleared: AMP fallback\r\n");
    else
        uart_poll_puts("[DBG] SSIP cleared: mailbox\r\n");
}
```

限制为八次的原因是：如果 SSIP 没有被清除，中断会快速重复触发；无限打印不仅淹没有效日志，还会显著改变中断和任务切换时序。

#### 3.5.3 在任务选择后输出新任务名

同一文件中临时增加：

```c
void vPortSwitchContextFromIpi(void)
{
    static unsigned int switch_trace_count;

    vTaskSwitchContext();
    if (switch_trace_count < 8U) {
        switch_trace_count++;
        uart_poll_puts("[DBG] SSIP selected task: ");
        uart_poll_puts(pcTaskGetName(NULL));
        uart_poll_puts("\r\n");
    }
}
```

这里先调用原始 `vTaskSwitchContext()`，再通过 `pcTaskGetName(NULL)` 读取新的 `pxCurrentTCB` 对应任务名。

随后在：

```text
trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/portASM.S
```

将 SSIP 分支中的临时调用从：

```asm
jal vPortClearIpiInterrupt
jal vTaskSwitchContext
```

改为：

```asm
jal vPortClearIpiInterrupt
jal vPortSwitchContextFromIpi
```

除增加任务名输出外，包装函数内部仍调用原始 `vTaskSwitchContext()`，汇编保存和恢复上下文的流程没有变化。

#### 3.5.4 第二阶段结果

得到：

```text
[DBG] SSIP cleared: scheduler yield
[DBG] SSIP selected task: UART_TX
[DBG] SSIP cleared: scheduler yield
[DBG] SSIP selected task: isr_log
[DBG] SSIP cleared: scheduler yield
[DBG] SSIP selected task: mbox_c1
[DBG] SSIP cleared: scheduler yield
[DBG] SSIP selected task: shell
```

日志证明：

- SSIP 来自 FreeRTOS scheduler yield，不是 Linux mailbox 连续发送造成的中断风暴。
- `vTaskSwitchContext()` 能正常返回。
- 调度器依次选择了 `UART_TX`、`isr_log`、`mbox_c1` 和 `shell`，ready list 与优先级选择正确。
- 尽管选中了 UART TX 和 Shell，它们的入口探针仍未执行。

因此 CPU 在 `sret` 恢复新任务后、执行任务第一条有效指令前再次进入同一个 SSIP。最终确定为 SSIP 没有被可靠清除，而不是任务创建、任务选择或 Shell 逻辑错误。

## 4. 根因

接入 IPI mailbox 时，FreeRTOS 原来的标准 SSIP 清除过程被替换为仅调用 AMP 扩展：

```c
sbi_clear_ipi_amp(&msg_type);
```

FreeRTOS 调度 IPI 和 mailbox IPI 共用 SSIP。实际运行中，AMP clear ecall 可以成功返回并取走 mailbox 消息位，但调度产生的 Supervisor IPI 仍可能保持 pending。

结果是：

```text
选择新任务
  -> 恢复任务上下文
  -> SSIP 仍 pending
  -> 新任务第一条指令执行前再次进入 SSIP
  -> 再次选择任务
  -> 无限循环
```

因此可以看到任务名循环变化，却看不到任何任务入口代码执行。

## 5. 正式修复

### 5.1 第一轮修复：恢复标准 SSIP 清除

在 `quard_ipi_mailbox_handle()` 中保留 AMP 消息读取，同时无条件执行标准 IPI 清除：

```c
ret = sbi_clear_ipi_amp(&msg_type);
sbi_clear_ipi();

if (ret != 0)
    return;
```

两次调用职责不同：

- `sbi_clear_ipi_amp()`：读取并清空 OpenSBI AMP mailbox 消息位。
- `sbi_clear_ipi()`：确保 hart4 的标准 Supervisor Software Interrupt 被清除。

之后再根据 `msg_type` 分发 Linux 到 FreeRTOS 的 mailbox 数据或 ACK。

### 5.2 第二轮修复：消除 SSIP 清除与新 mailbox IPI 的竞态

第一轮修复可以让 FreeRTOS 任务正常启动，但还不能完整覆盖 mailbox IPI 与调度 IPI 并发到达的情况。后续压力测试中仍可能出现 mailbox 消息位已经写入，但 hart4 不再进入 SSIP，表现为：

- 第一次或前几次通信正常，之后发送等待 ACK 超时。
- Linux 已成功执行 `sbi_send_ipi_amp()`，FreeRTOS consumer 却没有收到新消息。
- 共享内存中的 channel 状态停留在 `DATA_READY`。
- remote shell 在连续输入后不再回显，看起来像 FreeRTOS 挂死。

竞态窗口位于“读取 AMP 消息位”和“清除 SSIP”之间。原 OpenSBI 扩展处理顺序为：

```text
atomic_xchg(AMP message bits, 0)
clear SSIP
```

如果新的 mailbox IPI 恰好在两步之间到达：

```text
旧消息位被取走
  -> 新消息写入 AMP bits 并置位 SSIP
  -> 旧处理流程随后清除 SSIP
  -> 新消息位仍在，但已没有 SSIP 再次通知 hart4
```

因此在 `opensbi/lib/sbi/sbi_ipi.c` 的 `sbi_ipi_clear_ext_ipi()` 中，将正式顺序改为：

```c
sbi_ipi_clear_smode();
msg_type = atomic_raw_xchg_ulong(amp_data_addr + current_hartid(), 0);
*(unsigned long *)addr = msg_type;
```

新顺序的覆盖关系为：

- 新 IPI 在 `sbi_ipi_clear_smode()` 之前到达：本次原子交换取走消息位。
- 新 IPI 在清除 SSIP 后、原子交换前到达：本次原子交换仍能取走消息位。
- 新 IPI 在原子交换后到达：消息位和 SSIP 都会保留，由下一次 trap 处理。

FreeRTOS 侧同时增强 `trusted_domain/driver/mailbox/ipi_mailbox.c` 中的 `quard_ipi_mailbox_handle()`：

```c
unsigned long msg_type = 0;
unsigned long pending_type = 0;
int ret;

ret = sbi_clear_ipi_amp(&msg_type);
sbi_clear_ipi();
if (ret != 0)
    return;

if (sbi_clear_ipi_amp(&pending_type) == 0)
    msg_type |= pending_type;
```

第二次 `sbi_clear_ipi_amp()` 用于接收第一次 AMP ecall 与标准 `sbi_clear_ipi()` 之间可能新到达的消息，并通过按位或合并到本轮待处理类型中。这样既保留 FreeRTOS 调度器要求的标准 SSIP 清除，也不会把并发到达的 mailbox 类型位遗留到无中断状态。

对应修复提交为：

```text
ceed7f412 fix(mailbox): SSIP 没有调用标准 sbi_clear_ipi清除；isr_nesting 只减不加
75fb1ab56 fix: SSIP、UART和remote shell遗留提交
```

### 5.3 mailbox router ISR 不重复触发任务切换

FreeRTOS mailbox 接收通知 `router_rx_notify()` 运行在 SSIP trap 上下文中。该路径通过：

```c
xQueueSendToBackFromISR(consumer->rx_queue, msg, NULL);
```

把 28 字节消息复制到对应 consumer queue。这里最终没有调用 `portYIELD_FROM_ISR()`，原因不是不需要唤醒 consumer，而是当前 RISC-V SSIP 汇编出口在 `vPortClearIpiInterrupt()` 返回后固定调用：

```asm
jal vTaskSwitchContext
```

也就是说，本次 trap 退出前已经会选择最高优先级 ready task。若 `router_rx_notify()` 再调用 `portYIELD_FROM_ISR()`，会在同一次 mailbox SSIP 中重复请求调度，可能在 ACK 尚未完成时再次进入 SSIP，造成重复切换、上下文时序异常或中断风暴。

需要区分另一路 `send_shell_queue()`：它可能由 UART PLIC 中断调用，该中断出口没有 mailbox SSIP 路径的固定切换语义，因此仍应使用 `high_pri_task_ready` 和 `portYIELD_FROM_ISR()` 唤醒 Shell task。两处不能机械地采用同一种处理方式。

### 5.4 mailbox 错误路径禁止递归日志

remote shell 和 EasyLogger 的输出本身也通过 mailbox router 发送。如果 `quard_router_send_msg()` 或 `quard_router_send_msg_shell()` 在 mailbox 发送失败后调用 `LOG_E()`：

```text
mailbox 发送失败
  -> LOG_E()
  -> remote_shell_write()
  -> 再次进入 quard_router_send_msg()
  -> 再次失败并打印 LOG_E()
  -> 无限递归，最终栈溢出或系统假死
```

因此这两个底层发送函数只返回 `mbox_send_message()` 的原始错误码，不再通过同一传输链路记录错误。错误应由不会再次进入 mailbox 日志后端的上层处理，或者使用调试阶段的轮询 UART 输出。

## 6. 修复验证

### 6.1 调度器恢复验证

修复后日志显示：

```text
[DBG] SSIP selected task: UART_TX
[DBG] UART TX task started
[DBG] SSIP selected task: shell
[DBG] Shell task started
```

随后正常输出 Letter Shell banner：

```text
Build:       Aug 19 2026
Version:     3.2.4
Copyright:   (c) 2020 Letter

letter:/$
```

`mbox_c1` consumer 和 IDLE task 也能正常运行，证明 FreeRTOS 调度器、UART、router 和 Shell 均已恢复。

验证完成后，已删除所有 `[DBG]` 轮询输出和临时任务包装函数，只保留 SSIP 双重清除的正式修复。

具体清理内容如下：

- 删除 `port.c` 中启动前、SSIP 类型和任务名探针。
- 删除临时 `vPortSwitchContextFromIpi()`。
- 将 `portASM.S` 恢复为直接调用 `vTaskSwitchContext()`。
- 删除 `ns16550.c` 中 UART TX task 入口探针。
- 删除 `shell_port.c` 中临时 `userShellTask()`。
- 将 Shell 的 `xTaskCreateStatic()` 入口恢复为原始 `shellTask`。
- 将 `quard_ipi_mailbox_handle()` 返回类型恢复为 `void`。
- 保留 `sbi_clear_ipi_amp()` 后无条件调用 `sbi_clear_ipi()` 的正式修复。

### 6.2 mailbox 连续通信验证

第二轮修复后，需要连续触发 Linux 到 FreeRTOS、FreeRTOS 到 Linux 和 remote shell 三类流量，不能只验证一次发送。重点确认：

1. Linux 每次写入后，发送 channel 都能按 `IDLE -> DATA_READY -> ACK -> IDLE` 完成一轮状态转换。
2. FreeRTOS consumer queue 能连续接收消息，不停留在 `DATA_READY`。
3. FreeRTOS 回复经过反向 channel 到达 Linux，Linux ACK 后反向 channel 回到 `IDLE`。
4. 连续输入 remote shell 时，字符、回车和 prompt 均能持续回显。
5. 不再出现 ACK timeout、SSIP 连续重入、Instruction Access Fault 或 remote-log 递归。

本轮验证同时说明：一次通信成功只能证明共享内存地址、IPI hart 和基本方向正确，不能证明 SSIP 清除顺序和 ACK 状态机在连续通信下可靠。

## 7. 为什么 RT-Thread 未出现同样问题

RT-Thread 的 IPI mailbox 和调度器中断处理流程与当前 FreeRTOS RISC-V port 不同。当前 FreeRTOS 明确使用 SSIP 实现 `portYIELD()`，因此 mailbox 接入不能简单覆盖 `vPortClearIpiInterrupt()` 原有的标准清除职责。

移植其他 RTOS 的 IPI mailbox 实现时，可以复用共享内存布局、消息状态和 ACK 协议，但必须保留目标 RTOS 自身的调度中断处理过程。

## 8. 后续约束

1. mailbox IPI 与调度 IPI 共用 SSIP 时，必须同时处理两类状态。
2. mailbox handler 不能替代 FreeRTOS port 的标准 SSIP 清除。
3. ISR 中只完成消息读取、ACK 和队列唤醒，不进行持续日志输出。
4. 调试任务切换问题时，应使用轮询 UART，避免依赖尚未运行的 UART TX task。
5. 运行验证完成后应删除中断路径中的调试输出，避免改变时序。
6. OpenSBI AMP IPI 必须采用“先清 SSIP、再原子取走消息位”的顺序，不能恢复为相反顺序。
7. FreeRTOS mailbox handler 在标准 SSIP 清除后必须再次合并可能并发到达的 AMP 消息位。
8. mailbox SSIP trap 出口已经执行任务切换时，router ISR 不应再次调用 `portYIELD_FROM_ISR()`。
9. mailbox、remote shell 和 mailbox 日志后端的底层错误路径禁止使用同一链路递归打印。
10. 修改 mailbox、OpenSBI IPI 或 FreeRTOS trap 路径后，必须进行连续双向通信和 remote shell 压力验证，不能只做单次收发测试。
