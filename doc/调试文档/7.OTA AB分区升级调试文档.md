# OTA AB 分区升级调试文档

## OTA AB 启动调试记录

### 1. 调试背景

SD 卡使用 GPT 分区表，Linux A/B 槽位映射为：

| 槽位 | boot 分区 | rootfs 分区 | Linux 设备名 |
| --- | --- | --- | --- |
| A | p3 | p4 | `/dev/mmcblk1p4` |
| B | p5 | p6 | `/dev/mmcblk1p6` |

SPL 和 U-Boot proper 从 SPI NOR `recovery` 分区的 `current_bank`
选择槽位。U-Boot 再从选中的 p3/p5 加载 `vf2_uEnv.txt` 和
`image.fit`，并把 p4/p6 的 GPT `PARTUUID` 写入 Linux `bootargs`。

正常的 B 槽位选择日志为：

```text
SD bootctrl: current=b target=b
SD bootctrl: slot b uses SD boot 5, rootfs 6
```

`PARTUUID` 是 GPT 中每个分区的唯一标识，不依赖 Linux 将 SD
卡枚为 `mmcblk0` 还是 `mmcblk1`，比固定设备名更适合 A/B 启动。

### 2. 现象

#### 2.1 U-Boot 选择 B，Linux 却仍挂载 p4

U-Boot 显示已选择 B：

```text
SD bootctrl: current=b target=b
SD bootctrl: slot b uses SD boot 5, rootfs 6
```

但 Linux 命令行仍然是：

```text
Kernel command line: console=ttyS0,115200 earlycon=sbi \
root=/dev/mmcblk1p4 rootwait rw
```

这表明 bootctrl 已经计算出 p5/p6，但后续启动命令没有使用
`sd_bootpart` 和 `sd_rootpart`。

#### 2.2 恢复自动入口后，PARTUUID 挂载失败

清除固定 `bootargs` 并恢复 SDK 自动入口后：

```sh
setenv bootcmd 'run sdk_boot_env; run distro_boot_env'
setenv bootargs
saveenv
reset
```

U-Boot 能够从 p5 加载 FIT，也能把 p6 的 PARTUUID 传给 Linux：

```text
Kernel command line: ... \
root=PARTUUID=8852481a-92d5-492a-b7bb-436998efe31a \
rw active_bank=1
```

但早期用户空间挂载失败：

```text
PARTUUID=8852481a-92d5-492a-b7bb-436998efe31a: Can't lookup blockdev
mount: mounting PARTUUID=... on /rootfs/ failed: No such file or directory
Kernel panic - not syncing: Attempted to kill init!
```

手动改用设备名后可以正常启动 B：

```sh
setenv bootargs 'console=ttyS0,115200 earlycon=sbi root=/dev/mmcblk1p6 rootwait rw active_bank=1'
fatload mmc 1:5 ${loadaddr} image.fit
bootm ${loadaddr}
```

这证明 p5 中的 FIT、p6 中的 rootfs 和 A/B 映射均正常，
故障集中在 initramfs 的 PARTUUID 处理。

#### 2.3 修改 `/init` 后仍然出现旧报错

源码已增加 PARTUUID 解析，重新生成的 FIT 却仍然出现：

```text
mount: mounting PARTUUID=... failed
/init: line 71: can't open /rootfs/dev/console
```

进一步对比发现：

```text
buildroot/system/skeleton/init          新版
work/buildroot_initramfs/target/init   旧版
work/buildroot_initramfs_sysroot/init  旧版
/sbin/blkid                            BusyBox 版本
```

另外，启动日志中 FIT 的读取大小为 `19121192` 字节，与旧的
`work/target/amp/image.fit` 完全一致，而新的
`work/amp/image.fit` 为 `19165448` 字节。这证明板端实际使用了
旧镜像。

#### 2.4 PARTUUID 成功后仍不出现 Shell

更新正确 FIT 后，PARTUUID 已成功解析且 p6 已挂载：

```text
find PARTUUID=8852481a-92d5-492a-b7bb-436998efe31a \
as /dev/mmcblk1p6: 0
EXT4-fs (mmcblk1p6): mounted filesystem ... r/w
INIT: Entering runlevel: 3
Starting network: OK
```

但启动停在 `Starting network: OK` 之后，没有出现 Dropbear 和
`buildroot login:`。

### 3. 排查过程

#### 3.1 确认 A/B 选择与实际 rootfs

U-Boot 中检查：

```sh
printenv bootcmd
printenv bootargs
printenv sd_bootpart sd_rootpart bootpart rootpart
printenv sdk_boot_env mmc_test_and_boot
part uuid mmc 1:6 rootuuid
printenv rootuuid
```

Linux 能启动时检查：

```sh
cat /proc/cmdline
findmnt /
ota_info read current_bank
ota_info read target_bank
```

B 槽位的预期结果是：

```text
root=PARTUUID=<p6 PARTUUID>
/dev/mmcblk1p6 mounted on /
current_bank=b
target_bank=b
```

#### 3.2 分离 U-Boot、FIT 和 rootfs 问题

通过临时使用 `root=/dev/mmcblk1p6` 成功启动，确认以下环节无故障：

- U-Boot 已选择 B；
- p5 中 `image.fit` 可读且 FIT hash 校验通过；
- p6 包含可用的 ext4 rootfs；
- Linux MMC 驱动能够识别 p1 到 p6。

因此不应将问题误判为“p5/p6 是新增分区，U-Boot 无法使用”。
GPT 在分区工具创建 p5/p6 时已更新，U-Boot 可以直接读取。

#### 3.3 检查 initramfs `/init`

原 `/init` 将 `root=` 一律当作文件路径：

```sh
if [ ! -e $ROOT ]; then
    sleep 0.1
fi
mount $ROOT /rootfs/
```

当 `ROOT=PARTUUID=...` 时，`[ -e ]` 实际检查的不是 `/dev`
设备节点。当前 BusyBox `blkid` 也只输出文件系统 UUID，不能用于
GPT PARTUUID 查询。

#### 3.4 检查增量构建与部署文件

对比源码、Buildroot target、解包 sysroot 的 `/init` hash：

```sh
sha256sum \
    buildroot/system/skeleton/init \
    work/buildroot_initramfs/target/init \
    work/buildroot_initramfs_sysroot/init
```

检查 `blkid` 是否仍是 BusyBox 软链接：

```sh
ls -l work/buildroot_initramfs/target/sbin/blkid
file -L work/buildroot_initramfs/target/sbin/blkid
```

检查构建和实际部署镜像：

```sh
stat work/amp/image.fit work/target/amp/image.fit
sha256sum work/amp/image.fit work/target/amp/image.fit
```

必须再对比 SD p3/p5 中 `image.fit` 的 hash，不能只根据文件名
判断已经更新。

#### 3.5 确认 Shell 被哪个启动服务阻塞

`work/buildroot_rootfs/target/etc/inittab` 已包含：

```text
sole::respawn:/sbin/getty -L console 0 vt100
```

因此不是 getty 缺失。SysV init 使用 `wait` 运行 `rcS`，
`S41nfs-root` 又在前台调用：

```sh
mount -t nfs -o nolock,vers=3 \
    192.168.5.11:/home/xikao/VisionFive2_6.6/nfs_rootfs /mnt
```

此时 `S40network` 只完成了地址配置，PHY 链路可能尚未 Link Up。
NFS RPC 请求可长时间阻塞，导致 `rcS` 不返回，后续
`S50dropbear` 和串口 getty 都无法启动。

### 4. 根因

本次调试先后暴露了四个独立问题：

1. U-Boot 持久化环境中的 `bootcmd` 和 `bootargs` 硬编码为
   p3/p4，绕过了 bootctrl 输出的 p5/p6。
2. 恢复自动启动后，`vf2_uEnv.txt` 正确传递 `root=PARTUUID=...`，
   但 initramfs `/init` 只支持 `/dev/...` 格式，无法将 GPT PARTUUID
   解析为块设备。
3. Buildroot 增量构建没有重新安装 skeleton `/init`，util-linux
   也保留了旧构建结果；同时 `work/target/amp/image.fit` 没有随
   `work/amp/image.fit` 同步，导致板端反复运行旧镜像。
4. PARTUUID 修复生效后，完整 rootfs 中的 `S41nfs-root` 仍在
   SysV `rcS` 前台挂载 NFS。网络不可用时它会阻塞 Shell 和 SSH
   启动。

原 A 槽位看似没有 PARTUUID 问题，是因为当时持久化 `bootargs`
直接使用 `root=/dev/mmcblk1p4`，并未经过 PARTUUID 解析路径。

### 5. 修复

#### 5.1 恢复 U-Boot 自动 A/B 入口

删除持久化的固定 `bootargs`，使 U-Boot 每次启动都根据
`recovery.current_bank` 选择 3/4 或 5/6：

```sh
setenv bootcmd 'run sdk_boot_env; run distro_boot_env'
setenv bootargs
saveenv
reset
```

不要再保存以下这类固定命令：

```text
root=/dev/mmcblk1p4
fatload mmc 1:3 ...
```

#### 5.2 让 initramfs 解析 PARTUUID

`buildroot/system/skeleton/init` 现在区分两种 root 格式：

```text
/dev/...       直接等待对应块设备
PARTUUID=...   先用 util-linux blkid 解析设备路径
```

核心逻辑：

```sh
ROOT_DEVICE=$(/sbin/blkid -t "$ROOT" -o device 2>/dev/null)
if [ -n "$ROOT_DEVICE" ] && [ -b "$ROOT_DEVICE" ]; then
    mount "$ROOT_DEVICE" /rootfs
fi
```

Buildroot 的 BusyBox `blkid` 不报告 GPT PARTUUID，因此为 util-linux
新增了独立 `BR2_PACKAGE_UTIL_LINUX_BLKID` 选项。默认和 debug
initramfs 都显式启用该选项，只引入 `blkid + libblkid`，不引入
整套 util-linux 工具。

#### 5.3 修复增量构建和发布同步

- `conf/amp_rootfs_post_build.sh` 强制将源码 skeleton `/init` 安装到
  Buildroot target；
- 文件戳依赖保证 util-linux 配置变化后执行
  `util-linux-dirclean`；
- initramfs 配置、`/init`、post-build 脚本和 util-linux 规则均成为
  AMP FIT 的文件依赖；
- `make publish_amp_images` 将 OTA 所需的 AMP SPL、fw_payload、FIT 和 rootfs
  发布到 `work/target/amp`，OTA 自动取包也从该目录读取，不再维护平铺的
  兼容副本；该目标不生成或发布 `sdcard_amp.img`。

#### 5.4 NFS 自动挂载不再阻塞启动

`S41nfs-root` 改为后台重试，并为 NFS 请求增加边界：

```text
nolock,vers=3,soft,timeo=10,retrans=1
```

即使 NFS 主机不可达，`rcS` 也能继续启动 Dropbear 和串口
getty。脚本使用 `/run/nfs-root.pid` 防止重复重试任务。

initramfs `/init` 移动 devtmpfs 时，`/dev/shm` 和 `/dev/pts` 会作为
子挂载一起移动，因此删除了后续重复 `mount --move` 操作，
避免非致命的 `No such file or directory` 报错。

### 6. 构建与部署

#### 6.1 重新生成 AMP Linux FIT

```sh
make ampfit RTOS=freertos -j$(nproc)
```

必须使用本次成功构建的：

```text
work/amp/image.fit
```

A/B boot 分区都应保持同步：

```text
p3:/image.fit
p5:/image.fit
```

复制后比较工作区与 SD 卡文件的 SHA-256，两者必须一致。

#### 6.2 重新生成完整 rootfs

NFS 启动脚本位于完整 rootfs，需要另外生成：

```sh
make buildroot_rootfs
```

输出：

```text
work/buildroot_rootfs/images/rootfs.ext4
```

更新 B 槽位时将它写入 p6，更新 A 槽位时写入 p4。
`dd` 会覆盖整个目标分区，操作前必须核对主机设备名。

### 7. 修复后验证

#### 7.1 B 槽位预期日志

```text
SD bootctrl: current=b target=b
SD bootctrl: slot b uses SD boot 5, rootfs 6
Kernel command line: ... root=PARTUUID=<p6 PARTUUID> ... active_bank=1
find PARTUUID=<p6 PARTUUID> as /dev/mmcblk1p6: <count>
EXT4-fs (mmcblk1p6): mounted filesystem ... r/w
Starting network: OK
Starting NFS root mount in background
Starting dropbear sshd: OK
buildroot login:
```

#### 7.2 Linux 中确认槽位

```sh
cat /proc/cmdline
findmnt /
ota_info read current_bank
ota_info read target_bank
mountpoint /mnt
ps | grep '[d]ropbear'
```

B 槽位必须同时满足：

```text
boot FIT 来自 p5
rootfs 挂载为 p6
current_bank=b
target_bank=b
```

不能只依据 `SD bootctrl: slot b uses ...` 就判定整个 B 槽位启动
成功；还必须核对 Linux 命令行和实际根挂载。

### 8. 遗留观察项

日志中曾出现：

```text
Initramfs unpacking failed: invalid magic at start of compressed archive
```

当时 `/init` 仍然被成功执行，因此该警告不是 PARTUUID 挂载失败
的直接原因。它可能与 U-Boot `boot2` 向 `booti` 传递的 ramdisk
长度有关，应作为独立问题继续跟踪，不应与本次 PARTUUID
修复混为同一根因。
