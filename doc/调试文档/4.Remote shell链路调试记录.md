# Remote Shell 回显问题调试与修复

## 总结

一直让AI分析，但是还是那句话，自己没有分析问题的能力以及没有让AI去增加调试打印来分析问题

## 1. 文档目的

本文记录 VisionFive 2 AMP 环境下 `/dev/quard-freertos0` Remote Shell 的回显故障、定位依据和正式修复。

本次调试中出现过多种外观相似、实际原因不同的问题，不能统一归结为“mailbox 没收到数据”：

1. Linux 输入能够到达 FreeRTOS，但终端光标逐渐不换行或固定在一行。
2. 连续输入若干次后，mailbox channel 停在 `DATA_READY`，后续等待 ACK。
3. FreeRTOS 日志从正常任务名变成 `[ISR]`，之后一直保持 `[ISR]`。
4. FreeRTOS 调度器启动后普通任务不运行，Shell prompt 完全不出现。

其中第 4 类问题的 SSIP 调试过程已记录在：

```text
doc/开发文档/6.FreeRTOS-SSIP与IPI-Mailbox调试记录.md
```

本文重点说明 Remote Shell 数据链路和 Linux TTY 回显。

## 2. 数据链路

Linux 到 FreeRTOS 的输入路径：

```text
microcom/minicom
  -> /dev/quard-freertos0
  -> Linux UART core xmit buffer
  -> quard_remote_console
  -> quard_mbox_router
  -> Linux IPI mailbox TX channel
  -> OpenSBI IPI
  -> FreeRTOS IPI mailbox
  -> FreeRTOS router consumer queue
  -> shell_rx_queue
  -> Letter Shell
```

FreeRTOS 到 Linux 的回显路径：

```text
Letter Shell / EasyLogger
  -> remote_shell_write()
  -> FreeRTOS mailbox TX channel
  -> OpenSBI IPI
  -> Linux IPI mailbox RX channel
  -> quard_mbox_router
  -> quard_remote_console_receive()
  -> Linux TTY flip buffer
  -> microcom/minicom
```

因此，“命令在 FreeRTOS 执行”和“Linux 终端正确换行显示”是两个不同的验证点。

## 3. 现象与根因对应关系

| 现象 | 判断 | 根因或处理位置 |
|---|---|---|
| 输入字符和命令能到 FreeRTOS，异步日志也能返回，但光标固定在一行 | 双向 mailbox 仍然工作 | Linux TTY 的 CR/LF 处理或终端程序显示状态 |
| 换用 `microcom` 后长期正常，只有 `minicom` 使用一段时间后显示异常 | 驱动数据流正常 | minicom curses 页面/光标状态问题 |
| Linux TX channel 长时间为 `DATA_READY`，出现 TX busy/timeout | ACK 通知链路停滞 | SSIP/IPI 竞态或通知丢失，需要状态轮询恢复 |
| FreeRTOS 日志持续显示 `[ISR]` | `irq_is_in_isr()` 状态错误 | `isr_nesting` 只减未加导致无符号下溢 |
| 调度器不断选中任务，但任务入口不执行 | SSIP 一直 pending | mailbox handler 覆盖了 FreeRTOS 标准 SSIP 清除 |

## 4. 根因分析

### 4.1 固定在一行不等于 mailbox 中断丢失

故障日志中可以看到：

- Linux 每个输入字符都完成了 TX submit 和 TX ACK。
- FreeRTOS 能执行 `hello` 并返回 `Hello, RISC-V Shell!`。
- Linux RX 消息数和字节数继续增加。
- Letter Shell prompt 仍持续返回。

这证明 Linux -> FreeRTOS 和 FreeRTOS -> Linux 两个方向都在工作。此时屏幕看起来不换行，不能再按 mailbox 完全阻塞的方向排查。

Remote Shell 每个 mailbox payload 只有 28 字节。FreeRTOS 输出的 `\r\n` 可能处于不同 payload 中，也可能有代码只输出 `\n`。Linux 驱动原来把收到的字节直接逐个送入 TTY flip buffer，终端处于透明/raw 模式时，单独的 LF 只下移光标，不一定回到第 0 列，最终表现为 prompt 和日志堆叠、错位或固定在同一列。

### 4.2 `isr_nesting` 错误只解释 `[ISR]`，不是所有回显故障的根因

`trusted_domain/it.c` 原来在 PLIC 中断结束时执行：

```c
isr_nesting--;
```

但入口没有对应的递增。`isr_nesting` 是无符号变量，第一次 PLIC 中断后会从 0 下溢为最大值：

```text
0 - 1 -> UINT_MAX
```

随后：

```c
bool irq_is_in_isr(void)
{
    return isr_nesting != 0;
}
```

会永久返回 true。EasyLogger 因此选择 ISR buffer、跳过任务态锁并把上下文显示为 `[ISR]`。

正式修复是在有效 PLIC claim 后成对维护计数：

```c
isr_nesting++;

/* 调用 IRQ handler，并完成 PLIC source。 */

plic_complete(irq);
isr_nesting--;
```

这个修改是必要的，它修复了全局 ISR 状态判断和日志上下文；但如果 Linux 已持续收到正确字节、仅终端不换行，则还必须处理 Linux TTY 的 CR/LF，不能只改 `isr_nesting`。

### 4.3 SSIP 清除竞态会造成真正的 mailbox 停滞

FreeRTOS 调度 IPI 和 AMP mailbox IPI 共用 SSIP。正式修复包含两部分：

1. FreeRTOS mailbox handler 在读取 AMP 消息位后仍执行标准 `sbi_clear_ipi()`。
2. OpenSBI 按“先清 SSIP，再原子取走 AMP 消息位”的顺序处理扩展 IPI。

FreeRTOS 侧还会再次读取一次 AMP bits，合并第一次读取和标准 SSIP 清除之间并发到达的消息：

```c
ret = sbi_clear_ipi_amp(&msg_type);
sbi_clear_ipi();
if (ret != 0)
    return;

if (sbi_clear_ipi_amp(&pending_type) == 0)
    msg_type |= pending_type;
```

否则可能出现共享内存已经是 `DATA_READY`，但对应 SSIP 被旧处理流程清掉，新消息没有下一次中断通知。

## 5. 正式修复

### 5.1 Linux RX：跨 mailbox payload 规范化 CR/LF

文件：

```text
bsp/ipi_mailbox/consumer/quard_remote_console.c
```

驱动使用 `rx_pending_cr` 保存 payload 末尾尚未配对的 CR：

- 收到 `\r`：暂存，不立即提交。
- 后续收到 `\n`：向 TTY 原子提交 `\r\n`。
- 单独收到 `\n`：同样提交 `\r\n`。
- `\r` 后面不是 `\n`：先提交原 CR，再提交当前字符。

这样无论 `\r\n` 是否被 28 字节 mailbox 边界拆开，Linux 用户态都能收到稳定的换行序列。

### 5.2 Linux TX：UART 回调只调度工作，不同步等待 mailbox

`uart_ops.start_tx()` 可能被 UART core 高频调用。不能在该回调中直接执行可能等待 ACK 的同步 mailbox 发送。

当前实现中，`remote_console_uart_start_tx()` 只调度 delayed work：

```c
mod_delayed_work(system_wq, &console->tx_work, 0);
```

worker 从 UART circular buffer 中按 28 字节切片发送：

```text
UART xmit buffer
  -> 最多 28 字节
  -> quard_mbox_send_msg()
  -> 成功后推进 xmit->tail
```

发送失败时不丢弃 xmit buffer 中的数据，也不推进 tail，而是在 10 ms 后重试。这样 mailbox 暂时 busy 不会直接丢失用户输入，也不会长时间阻塞 UART core 回调。

### 5.3 Linux mailbox：共享状态为准，IPI 只作为通知

共享 channel 状态机为：

```text
IDLE -> DATA_READY -> ACK -> IDLE
```

IPI 可能被合并或在竞态窗口中丢失，因此不能把一次 IPI 当作唯一事实来源。Linux provider 当前采用：

- `last_tx_done()` 每 2 ms 检查 TX ACK。
- recovery work 每 20 ms 检查共享状态。
- TX 停在 `DATA_READY` 时重新通知 FreeRTOS。
- RX 已进入 `ACK`、但对端可能未收到 ACK IPI 时重新通知 FreeRTOS。
- 新发送遇到 stale ACK 时先安全恢复为 `IDLE`。

正常收发路径不逐消息打印；只在 TX busy、stale ACK、SBI IPI 失败和 recovery kick 失败等关键异常路径打印 ratelimited 日志。

### 5.4 FreeRTOS router：避免重复调度和错误日志递归

FreeRTOS mailbox RX callback 在 SSIP trap 中运行。SSIP 汇编出口已经固定调用 `vTaskSwitchContext()`，所以 router callback 只执行：

```c
xQueueSendToBackFromISR(consumer->rx_queue, msg, NULL);
```

这里不再调用 `portYIELD_FROM_ISR()`，避免同一次 SSIP 中重复调度。

另外，Remote Shell 和 EasyLogger 本身也走 mailbox。底层 mailbox 发送失败时不能再通过同一 Remote Shell 链路执行 `LOG_E()`，否则会形成：

```text
mailbox 发送失败
  -> LOG_E
  -> remote_shell_write
  -> mailbox 再次发送失败
  -> 递归
```

底层发送函数只返回原始错误码，由不会复用同一链路的位置决定如何处理。

### 5.5 初始化顺序

`shell_rx_queue` 必须先创建，再注册 remote-shell mailbox consumer：

```c
shell_rx_queue = xQueueCreateStatic(...);
remote_shell_agent();
```

否则 mailbox consumer 注册完成后立即收到输入时，callback 可能访问尚未创建的队列。这个顺序修复是必要的防竞态措施，但它不能解释“运行固定次数后仅 Linux 屏幕不换行”的现象。

## 6. 终端程序选择

推荐使用透明字节桥 `microcom`：

```sh
microcom -s 115200 /dev/quard-freertos0
```

不要加 `-X`，因为 BusyBox `microcom -X` 会禁用 `Ctrl+X` 退出功能。也不建议在手工调试时加 `exec`，否则 microcom 退出后当前 shell 会一起结束。

退出：

```text
Ctrl+X
```

如果已使用 `-X` 启动，只能从另一个 shell 执行：

```sh
killall microcom
```

`minicom` 可用于普通串口操作，但本次测试中出现过运行一个终端页面后 curses 光标/滚动状态异常，而底层 mailbox 数据仍然正确的情况。判断方法是：同一镜像和驱动换成 `microcom` 后继续压力输入；若不再复现，则不是 mailbox 卡死。

在工程根目录执行：

```sh
make ampuboot_fit AMP_RTOS=freertos -j$(nproc)
```

```text
work/visionfive2_fw_payload_amp.img
```

### 7.2 编译 Linux mailbox 模块

```sh
./bsp/ipi_mailbox/build.sh build
```

模块会复制到：

```text
nfs_rootfs/
```

### 7.3 Linux 模块加载顺序

必须按 provider -> router -> consumer 的顺序加载：

```sh
insmod /mnt/starfive_ipi_mailbox.ko
insmod /mnt/quard_mbox_router.ko
insmod /mnt/quard_remote_console.ko
```

不要同时加载 `starfive_ipi_mailbox-test.ko`，测试模块会占用相同 mailbox channel。

确认设备节点：

```sh
ls -l /dev/quard-freertos0
```

## 8. 验证方法

### 8.1 基本验证

启动 `microcom` 后连续执行：

```text
hello
hello
hello
```

确认每次均满足：

- 输入字符立即回显。
- 回车后命令被 FreeRTOS 执行。
- `Hello, RISC-V Shell!` 正常返回。
- 新 prompt 从下一行第 0 列开始。

### 8.2 压力验证

至少连续输入 100 次，并穿插错误命令和异步日志。重点检查：

1. 不出现固定在一行、持续右移或异常空白页。
2. 不出现输入字符丢失或顺序改变。
3. 不出现持续 `[ISR]`。
4. 不出现 `ipi TX busy` 连续增长。
5. 不出现 `rshell TX failed` 持续重试。
6. 异步日志插入 prompt 时，后续输入和换行仍可恢复。

### 8.3 Linux 关键日志

```sh
dmesg -w | grep -E 'IPI mailbox|mailbox router|remote shell|ipi TX|stale TX ACK|recovery kick|rshell TX'
```

正常启动只应看到 provider、router 和 remote shell 的 ready 信息。正常逐字符收发不打印日志。

关键错误含义：

| 日志 | 含义 |
|---|---|
| `ipi TX busy: state=1` | 上一次 Linux -> FreeRTOS 数据仍为 `DATA_READY` |
| `ipi TX busy: state=2` | ACK 尚未被 Linux mailbox core 回收 |
| `ipi recovered stale TX ACK` | 超时请求后来完成，发送前已恢复旧 ACK |
| `ipi TX IPI failed` | 初次 SBI IPI 发送失败，驱动已回滚 channel 状态 |
| `ipi recovery kick failed` | 共享状态仍 pending，且重发 IPI 失败 |
| `rshell TX failed` | Linux TTY -> FreeRTOS 发送失败，xmit 数据保留并延迟重试 |

## 9. 快速判断流程

```text
输入后 FreeRTOS 是否执行命令？
  ├─ 是
  │   ├─ microcom 正常、minicom 异常 -> 终端显示问题
  │   └─ 两者都不换行 -> 检查 Linux CR/LF 规范化
  └─ 否
      ├─ Linux 报 rshell TX failed / ipi TX busy -> 检查 TX 状态和 ACK
      ├─ channel 停在 DATA_READY -> 检查 SSIP/IPI 和 recovery
      └─ FreeRTOS 普通任务均不运行 -> 检查标准 SSIP 清除

日志是否持续显示 [ISR]？
  ├─ 是 -> 检查 isr_nesting 是否成对递增/递减
  └─ 否 -> 按上述双向链路继续定位
```

## 10. 结论

本次 Remote Shell 回显故障由多个独立问题叠加：

1. `isr_nesting` 只减不加，导致系统永久误判为 ISR 上下文。
2. Linux TTY 未处理跨 mailbox payload 的 CR/LF，造成终端换行和光标错乱。
3. Linux UART `start_tx` 不能同步等待 mailbox，需通过 worker 切片发送并重试。
4. SSIP/IPI 清除竞态可能把 channel 留在 `DATA_READY`，需修复 OpenSBI 顺序并以共享状态轮询恢复。
5. minicom 自身的页面显示状态可能制造“链路卡死”的假象，应使用 microcom 交叉验证。

因此，判断 Remote Shell 是否真正卡死，必须同时检查命令是否在 FreeRTOS 执行、反向字节是否到达 Linux、mailbox 状态机是否完成以及终端程序是否正确显示，不能只根据屏幕布局下结论。
