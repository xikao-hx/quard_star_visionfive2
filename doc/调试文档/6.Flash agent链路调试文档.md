# Flash agent 链路调试记录

# U-Boot 通过 Mailbox 访问 Flash

## 问题一：执行 `mtd list` 触发 Store/AMO access fault

### 现象

U-Boot proper 中物理 QSPI 已按设计禁用，但第一次执行 `mtd list` 时发生异常并复位：

```text
StarFive # mtd list
Unhandled exception: Store/AMO access fault
EPC: 00000000f7f23ec2 RA: 00000000f7f23f84 TVAL: 0000000000000090
EPC: 000000004022cec2 RA: 000000004022cf84 reloc adjusted

Code: 6905 0b13 0204 6bd8 3783 1684 855a 54d1 (ebd8)

resetting ...
```

与此同时，FreeRTOS 输出：

```text
D/NOR_AGENT [00:00:06.220] cmd 0x0, offset 0x0, len 0xa20, addr 0x6e500000
```

其中 `cmd 0x0` 是 `NOR_GET_INFO`，`0xa20` 是
`sizeof(struct quard_nor_info)`，`0x6e500000` 是约定的共享内存地址。
这说明 U-Boot 到 FreeRTOS 的 mailbox 请求已经送达，故障发生在 U-Boot 收到
Flash 信息并注册 MTD 的阶段，而不是 QSPI 所有权或 mailbox 传输阶段。

### 排查过程

#### 1. 排除物理 QSPI 节点禁用问题

U-Boot proper 的设备树中：

```text
/soc/spi@13010000 status = "disabled"
```

该状态由 AMP Flash 所有权设计决定。FreeRTOS 已收到 `NOR_GET_INFO`，进一步证明
U-Boot 没有尝试通过已禁用的 QSPI 节点直接访问 Flash。

#### 2. 根据 EPC 定位异常函数

使用带符号的 U-Boot ELF 对重定位后的 EPC 做定位：

```bash
export RVROOT=$PWD/work/buildroot_initramfs/host
export CROSS_COMPILE=$RVROOT/bin/riscv64-buildroot-linux-gnu-

${CROSS_COMPILE}addr2line -e work/amp/u-boot/u-boot \
    -f -C 0x4022cec2 0x4022cf84
```

异常落在 `quard_nor_set_mtd_info()` 的 MTD/ofnode 初始化路径。

#### 3. 结合 `TVAL=0x90` 检查空指针写入

原初始化顺序为：

```c
mtd_set_ofnode(mtd, dev_ofnode(nor->dev));
mtd->dev = nor->dev;
```

在启用 Driver Model 时，`mtd_set_ofnode()` 最终执行：

```c
dev_set_ofnode(mtd->dev, node);
```

此时 `mtd->dev` 尚未赋值，仍然是空指针。`dev_set_ofnode()` 尝试写入
`struct udevice` 的 `node_` 成员，因此形成“空指针基址 + 成员偏移”的写访问；
异常地址 `TVAL=0x90` 正好符合这一特征。

### 根因

`quard_nor_set_mtd_info()` 的初始化顺序错误：在设置 `mtd->dev` 前调用了
依赖该指针的 `mtd_set_ofnode()`。FreeRTOS 返回的 NOR 信息和 mailbox 响应均正常，
但 U-Boot 在注册 MTD master 前发生了空指针写入。

### 修复

先设置 MTD 对应的 `udevice`，再设置其设备树节点：

```c
static int quard_nor_set_mtd_info(struct quard_nor_client_dev *nor)
{
    struct mtd_info *mtd = &nor->mtd;

    mtd->dev = nor->dev;
    mtd_set_ofnode(mtd, dev_ofnode(nor->dev));
    /* 初始化其余 MTD geometry 和 operation callback。 */
}
```

对应代码：

```text
u-boot/drivers/mtd/quard_nor_client.c
```

### 板端验证

修复后重新执行：

```text
fdt addr ${fdtcontroladdr}
fdt print /soc/spi@13010000 status
mtd list
```

预期结果：

- 物理 QSPI 仍为 `disabled`；
- FreeRTOS 收到一次 `NOR_GET_INFO`；
- U-Boot 不再出现 Store/AMO access fault；
- `mtd list` 至少能打印 `quard-nor` master。

## 问题二：MTD master 存在，但按 GPT 分区名访问返回 `-19`

### 现象

修复 `mtd list` 崩溃后，`quard-nor` master 已能注册，但按 FreeRTOS 返回的 GPT
分区名执行命令失败：

```text
Bytes transferred = 5538629 (548345 hex)
StarFive # mtd erase fw_payload_a 0x0 0x600000
MTD device fw_payload_a not found, ret -19

StarFive # mtd read spl_a 0xa1000000 0x0 0x40000
MTD device spl_a not found, ret -19
```

`-19` 是 `-ENODEV`。该错误发生在 U-Boot 根据名字查找 MTD 时，请求尚未进入
mailbox，因此不是 FreeRTOS 拒绝读写，也不是 SPI NOR 擦写失败。

### 动态分区注册机制

`quard_nor_client` probe 的正常顺序为：

```text
NOR_GET_INFO
    -> 填充 quard-nor master 的容量和 geometry
    -> add_mtd_device(&nor->mtd)
    -> 将 FreeRTOS 返回的六个分区转换为 mtd_partition
    -> add_mtd_partitions(...)
```

六个分区的名称、offset 和 size 来自 FreeRTOS 已校验的 GPT 视图。U-Boot client
不再维护另一套分区语义验证，也不应通过设备树或默认环境复制一份静态分区表。

### 排查过程

#### 1. 确认不是 FreeRTOS 没有返回分区

`quard_nor_client` probe 成功，且 `NOR_GET_INFO` 返回结构包含六个分区。驱动中的
`add_mtd_partitions()` 也返回成功，但最终 `mtd list` 只打印 master，说明分区是在
probe 完成后被移除的。

#### 2. 检查 `mtd list` 的二次 probe 行为

U-Boot 的 `mtd list/read/write/erase` 在按名称操作前都会调用：

```c
mtd_probe_devices();
```

`mtd_probe_devices()` 不只 probe MTD uclass，还会检查 `mtdids` 和 `mtdparts` 是否
变化。检测到变化时，它会先执行：

```c
mtd_del_all_parts();
```

然后尝试根据环境变量或设备树重新创建分区。

#### 3. 检查生成配置中的默认值

当前配置为：

```text
CONFIG_MTDIDS_DEFAULT=""
CONFIG_MTDPARTS_DEFAULT=""
```

原 `get_mtdids()` 和 `get_mtdparts()` 只判断指针是否为 `NULL`，没有判断字符串
是否为空。因此 `""` 被当作有效配置返回：

```text
driver probe 动态注册六分区
    -> mtd_probe_devices() 将空字符串误判为有效/变化配置
    -> mtd_del_all_parts() 删除六个动态分区
    -> 空 mtdparts 无法重新创建任何分区
    -> 设备树没有重复的 fixed-partitions
    -> 最终只剩 quard-nor master
```

这解释了为什么 master 可以访问，而 `spl_a`、`fw_payload_a` 等名字全部返回
`-ENODEV`。

### 根因

U-Boot MTD 公共层混淆了“没有 `mtdids/mtdparts` 配置”和“配置值为空字符串”两种
状态。空默认字符串错误触发了动态分区清理，而后续又没有任何有效静态分区表可以
回补。

问题不在 mailbox channel，也不在 FreeRTOS GPT parser；FreeRTOS 返回的分区已经
被 client 正确注册，只是在随后的 U-Boot MTD 公共流程中被删除。

### 修复

在 `get_mtdids()` 和 `get_mtdparts()` 中同时检查指针和首字符，将空字符串规范化为
`NULL`：

```c
if (mtdids && *mtdids)
    return mtdids;
/* fallback 后仍为空时： */
mtdids = NULL;

if (mtdparts && *mtdparts)
    return mtdparts;
/* fallback 后仍为空时： */
mtdparts = NULL;
```

对应代码：

```text
u-boot/drivers/mtd/mtd_uboot.c
```

修复后，`mtd_probe_devices()` 能识别“没有外部静态分区配置”，直接保留
`quard_nor_client` 从 FreeRTOS info 动态注册的六个分区。

这里不采用以下方案：

- 不在 U-Boot DTS 中重复六个 `fixed-partitions`；
- 不在默认环境中硬编码一份 `mtdparts=`；
- 不在 U-Boot client 中重新验证 canonical 六分区布局。

这些方案都会引入第二份分区事实源。当前职责仍是 FreeRTOS 校验 GPT 并发布分区，
U-Boot 只完成 MTD/RPC 转换。

### 构建和部署

修改 U-Boot 或 FreeRTOS 后执行完整 AMP 构建：

```bash
make ampfit AMP_RTOS=freertos -j$(nproc)
```

本问题只需要更新包含 U-Boot proper 和 FreeRTOS 的 payload，不需要重复更新已经工作
的 SPL。复制最新产物到 TFTP 目录并核对哈希：

```bash
sudo cp work/visionfive2_fw_payload_amp.img /srv/tftp/
sha256sum \
    work/visionfive2_fw_payload_amp.img \
    /srv/tftp/visionfive2_fw_payload_amp.img
```

旧 U-Boot 若只能看到 `quard-nor` master，可用绝对 offset 更新 payload：

```text
tftpboot 0xa0000000 visionfive2_fw_payload_amp.img
setenv payload_size $filesize
printenv filesize payload_size

mtd erase quard-nor 0x100000 0x600000
mtd write quard-nor 0xa0000000 0x100000 $payload_size

mtd read quard-nor 0xa1000000 0x100000 $payload_size
cmp.b 0xa0000000 0xa1000000 $payload_size
reset
```

`payload_size` 必须在成功执行 `tftpboot` 后保存。如果变量为空，`mtd write` 会使用
整个 MTD 的默认长度，打印 `Writing 16777216 byte(s)`，并因访问越界返回 `-22`。

### 板端验证

修复后的 `mtd list` 应保留 FreeRTOS 返回的全部分区：

```text
StarFive # mtd list
List of MTD devices:

* quard-nor
  - type: NOR flash
  - block size: 0x1000 bytes
  - min I/O: 0x1 bytes
  - 0x000000000000-0x000001000000 : "quard-nor"
    - 0x000000000000-0x000000040000 : "spl_a"
    - 0x000000040000-0x000000080000 : "spl_b"
    - 0x000000080000-0x0000000c0000 : "gpt"
    - 0x0000000c0000-0x000000100000 : "recovery"
    - 0x000000100000-0x000000700000 : "fw_payload_a"
    - 0x000000700000-0x000000d00000 : "fw_payload_b"
```

按名称执行只读验证：

```text
mtd read spl_a 0xa1000000 0x0 0x40000
mtd read gpt 0xa1040000 0x0 0x40000
nor_gpt 0xa1040000 0x40000
```

更新 payload 时使用分区相对 offset：

```text
tftpboot 0xa0000000 visionfive2_fw_payload_amp.img
setenv payload_size $filesize
printenv payload_size

mtd erase fw_payload_a 0x0 0x600000
mtd write fw_payload_a 0xa0000000 0x0 $payload_size
mtd read fw_payload_a 0xa1000000 0x0 $payload_size
cmp.b 0xa0000000 0xa1000000 $payload_size
```

### 结果解释

- FreeRTOS 有 `NOR_GET_INFO`，U-Boot 随即崩溃：优先检查 U-Boot MTD 对象初始化和
  EPC 对应的空指针访问。
- `mtd list` 有 master、没有子分区：检查 `mtd_probe_devices()` 是否清除了驱动
  动态注册的分区，以及 `mtdids/mtdparts` 是否为空字符串。
- 按分区名立即返回 `-19`：请求尚未进入 mailbox，先检查 U-Boot MTD 名称注册。
- 已进入 `NOR_WRITE/NOR_ERASE` 但 FreeRTOS 返回失败：再检查 destructive range、
  erase 对齐、共享内存范围和 checksum。
- `mtd write` 显示 16 MiB 而不是实际镜像大小：`$filesize` 或保存的 size 变量为空。

## 调试原则总结

1. 物理 QSPI 为 `disabled` 是 U-Boot proper 的设计结果，不能据此判断 mailbox Flash
   不可用。
2. FreeRTOS 收到 `NOR_GET_INFO` 只能证明请求链路和共享内存参数正常，不能证明
   U-Boot 后续 MTD 对象注册正确。
3. `TVAL` 接近零地址时应结合结构体成员偏移排查空指针，不能只看 FreeRTOS 日志。
4. MTD master 注册成功不代表动态分区会一直保留；必须检查 `mtd_probe_devices()`
   的删除和重建流程。
5. GPT 分区视图由 FreeRTOS 负责校验和发布，U-Boot DTS、默认环境和 client 不应
   再复制一份静态分区事实源。
6. `-ENODEV` 表示名称解析阶段失败，请求尚未进入 mailbox；`-EINVAL` 则应结合
   offset、size 和变量展开结果继续判断。
7. 使用 `$filesize` 前必须确认刚刚成功执行过 `tftpboot`，并用 `printenv` 检查保存
   的长度，避免缺少 size 参数时误用整个 MTD 默认长度。
8. 更新启动链时先验证 payload，最后才更新 `spl_a`；写后必须回读并比较。
