# VisionFive2 SPL、OpenSBI、U-Boot 与 FreeRTOS 日志落盘调试记录

## 总结

本文记录 2026-08-20 在 VisionFive2 AMP 启动日志和 FreeRTOS 动态日志落盘过程中遇到的两个问题：

1. 增加 SPL 日志采集后，SPL 无串口输出、系统无法继续启动。
2. Linux 可以生成 `linux_boot_log.log`，但没有 FreeRTOS 对应的 `mcu_log.log`。

两个问题均不是 Linux 文件写入接口导致：

- SPL 故障来自 JH7110 SPL 的 `.bss` 清零时序，早期日志状态在首次使用时尚未初始化。
- FreeRTOS 日志缺失来自 MCU 共享日志控制块未初始化，定时 flush 可能被 DDR 随机值或热复位残留状态永久阻塞。

最终数据链路如下：

```text
SPL/OpenSBI/U-Boot UART 输出
        -> 各阶段 ramlog 保留内存
        -> Linux quard_log.ko 快照
        -> soc_logd
        -> /opt/soc_log/linux_boot_log.log

FreeRTOS EasyLogger
        -> FreeRTOS 本地 master_buf
        -> 0x6e404000 MCU 共享日志区
        -> Linux quard_log.ko 轮询并快照
        -> netlink 通知 soc_logd
        -> /opt/soc_log/mcu_log.log
```

# 问题一：增加日志采集后 SPL 无法启动

## 现象

将 ramlog 写入接入 `u-boot/drivers/serial/ns16550.c` 后，烧写新 SPL，串口看不到 SPL banner，后续 OpenSBI、U-Boot 和 Linux 也不会启动。

单纯检查编译结果无法发现该问题：SPL、OpenSBI、U-Boot 均可以通过编译和链接，最终镜像也能正常打包。

## 初始设计

SPL 在 DDR 初始化前已经调用 `preloader_console_init()`。为了保留这部分早期串口输出，最初增加了一个本地环形缓冲区：

```c
static char ramlog_early_buffer[SPL_RAMLOG_SIZE];
static u32 ramlog_early_head;
static u32 ramlog_early_tail;
static bool ramlog_ddr_ready;
```

DDR 初始化完成后，再由 `ns16550_ramlog_ddr_ready()` 将暂存字符迁移到 `0x6e408000` 的 SPL 日志区。

## 排查过程

### 1. 检查 SPL 大小和内存范围

SPL 大小没有超过 `CONFIG_SPL_MAX_SIZE`，早期缓冲所在的 L2 LIM 地址也属于平台可访问范围。因此问题不是 SPL 文件过大，也不是地址超出 L2 LIM。

### 2. 检查链接符号

故障镜像中的符号位置为：

```text
0x08040000  __bss_start
0x080406c4  ramlog_ddr_ready
0x080406c8  ramlog_early_tail
0x080406cc  ramlog_early_head
0x080406d0  ramlog_early_buffer
0x08040ac0  __bss_end
```

这说明早期日志缓冲及其状态全部位于 `.bss`。

### 3. 检查 JH7110 SPL 初始化顺序

RISC-V SPL 入口的实际顺序是：

```text
start.S
  -> board_init_f()
       -> preloader_console_init()
       -> spl_board_init_f()
            -> spl_soc_init()
                 -> DDR 初始化
  -> board_init_f() 返回
  -> spl_clear_bss
```

也就是说，第一次 SPL 串口输出发生在通用 `spl_clear_bss` 之前。

串口字符实际写出后会立即进入 `ramlog_append_early()`。此时 `ramlog_early_head`、`ramlog_early_tail` 和 `ramlog_ddr_ready` 仍是未初始化值，随机索引可能导致越界写入，SPL 因而在最早期阶段异常停止。

## 根因

错误地假设 `.bss` 在 `board_init_f()` 之前已经清零。

对于当前 JH7110 SPL，任何在 `preloader_console_init()` 阶段使用的状态都不能依赖普通 `.bss` 初始化。

## 修复

将所有 DDR 初始化前使用的日志状态显式放入 SPL 镜像的 `.data` 段：

```c
static char ramlog_early_buffer[SPL_RAMLOG_SIZE] __section(".data");
static u32 ramlog_early_head __section(".data");
static u32 ramlog_early_tail __section(".data");
static bool ramlog_ddr_ready __section(".data");
```

修复后链接位置变为：

```text
0x08022928  ramlog_ddr_ready
0x0802292c  ramlog_early_tail
0x08022930  ramlog_early_head
0x08022938  ramlog_early_buffer
```

`.data` 属于 SPL 可加载镜像，BootROM 加载 SPL 时会同时加载这些初始值。`board_init_f()` 返回后的 `.bss` 清零也不会再次破坏 `ramlog_ddr_ready` 状态。

对应代码：

```text
u-boot/drivers/serial/ns16550.c
u-boot/arch/riscv/cpu/jh7110/spl.c
```

## 验证

### 静态检查

```bash
riscv64-linux-gnu-readelf -S work/amp/u-boot/spl/u-boot-spl
riscv64-linux-gnu-nm -S work/amp/u-boot/spl/u-boot-spl | \
    grep -E 'ramlog_(early|ddr_ready)|__bss_(start|end)'
```

验收要求：早期缓冲和三个状态变量的符号类型为 `d/D`，不能再是 `b/B`。

### 构建和板端验证

```bash
make ampfit AMP_RTOS=freertos -j$(nproc)
```

烧写新 SPL 后，串口重新出现：

```text
U-Boot SPL 2021.10 (...)
LPDDR4: 8G ...
Trying to boot from SPI
```

在 U-Boot 中检查 SPL 日志头：

```text
md.l 0x6e408000 4
```

首字应为 ramlog magic `0x52414d4c`，size 应为 `0x3f0`。

# 问题二：Linux 启动日志正常，但没有 FreeRTOS 日志文件

## 现象

Linux 侧日志模块和 `soc_logd` 启动成功，并生成：

```text
/opt/soc_log/linux_boot_log.log
```

文件中可以看到 SPL、OpenSBI、U-Boot 分段，说明以下链路已经正常：

```text
保留内存 -> quard_log.ko -> mmap -> soc_logd -> 文件
```

但目录中没有：

```text
/opt/soc_log/mcu_log.log
```

需要注意，`linux_boot_log.log` 成功只能证明启动日志链路正常，不能证明 FreeRTOS 动态日志状态机正常。两者使用不同的内存格式和触发机制。

## FreeRTOS 日志触发机制

FreeRTOS 的 EasyLogger 输出先进入本地 `master_buf`。1 秒定时器唤醒 `log_flush_task` 后，只有共享区状态为 `SLAVE_BUFFER_EMPTY`，才会把日志复制到 `0x6e404000`，随后将状态发布为 `SLAVE_BUFFER_FULL`。

Linux `soc_klogd` 每 100 ms 检查该状态：

```text
state == FULL
  -> 复制共享区到内核普通页
  -> 将共享区状态改回 EMPTY
  -> 通过 netlink 通知 soc_logd
  -> soc_logd 生成或追加 mcu_log.log
```

## 排查过程

### 1. 确认 EasyLogger 已接入共享后端

FreeRTOS 初始化顺序为：

```text
log_rb_backend_init()
elog_init()
elog_start()
init_quard_mbox_router()
soc_log_agent()
LOG_I("Hello FreeRTOS ...")
vTaskStartScheduler()
```

`elog_port_output_task()` 最终会调用 `log_rb_backend_output()`，因此 EasyLogger 到本地 `master_buf` 的路径存在。

### 2. 检查定时 flush 条件

原实现的 `log_rb_backend_init()` 只初始化了本地 `master_buf`：

```c
mst_cb = (slave_buffer_cb *)&master_buf[0];
quard_ringbuffer_init(&mst_cb->rb_ctrl, ...);
```

它没有初始化 `LOG_BUF_BASE` 指向的 `0x6e404000` 共享控制块。

定时任务则依赖：

```c
if (!log_flush_enable &&
    LOG_BUF_BASE->buffer_state == SLAVE_BUFFER_EMPTY)
    log_flush_enable = true;

if (!log_flush_enable)
    continue;
```

如果 DDR 上电内容是随机值，或者热复位后保留了上次的 `FULL` 状态，`log_flush_enable` 将一直为 `false`，定时任务永久跳过 flush。Linux 看不到 `FULL`，所以不会发送 netlink 事件，也不会创建 `mcu_log.log`。

## 根因

FreeRTOS 是 MCU 共享日志区的生产端，但没有在 Linux 启动前初始化共享控制块，错误地依赖了 DDR 初值或上一次启动留下的状态。

## 修复

在 `log_rb_backend_init()` 中同时初始化本地缓冲和共享缓冲：

```c
memset((void *)LOG_BUF_BASE, 0, MCU_LOG_BUF_SIZE);
LOG_BUF_BASE->head_magic = MAGIC_PATTERN;
LOG_BUF_BASE->middle_magic = MAGIC_PATTERN;
quard_ringbuffer_init(&LOG_BUF_BASE->rb_ctrl,
                      (uint8_t *)&LOG_BUF_BASE->buffer_first_byte,
                      RB_SIZE);
__asm volatile ("fence rw, rw" ::: "memory");
```

该初始化发生在 FreeRTOS 启动阶段，此时 Linux 尚未运行，因此不会与 Linux 消费端竞争。初始化后第一个定时周期即可把启动日志发布到共享区。

对应代码：

```text
trusted_domain/driver/log_backend/buffer_be_mcu.c
```

## 构建和部署

修改 FreeRTOS 后必须执行完整 AMP 构建，确保 `trusted_fw.bin` 被重新追加到 U-Boot payload：

```bash
make ampfit AMP_RTOS=freertos -j$(nproc)

cmp work/amp/trusted_domain/trusted_fw.bin \
    work/amp/amp_rtos.bin
```

本问题的修复位于 FreeRTOS 固件，只更新以下 payload 即可验证，不需要重复烧写已经工作的 SPL：

```bash
sudo cp work/visionfive2_fw_payload_amp.img /srv/tftp/
```

U-Boot 中执行：

```text
tftpboot 0xa0000000 visionfive2_fw_payload_amp.img
sf update 0xa0000000 0x100000 $filesize
reset
```

## 板端验证

Linux 启动后加载日志模块并启动守护进程：

```bash
/mnt/install.sh
sleep 2

ls -l /dev/log_device
ps | grep '[s]oc_logd'
ls -l /opt/soc_log/mcu_log.log
cat /opt/soc_log/mcu_log.log
```

预期无需手动触发，在 FreeRTOS 定时器第一次 flush 后自动出现 `mcu_log.log`。

如果文件仍未生成，可使用手动 flush 对链路分层定位：

```bash
echo flush > /sys/kernel/soc_log/mcu_log
sleep 1
dmesg | tail -n 30
ls -l /opt/soc_log/mcu_log.log
```

结果解释：

- 手动 flush 后生成文件：共享区和 Linux 落盘链路正常，应继续检查 FreeRTOS 定时任务。
- 内核出现 `Handling flush for mcu_log`，但 FreeRTOS 未打印收到命令：检查 mailbox router 和 LOG consumer。
- FreeRTOS 已收到命令并完成 flush，但 Linux 看不到 `FULL`：检查共享 DDR 的 cache 一致性和内存映射属性。
- Linux 已发送 netlink 事件但没有文件：检查 `soc_logd` 进程、配置目录和 `/var/log/soc_logd.log`。

# 调试原则总结

1. 编译成功不代表 SPL 早期运行时状态已经初始化，必须结合入口汇编确认 `.data/.bss` 时序。
2. 启动日志和 FreeRTOS 动态日志是两条不同链路，不能用 `linux_boot_log.log` 推断 MCU 日志正常。
3. 共享内存协议必须明确初始化责任方。当前 MCU 日志区由 FreeRTOS 在 Linux 启动前初始化。
4. 状态发布必须遵守“先写 payload 和元数据，最后发布 FULL”的顺序。
5. 修改 FreeRTOS 后必须确认 `trusted_fw.bin` 已进入 `visionfive2_fw_payload_amp.img`，不能只重新打包 Linux `image.fit`。
6. 部署前后应比较时间戳和 SHA-256，避免继续运行 TFTP 目录中的旧镜像。
