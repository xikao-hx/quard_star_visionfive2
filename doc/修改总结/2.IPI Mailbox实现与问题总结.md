# IPI Mailbox 实现与问题总结

## 1. 文档目的

本文总结 VisionFive 2 AMP 项目中 IPI Mailbox 的实现方式，以及开发、联调过程中
遇到的主要问题、问题原因和最终处理方法。

与按 SPL、OpenSBI、U-Boot 分类的修改说明不同，本文以一条消息从发送到响应的过程
为主线，重点回答：

- IPI Mailbox 如何传输数据；
- OpenSBI 在通信中承担什么职责；
- channel、state 和 service ID 如何配合；
- 为什么 Mailbox IPI 会影响 FreeRTOS 调度；
- 为什么单次收发成功仍不能证明链路可靠；
- 已经遇到过哪些故障，以及如何修复。

## 2. 为什么使用 IPI Mailbox

项目最初尝试使用 JH7110 的硬件 Mailbox 外设，但实际联调时只能稳定完成
Linux 向 FreeRTOS 的单向通信，FreeRTOS 返回 Linux 时无法可靠触发接收中断。
硬件 Mailbox 的中断号、通道方向和厂商驱动行为难以形成稳定闭环。

最终实现改为：

```text
共享内存负责保存消息
OpenSBI IPI 负责通知目标 hart
Router 负责按 service ID 分发业务
```

这种实现将通信拆成三个相互独立的部分：

| 层次 | 职责 |
| --- | --- |
| 共享内存 | 保存 payload 和通道状态 |
| OpenSBI IPI | 设置目标 hart 的 pending bit，并产生 SSIP |
| Mailbox Router | 区分日志、vshell、NOR 等业务服务 |

OpenSBI 不解析业务 payload，Router 不直接控制 hart 中断，业务 consumer 也不直接
操作共享内存。

## 3. 整体架构

生产链路如下：

```text
Linux 或 U-Boot proper
        |
        v
quard_mbox_router
        |
        v
IPI mailbox controller
        |
        | 共享内存 + SBI AMP IPI
        v
OpenSBI
        |
        | SSIP 通知 hart4
        v
FreeRTOS IPI mailbox handler
        |
        v
FreeRTOS mailbox router task
        |
        +-- service 0：日志
        +-- service 1：vshell
        +-- service 2：NOR agent
```

Linux 与 U-Boot proper 不会同时运行，但两者使用相同的协议访问 hart4 上的
FreeRTOS 服务。

当前依赖方向必须保持为：

```text
Linux/U-Boot consumer -> Router -> IPI Mailbox
                                      |
                              共享内存 + SBI IPI
                                      |
FreeRTOS service <- Router task <- IPI Mailbox handler
```

## 4. 共享内存协议

### 4.1 地址和通道

IPI Mailbox 共享内存起始地址为：

```text
0x6E402000
```

协议包含两个 32 字节通道：

| 通道 | 方向 | 用途 |
| --- | --- | --- |
| channel 1 | Linux/U-Boot -> FreeRTOS | 请求 |
| channel 0 | FreeRTOS -> Linux/U-Boot | 响应或反向消息 |

每个通道格式为：

```text
offset +0x00 : payload[28]
offset +0x1C : state[4]
```

两个通道实际占用前 64 字节。设备树保留更大的 Mailbox 区域，是为了固定 AMP
共享内存边界，而不是表示每条消息可以使用全部 reserved-memory。

### 4.2 通道状态机

每个通道使用以下状态：

```text
IDLE(0) -> DATA_READY(1) -> ACK(2) -> IDLE(0)
```

状态含义如下：

| 状态 | 含义 |
| --- | --- |
| `IDLE` | 通道空闲，可以发送新消息 |
| `DATA_READY` | payload 已写完，等待对端处理 |
| `ACK` | 对端已经复制或处理该消息 |

如果发送端发现通道不是 `IDLE`，必须返回 `-EBUSY`，不能覆盖上一条尚未完成的消息。

### 4.3 为什么必须使用内存屏障

发送端的正确顺序是：

```text
写 payload
  -> fence rw, rw
  -> 写 DATA_READY
  -> fence rw, rw
  -> 发送 IPI
```

如果没有内存屏障，另一个 hart 可能先观察到 `DATA_READY`，却仍然读到缓存或乱序
导致的旧 payload。

接收端在读取 state、复制 payload 和更新 ACK 时也必须保持相同的可见性约束。

## 5. OpenSBI IPI 通知实现

### 5.1 AMP IPI ecall

当前 OpenSBI 在标准 SBI IPI extension 下增加三个 function ID：

| function ID | 作用 |
| --- | --- |
| `0x100` | 给指定 hart 设置 AMP 消息位并发送 IPI |
| `0x101` | 注册 per-hart AMP pending bitmap 地址 |
| `0x102` | 清除 SSIP 并原子取出当前 hart 的 AMP 消息位 |

相关实现：

- [sbi_ecall_interface.h](../../opensbi/include/sbi/sbi_ecall_interface.h)
- [sbi_ecall_ipi.c](../../opensbi/lib/sbi/sbi_ecall_ipi.c)
- [sbi_ipi.c](../../opensbi/lib/sbi/sbi_ipi.c)

### 5.2 发送消息类型

调用：

```c
sbi_send_ipi_amp(4, 1);
```

表示向 hart4 发送类型编号 `1`。OpenSBI 设置的是 pending bitmap 中的 bit1：

```text
1UL << 1 = 0x2
```

因此发送参数 `1` 与接收方看到的 bitmap `0x2` 都是正确的：前者是 bit 编号，后者
是置位后的位图。

### 5.3 AMP bit 与 payload 的区别

OpenSBI pending bitmap 只表示“哪个类型的通知到达”，不保存 28 字节业务消息。

```text
AMP bit       -> 告诉目标 hart 应检查哪个通道
共享内存      -> 保存实际 payload 和 state
Router header -> 保存 service ID
```

所以看到目标 hart 进入 SSIP，只能证明通知到达，不能证明 payload、ACK 和 Router
分发均正确。

## 6. Router 实现

物理 IPI Mailbox 只有一组双向通道，但项目需要多种业务，因此在其上增加 Router。

当前 service ID 为：

| service ID | 服务 |
| --- | --- |
| `0` | 日志 |
| `1` | vshell |
| `2` | NOR agent |

发送时：

```text
consumer 构造消息
  -> Router 写入 service ID
  -> IPI Mailbox 发送固定 28 字节 payload
```

接收时：

```text
IPI Mailbox 复制消息
  -> 唤醒 Router task
  -> Router 读取 service ID
  -> 找到对应 consumer
  -> 在任务上下文处理
```

同一个 service ID 只能由一个 consumer 注册。否则无法确定响应属于哪个调用者。

## 7. 一次请求和响应的完整过程

以 Linux/U-Boot 向 FreeRTOS NOR agent 发送请求为例：

1. NOR client 构造 service `2` 的请求。
2. Router 在消息头中写入 service ID。
3. 发送端检查 channel 1 是否为 `IDLE`。
4. 将 28 字节请求复制到 channel 1 payload。
5. 执行内存屏障，将 channel 1 state 设置为 `DATA_READY`。
6. 通过 OpenSBI `0x100` 给 hart4 设置对应 AMP bit 并发送 IPI。
7. hart4 收到 SSIP，FreeRTOS handler 清除并读取 AMP bits。
8. FreeRTOS Mailbox handler 从 channel 1 复制消息，并设置 ACK。
9. handler 只唤醒 Router task，不在中断上下文访问 SPI NOR。
10. Router task 根据 service `2` 将请求交给 NOR agent。
11. NOR agent 完成请求，通过 channel 0 写入响应并通知 Linux/U-Boot。
12. Linux/U-Boot 从 channel 0 复制响应并设置 ACK。
13. 双方分别把完成的通道从 `ACK` 恢复为 `IDLE`。

对于 NOR 大块读写，28 字节消息只传控制参数，实际数据通过 `0x6E500000` 的 2 MiB
共享区传输。

## 8. 实施过程中遇到的问题

### 8.1 硬件 Mailbox 无法稳定完成双向中断

#### 现象

- Linux 发送后 FreeRTOS 可以收到；
- FreeRTOS 回复后 Linux 收不到接收中断；
- 无法确定厂商 Mailbox 通道对应的完整双向 IRQ关系。

#### 原因与处理

硬件 Mailbox 外设和厂商驱动没有形成可靠的双向闭环，因此改为共享内存保存数据，
使用 OpenSBI IPI 负责跨 hart 通知。

### 8.2 FreeRTOS 调度 IPI 与 Mailbox IPI 共用 SSIP

#### 现象

接入 Mailbox 后，FreeRTOS 可能在任务切换时连续进入 SSIP，新任务尚未执行第一条
有效指令就再次陷入中断，严重时出现中断风暴或上下文异常。

#### 根因

FreeRTOS 的 `portYIELD()` 本身使用 SSIP。早期 Mailbox handler 只调用：

```c
sbi_clear_ipi_amp(&msg_type);
```

却没有保留 FreeRTOS 原有的：

```c
sbi_clear_ipi();
```

AMP clear 只读取 Mailbox 消息位，不能替代调度器要求的标准 SSIP 清除。

#### 修复

同时执行 AMP clear 和标准 clear，并根据 AMP bit 决定是否处理 Mailbox：

```text
sbi_clear_ipi_amp()
  -> sbi_clear_ipi()
  -> 处理 Mailbox pending bits
```

### 8.3 OpenSBI 先取 bit、后清 SSIP 导致丢通知

#### 现象

- 发送端 SBI 调用返回成功；
- 共享内存已经是 `DATA_READY`；
- 目标 hart 没有再次进入 SSIP；
- 发送端最终 timeout。

#### 根因

早期 OpenSBI 顺序是：

```text
读取并清空 AMP bit
  -> 清除 SSIP
```

如果新消息恰好在两步之间到达，新消息会设置 AMP bit 和 SSIP，但旧处理流程随后又
清除 SSIP，造成“消息位存在、通知却消失”。

#### 修复

提交 `75fb1ab56` 将顺序改为：

```text
先清除当前 SSIP
  -> 再 atomic_raw_xchg_ulong() 取走 AMP bits
```

这样新消息要么被本次原子交换取走，要么留下新的 SSIP 供下一次 trap 处理。

### 8.4 AMP clear 与标准 clear 之间仍有竞态窗口

#### 现象

第一轮修复后，大部分请求正常，但连续压力通信中仍可能偶发消息位没有被处理。

#### 根因

新 Mailbox IPI 可能在第一次 AMP clear 与标准 `sbi_clear_ipi()` 之间到达。

#### 修复

FreeRTOS 当前采用双重读取：

```c
sbi_clear_ipi_amp(&msg_type);
sbi_clear_ipi();
if (sbi_clear_ipi_amp(&pending_type) == 0)
    msg_type |= pending_type;
```

第二次 AMP clear 接收竞态窗口中的新消息，并与第一次结果合并。

### 8.5 中断嵌套计数只减不加

#### 现象

ISR 上下文判断和中断退出后的任务切换状态异常。

#### 根因

FreeRTOS trap 路径中的 `isr_nesting` 在退出时递减，但进入中断时没有对应递增。

#### 修复

提交 `ceed7f412` 恢复进入/退出中断时的对称计数，保证 FromISR API 和调度判断使用
正确的 ISR nesting 状态。

### 8.6 Mailbox ISR 重复请求任务切换

#### 现象

Mailbox 回调唤醒 Router task 后，又在同一 SSIP 路径中调用
`portYIELD_FROM_ISR()`，可能造成重复调度、ACK 时序异常或连续重入。

#### 根因

当前 RISC-V FreeRTOS SSIP trap 出口已经会选择最高优先级 ready task。Mailbox ISR
再次请求 yield 等于在同一个中断出口重复执行调度语义。

#### 修复

Mailbox SSIP 路径只唤醒任务，由统一 trap 出口完成任务切换。

需要注意，UART PLIC 中断的出口路径不同，仍可能需要 `portYIELD_FROM_ISR()`；两条
路径不能机械地采用同一种处理方式。

### 8.7 中断上下文执行过多工作

#### 风险

如果在 SSIP handler 中打印日志、阻塞等待、执行 Router 服务或访问 SPI NOR，会：

- 延长中断关闭时间；
- 阻塞其他任务和中断；
- 造成 Mailbox 递归；
- 增加 ACK timeout 和死锁风险。

#### 最终边界

```text
ISR/trap：
  清中断
  复制消息
  更新 ACK
  唤醒任务

任务上下文：
  Router 分发
  日志/vshell 处理
  SPI NOR 读写擦除
```

### 8.8 Mailbox 错误路径递归打印日志

#### 现象

底层发送失败后使用 `LOG_E()`，而日志后端本身也通过 Mailbox 发送，最终形成递归：

```text
Mailbox 发送失败
  -> LOG_E
  -> Mailbox 日志后端再次发送
  -> 再次失败
  -> 递归
```

#### 修复

底层 Mailbox 和 Router 发送函数只返回原始错误码，不再通过同一条 Mailbox 日志链路
打印错误。需要定位时使用不会回到该链路的轮询 UART，且调试完成后删除临时打印。

### 8.9 ACK 没有恢复导致 `-EBUSY`

#### 现象

第一次收发成功，第二次发送返回 `-EBUSY` 或等待超时。

#### 根因

上一次通信结束后，channel 没有完成：

```text
ACK -> IDLE
```

发送端因此认为通道仍被占用。

#### 修复和验证

发送端在确认 ACK 后恢复 IDLE，接收端严格按照 state 所属方向处理。验证时必须连续
发送请求，确认每轮都完整经过：

```text
IDLE -> DATA_READY -> ACK -> IDLE
```

### 8.10 通道方向处理错误

#### 现象

FreeRTOS ISR 同时遍历并清理请求和响应通道，可能提前清除本应由 Linux/U-Boot 消费
的响应，或者把 ACK 误当成新请求。

#### 修复

FreeRTOS 只接收 channel 1 请求、使用 channel 0 发送响应；Linux/U-Boot 采用相反
方向。处理函数同时检查 IPI type、channel direction 和 state。

### 8.11 SPL 与 U-Boot proper 的 QSPI 所有权混淆

#### 现象

U-Boot proper 继续使用 `sf probe/read/update`，与已经运行的 FreeRTOS NOR agent
同时访问物理 QSPI。

#### 原因

SPL 和 U-Boot proper 虽然都属于 U-Boot 工程，但运行阶段和硬件所有权不同：

- SPL 运行时 FreeRTOS 尚未启动，必须直接访问 QSPI 加载 payload；
- U-Boot proper 运行时 QSPI 已归 FreeRTOS 独占。

#### 修复

AMP DTS 给 QSPI 增加 `quard,rtos-owned`，U-Boot proper 在 Driver Model probe 前
将该节点禁用。proper 改用：

```text
mtd -> quard-nor -> NOR client -> Router -> IPI Mailbox -> FreeRTOS NOR agent
```

### 8.12 测试客户端与生产 Router 抢占同一通道

#### 现象

同时加载直接 Mailbox test client、RPMsg transport 和生产 Router 后，出现 ACK 被
错误客户端消费、channel 长期 busy 或 service 响应无法匹配。

#### 修复

生产环境保持以下模块禁用：

```text
amp-virtio-rpmsg
starfive_rpmsg
直接申请 channel 0/1 的 IPI mailbox test client
```

生产链路只允许 `quard_mbox_router` 占用该组通道。

### 8.13 只做单次收发测试导致错误结论

单次请求成功只能证明：

- 共享内存地址基本正确；
- 目标 hart 基本正确；
- 至少有一次 IPI 通知到达；
- 基本通道方向没有完全配置错误。

它不能证明：

- ACK 会持续恢复为 IDLE；
- SSIP 清除不存在竞态；
- 连续请求不会出现 `-EBUSY`；
- Router 响应始终属于正确 consumer；
- timeout 后下一次请求可以恢复。

因此最终必须执行连续双向通信和业务压力测试。

## 10. 最终实现原则

IPI Mailbox 的实现和调试经验可以归纳为：

1. 共享内存传数据，OpenSBI IPI 只负责通知。
2. channel 1 是请求，channel 0 是响应。
3. payload 必须先写完，再发布 `DATA_READY`。
4. 每次通信必须完成 `IDLE -> DATA_READY -> ACK -> IDLE`。
5. OpenSBI 必须先清 SSIP，再原子取走 AMP bit。
6. FreeRTOS 必须同时处理标准调度 SSIP 和 AMP Mailbox SSIP。
7. FreeRTOS 在标准 clear 后再次读取 AMP bits，覆盖并发窗口。
8. ISR 只确认、复制和唤醒，业务分发及 NOR 访问放在任务上下文。
9. 底层错误路径不能使用同一条 Mailbox 日志链路递归打印。
10. Router 使用唯一 service ID 复用物理通道。
11. SPL 可以直接访问 QSPI，U-Boot proper 必须使用 Mailbox-backed MTD。
12. 生产 Router 与直接通道测试客户端不能同时运行。
13. 必须连续双向测试，不能以一次成功作为最终结论。

## 11. 验证边界

现有仓库调试记录包含 IPI Mailbox 双向通信、SSIP 清除、Router、remote shell 和 NOR
agent 的历史验证证据。一次完整的新版本验证仍应至少取得：

```text
FreeRTOS IPI mailbox init successful: base=0x6e402000
router server mbox_c2 started
mailbox router ready
registered 6 GPT partitions
```

还需要重复发送请求，确认没有 ACK timeout、`-EBUSY`、SSIP 连续重入和消息丢失。
