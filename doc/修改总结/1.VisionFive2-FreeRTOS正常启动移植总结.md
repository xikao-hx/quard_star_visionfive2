# VisionFive2 FreeRTOS 正常启动移植总结

## 1. 范围

本文结合 [Quard Star 教程第 21 章](https://quard-star-tutorial.readthedocs.io/zh-cn/latest/ch21.html)
和当前 VisionFive2 AMP SDK，总结“让 FreeRTOS 在 JH7110 hart4 上正常进入并启动
调度器”所需的移植内容。

本文只讨论以下启动主线：

```text
构建 FreeRTOS 固件
  -> SPL 将固件搬到运行地址
  -> OpenSBI 将 hart4 交给独立 S-mode domain
  -> startup.S 初始化 C 运行环境
  -> main() 完成最小板级初始化
  -> vTaskStartScheduler()
  -> SBI timer 产生 tick
  -> FreeRTOS 任务开始调度
```

Mailbox 协议、router、NOR agent、日志落盘、远程 shell 和 OTA 不属于本文范围。
不过，如果这些功能已经侵入基础 port 层并成为启动依赖，本文会将其作为耦合缺陷指出。

## 2. 教程方案与当前项目的关系

教程移植的关键前提是：FreeRTOS 运行在 OpenSBI 之上的 RISC-V S-mode，而不是直接
运行在 M-mode。对应的基础移植内容包括：

- 引入 FreeRTOS Kernel；
- 编写 RISC-V S-mode 的 `port.c`、`portASM.S` 和 `portmacro.h`；
- 通过 SBI 设置 timer 和发送/清除 IPI；
- 使用 `stvec`、`scause`、`sepc`、`sstatus` 处理 S-mode trap；
- 编写 `startup.S`、链接脚本、`FreeRTOSConfig.h` 和 Makefile；
- 使用支持高地址运行的 `-mcmodel=medany`；
- 创建测试任务并启动调度器。

当前项目保留了这套 S-mode port 思路，但从 QEMU trusted domain 扩展到了真实
VisionFive2 AMP 环境，因此还必须解决：

- hart4 的独占与 OpenSBI domain 划分；
- FreeRTOS 固件如何嵌入启动镜像并由 SPL 搬运；
- JH7110 的实际内存地址、PLIC context、UART2 时钟和复位；
- Linux 与 FreeRTOS 的 CPU、内存和外设资源隔离。

## 3. 正常启动必须适配的内容

### 3.1 引入 FreeRTOS Kernel 和裸机工具链

主要文件：

- [trusted_domain/FreeRTOS-Kernel](../../trusted_domain/FreeRTOS-Kernel)
- [trusted_domain/Makefile](../../trusted_domain/Makefile)
- [Makefile](../../Makefile)

当前项目使用 FreeRTOS V10.4.3/V202104.00 时代的 Kernel，并保留 `heap_4.c` 作为
动态内存分配实现。

FreeRTOS 固件不能使用 Linux glibc 工具链构建。当前使用：

```text
/opt/riscv/bin/riscv64-unknown-elf-
```

编译参数的核心部分为：

```text
-march=rv64imafdc
-mabi=lp64d
-mcmodel=medany
-nostartfiles
```

其中 `-mcmodel=medany` 是必需的，因为固件链接和运行在 `0x6e800000`，不能假设代码
位于低地址附近。`-nostartfiles` 表示不使用工具链默认启动文件，而由项目自己的
`startup.S` 建立运行环境。

顶层 Makefile 使用 `RTOS=freertos` 选择 FreeRTOS，并生成：

```text
work/amp/trusted_domain/trusted_fw.bin
```

### 3.2 确定 hart 和运行权限级别

主要文件：

- [trusted_domain/driver/include/quard_star.h](../../trusted_domain/driver/include/quard_star.h)
- [u-boot/arch/riscv/dts/starfive_jh7110-amp.dts](../../u-boot/arch/riscv/dts/starfive_jh7110-amp.dts)

当前项目固定：

```text
FreeRTOS hart：hart4
运行模式：RISC-V S-mode
入口地址：0x6e800000
```

`quard_star.h` 中的 `PRIM_HART=4` 用于 FreeRTOS 启动代码和调度让步 IPI。OpenSBI
domain 配置则将 `cpu4` 分给 `rt-domain`，并设置：

```dts
boot-hart = <&cpu4>;
next-addr = <0x0 0x6e800000>;
next-mode = <0x1>;
```

`next-mode = 1` 表示 OpenSBI 最终以 S-mode 进入 FreeRTOS。hart0～hart3 分给另一
domain，用于 U-Boot/Linux 链路。

这一步解决的不是 FreeRTOS 内核问题，而是“由谁把 hart4 从 M-mode 交给 FreeRTOS，
并以什么权限级别进入”的启动问题。

### 3.3 规划和保留 FreeRTOS 内存

主要文件：

- [trusted_domain/link-jh7110.lds](../../trusted_domain/link-jh7110.lds)
- [u-boot/arch/riscv/dts/starfive_jh7110-amp.dts](../../u-boot/arch/riscv/dts/starfive_jh7110-amp.dts)
- [linux/arch/riscv/boot/dts/starfive/jh7110-starfive-visionfive-2-amp.dts](../../linux/arch/riscv/boot/dts/starfive/jh7110-starfive-visionfive-2-amp.dts)

FreeRTOS 链接脚本当前将代码、只读数据、数据、BSS、堆和启动栈放在：

```text
0x6e800000 - 0x6f000000，共 8 MiB
```

链接入口为 `_start`。脚本还导出：

- `__global_pointer$`：初始化 RISC-V `gp`；
- `_data_lma`、`_data`、`_edata`：初始化 `.data`；
- `__bss_start`、`__bss_end`：清零 `.bss`；
- `heap_start`、`heap_end`：供裸机堆和 C 库桩使用；
- `_sp`：启动栈顶。

只有链接到该区域还不够。OpenSBI domain 必须允许 hart4 访问该区域，Linux DTS 也
必须将其作为保留内存，避免 Linux 页分配器覆盖 FreeRTOS 固件、堆栈或数据。

### 3.4 将 FreeRTOS 固件装入运行地址

主要文件：

- [Makefile](../../Makefile)
- [u-boot/arch/riscv/dts/starfive_jh7110-amp-u-boot.dtsi](../../u-boot/arch/riscv/dts/starfive_jh7110-amp-u-boot.dtsi)
- [u-boot/board/starfive/visionfive2/spl.c](../../u-boot/board/starfive/visionfive2/spl.c)

当前打包方式不是单独加载一个标准 FIT 子镜像，而是：

1. 构建 `trusted_fw.bin`；
2. 将 AMP U-Boot binary 扩展到固定长度 `3342336` 字节，即 `0x330000`；
3. 将 `trusted_fw.bin` 追加在 U-Boot binary 后面；
4. OpenSBI `fw_payload` 在该 payload 前还有 `0x200000` 布局开销；
5. U-Boot DTS 因此把最终 RTOS 源偏移写为 `0x530000`；
6. SPL 从 `CONFIG_SPL_OPENSBI_LOAD_ADDR + 0x530000` 找到 RTOS 数据；
7. SPL 将其复制到 `0x6e800000`。

SPL 还提前配置 UART2 pinmux，使 FreeRTOS 后续可以使用 UART2 输出。

这一步必须保证三个地址一致：

| 含义 | 当前值 |
| --- | --- |
| payload 中 RTOS 偏移 | `0x530000` |
| FreeRTOS 链接地址 | `0x6e800000` |
| OpenSBI `next-addr` | `0x6e800000` |

只修改其中一个值会造成 SPL 从错误位置复制，或者 OpenSBI 跳到没有有效代码的地址。

### 3.5 编写 S-mode 启动入口

主要文件：

- [trusted_domain/startup.S](../../trusted_domain/startup.S)

OpenSBI 跳到 `_start` 时，`a0` 保存当前 hart ID。启动代码依次完成：

1. 初始化 `gp`；
2. 将 hart ID 保存到 `tp`；
3. 检查当前 hart 是否为 `PRIM_HART=4`；
4. 清除 `sie` 和 `sip`，避免带着旧中断状态进入初始化；
5. 初始化 FPU 状态和 S-mode `sstatus`；
6. 将 `sp` 设置为链接脚本提供的 `_sp`；
7. 复制 `.data`；
8. 清零 `.bss`；
9. 初始化 C/C++ 构造函数环境；
10. 跳转到 `main()`；
11. 如果 `main()` 返回，则进入 `wfi` 循环。

当前实现只支持一个 FreeRTOS hart，其他 hart 会进入 `secondary` 的 `wfi` 循环。

### 3.6 移植 RISC-V S-mode FreeRTOS port

主要文件：

- [trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/port.c](../../trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/port.c)
- [trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/portASM.S](../../trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/portASM.S)
- [trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/portmacro.h](../../trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/portmacro.h)
- [trusted_domain/riscv/sbi.c](../../trusted_domain/riscv/sbi.c)

这是教程移植的核心。

`portmacro.h` 负责：

- 定义 RV64 的 `StackType_t`、`BaseType_t` 和 `TickType_t`；
- 设置 16 字节栈对齐；
- 定义栈向低地址增长；
- 使用 `sstatus.SIE` 实现临界区中断开关；
- 使用 SBI IPI 实现 `portYIELD()`。

`portASM.S` 负责：

- 初始化新任务的栈帧；
- 保存和恢复整数寄存器、`sepc`、`sstatus`，以及需要时的浮点寄存器；
- 将 `stvec` 指向 `freertos_risc_v_trap_handler`；
- 区分 SSIP、STIP、SEIP 和同步异常；
- timer 中断中调用 `xTaskIncrementTick()`；
- tick 唤醒更高优先级任务时调用 `vTaskSwitchContext()`；
- 恢复目标任务上下文并执行 `sret`。

`port.c` 负责：

- 读取 RISC-V `time`；
- 通过 SBI `set_timer` 设置下一次 tick；
- 在调度器启动时打开 STIP 和 SSIP；
- 初始化独立 ISR stack；
- 启动第一个任务。

因为 FreeRTOS 运行在 S-mode，不能像传统 M-mode 裸机 port 那样直接完全控制 machine
timer 和 machine software interrupt，所以 timer/IPI 操作需要通过 OpenSBI ecall。

### 3.7 配置 FreeRTOS 内核参数

主要文件：

- [trusted_domain/FreeRTOSConfig.h](../../trusted_domain/FreeRTOSConfig.h)

与正常启动直接相关的当前配置包括：

```text
configUSE_PREEMPTION          = 1
configCPU_CLOCK_HZ            = 4,000,000
configTICK_RATE_HZ            = 1,000
configMAX_PRIORITIES          = 7
configTOTAL_HEAP_SIZE         = 64,500 bytes
configISR_STACK_SIZE_WORDS    = 2,048
configCHECK_FOR_STACK_OVERFLOW = 2
```

这里的 `4,000,000` 实际被 port 用作 RISC-V `time` 计数频率，以计算每个 tick 的
间隔：

```text
4,000,000 / 1,000 = 4,000 个 time ticks
```

若该值与 JH7110/OpenSBI 提供的 timebase 不一致，FreeRTOS 的延时和调度周期都会不准。

### 3.8 完成最小 JH7110 板级初始化

主要文件：

- [trusted_domain/board/jh7110.c](../../trusted_domain/board/jh7110.c)
- [trusted_domain/driver/include/memlayout.h](../../trusted_domain/driver/include/memlayout.h)
- [trusted_domain/driver/plic/plic.c](../../trusted_domain/driver/plic/plic.c)
- [trusted_domain/driver/serial](../../trusted_domain/driver/serial)
- [trusted_domain/main.c](../../trusted_domain/main.c)

在真实 VisionFive2 上，为了获得最基本的启动输出和外部中断，还需要适配：

- UART2 物理地址 `0x10020000`；
- UART2 PLIC IRQ 34；
- UART2 APB/core 时钟和复位；
- JH7110 hart4 的 S-mode PLIC context；
- PLIC priority、enable、threshold、claim 和 complete；
- S-mode external interrupt 使能位 `SEIE`。

JH7110 的 PLIC context 排列不能直接沿用 QEMU 公式。当前代码明确使用 hart4 S-mode
context 8：

```text
PLIC_CONTEXT(hart) = hart << 1
```

如果 context 计算错误，FreeRTOS 可能能够执行普通任务和 timer tick，但 UART 等外部
中断不会进入预期 hart，甚至会与 Linux 操作同一 PLIC context。

最小 `main()` 应只完成板级时钟、PLIC、串口初始化，创建一个或两个基础任务，然后
调用：

```c
vTaskStartScheduler();
```

调度器正常启动后不应返回。

### 3.9 与 Linux 做最小资源隔离

主要文件：

- [linux/arch/riscv/boot/dts/starfive/jh7110-starfive-visionfive-2-amp.dts](../../linux/arch/riscv/boot/dts/starfive/jh7110-starfive-visionfive-2-amp.dts)

单看 FreeRTOS 的第一条指令，这一步不是 port 的组成部分；但要让 Linux 与 FreeRTOS
长期稳定并行启动，它是必需条件：

- Linux 不得使用 hart4；
- Linux PLIC `interrupts-extended` 不得包含 hart4 context；
- Linux 不得绑定 UART2；
- Linux 内存管理不得分配 FreeRTOS 的代码、堆栈和共享区域。

否则 FreeRTOS 可能偶尔能够打印启动日志，却会在 Linux 初始化 CPU、PLIC、串口或
内存后随机失效。这种情况不能算“移植成功”。

## 4. 当前启动时序

```text
主机构建
  trusted_domain/Makefile
      -> trusted_fw.elf
      -> trusted_fw.bin

顶层打包
  U-Boot binary + 固定 padding + trusted_fw.bin
      -> OpenSBI fw_payload

SPL
  初始化 DDR
  从 payload 固定偏移找到 trusted_fw.bin
  配置 UART2 pinmux
  复制 FreeRTOS 到 0x6e800000

OpenSBI
  创建 Linux domain：hart0-hart3
  创建 RT domain：hart4
  在 hart4 以 S-mode 跳转 0x6e800000

FreeRTOS startup.S
  gp/tp/sp -> data -> bss -> libc init -> main

FreeRTOS main
  最小板级初始化 -> 创建任务 -> vTaskStartScheduler

FreeRTOS port
  stvec -> 设置 SBI timer -> 打开 STIP/SSIP -> 恢复第一个任务
```

## 5. 当前适配存在的缺陷

### 5.1 地址和偏移在多个组件中重复写死

`0x6e800000` 同时出现在链接脚本、OpenSBI domain、U-Boot DTS 和 SPL 搬运配置中；
hart4、UART2、PLIC context、timebase 和 payload 偏移也分散在多个文件。

任何一个值单独变化，都可能产生“编译正常，但上板无输出或直接异常”的问题。当前只
依靠注释提醒同步，没有构建期一致性检查。

### 5.2 RTOS 使用固定 padding 拼接，缺少镜像描述和边界校验

当前 Makefile 使用 `truncate + cat` 将 FreeRTOS 追加到 U-Boot binary，SPL 再按固定
`0x530000` 偏移复制：

- 没有独立记录 RTOS 镜像长度；
- 没有验证固件是否超过 8 MiB 链接区域；
- SPL 使用 `spl_image->size - rtos_offset` 作为复制长度，容易受整个 payload 布局变化
  影响；
- 没有对 RTOS 子镜像单独做 hash、签名或格式校验；
- OpenSBI/U-Boot 布局变化后，偏移容易失效。

### 5.3 S-mode port 是旧版本上的项目内私有实现

该 port 源于 FreeRTOS V10.4.3 时代的自定义 S-mode 实现，与后续 FreeRTOS Kernel、
RISC-V ABI 和 SBI 规范的演进没有自动同步。升级 Kernel 时，任务栈帧、临界区、FPU
上下文或中断 API 的假设都需要重新审核。

### 5.4 ISR 中断屏蔽接口实现不完整

当前：

```c
#define portSET_INTERRUPT_MASK_FROM_ISR() 0
#define portCLEAR_INTERRUPT_MASK_FROM_ISR(x) (void)x
```

没有真正保存和恢复进入 ISR 临界区前的中断状态。若后续驱动或 FreeRTOS API 依赖这组
宏提供原子保护，就可能出现嵌套中断、竞态或不可预期的临界区行为。

### 5.5 调度器 SSIP 清除与 mailbox 实现耦合

教程中的 `vPortClearIpiInterrupt()` 只负责清除用于任务让步的标准 SSIP。当前项目却
直接调用 `quard_ipi_mailbox_handle()`，由 mailbox 路径再清除标准 IPI。

结果是：即使只想构建一个最小 FreeRTOS 调度器，port 层也依赖 mailbox 符号和具体
处理顺序。基础调度能力与上层跨核通信不再能独立测试。

### 5.6 hart 和 timebase 被硬编码

`portYIELD()` 直接使用 `PRIM_HART=4`，tick 又把硬编码的 `4 MHz` 放在名为
`configCPU_CLOCK_HZ` 的配置中。当前单 hart 固定平台可以工作，但代码难以迁移到其他
hart、其他板卡或不同 timebase 的固件环境。

### 5.7 链接区域缺少代码与数据权限分离

`link-jh7110.lds` 将同一段 8 MiB 内存同时声明为 `rwx`，代码、可写数据、堆和栈都在
同一权限区域。OpenSBI domain 对 `rtcode` 也给出统一权限。功能上简单，但不能阻止
栈溢出或错误指针修改代码，也无法落实 W^X。

### 5.8 `main()` 在启动调度器前承担过多功能初始化

当前 `main()` 不只进行 CPU/板级初始化，还初始化日志后端、mailbox router、NOR
agent 和 shell。任一上层服务初始化出错，都可能表现成“FreeRTOS 启动失败”，增加
定位难度。

### 5.9 构建规则存在维护风险

`trusted_domain/Makefile` 使用 `find` 收集大量源文件，再通过 `notdir` 生成 object
名称。不同目录出现同名 `.c` 文件时可能映射到同一个 object 名称。当前还固定
`DEBUG=1` 和 `-Og`，没有清晰区分最小启动、调试和发布固件。

链接脚本注释仍写着“RT-Thread code region”，也说明 FreeRTOS 与 RT-Thread 共用启动
布局后存在命名和维护残留。

## 6. 改进建议

### 6.1 建立单一平台配置来源

将以下参数集中到一个板级内存布局头文件或构建生成文件：

```text
RTOS_HART_ID
RTOS_LOAD_ADDR
RTOS_REGION_SIZE
RTOS_PAYLOAD_OFFSET
TIMEBASE_FREQ
UART_BASE / UART_IRQ
PLIC_S_CONTEXT
```

再由构建系统生成或检查 linker script、U-Boot DTS、OpenSBI domain 和 FreeRTOS 头文件。
至少应增加静态断言或构建脚本检查，发现地址不一致时立即失败。

### 6.2 使用 FIT 子镜像描述 FreeRTOS

建议将 FreeRTOS 作为独立 FIT image，而不是固定 padding 后直接拼接：

- 显式记录 load address、entry address 和 size；
- SPL 按 FIT 元数据加载；
- 增加 hash，必要时增加签名；
- 构建时检查镜像大小不超过保留区域；
- U-Boot/OpenSBI 布局变化时不再手工重算 `0x530000`。

### 6.3 将基础 port 与平台扩展解耦

建议把 SSIP 处理拆成：

```text
port 层：清除标准 SSIP，完成调度器 yield
平台层：可选检查并分发 AMP IPI
```

平台扩展可通过 weak hook 或注册回调接入。这样可以先用最小双任务固件验证 scheduler，
再逐项启用跨核通信功能。

### 6.4 完整实现 ISR mask API

`portSET_INTERRUPT_MASK_FROM_ISR()` 应读取并保存 `sstatus.SIE`，再关闭中断；
`portCLEAR_INTERRUPT_MASK_FROM_ISR()` 应按保存值恢复，而不是固定返回 0 和空操作。
实现后需要覆盖：任务临界区、ISR 临界区、嵌套调用和从 ISR 唤醒高优先级任务。

### 6.5 从平台信息获取 hart 和 timebase

- `portYIELD()` 应以当前 hart ID 或统一 platform API 为目标，避免直接写死 hart4；
- 将 `configCPU_CLOCK_HZ` 改为语义明确的 timebase 配置；
- 构建时从 JH7110 DTS `timebase-frequency` 生成配置，或由 OpenSBI 平台接口提供；
- 启动时打印实际 timebase 和 tick interval，便于核对。

### 6.6 拆分最小启动和业务服务初始化

建议启动阶段按层次执行：

1. `platform_early_init()`：时钟、复位、UART polling；
2. `interrupt_init()`：PLIC 和 trap；
3. 创建最小 health task；
4. 启动 scheduler；
5. 由独立 init task 初始化日志、mailbox、NOR、shell 等可选服务。

这样即使某个业务服务失败，FreeRTOS 调度器仍能运行，并能输出明确的阶段错误。

### 6.7 分离代码、数据、堆和栈

在链接脚本和 OpenSBI domain 中分别描述 RX code/rodata 与 RW data/heap/stack，至少
增加链接期边界断言：

```ld
ASSERT(_end <= ORIGIN(ram) + LENGTH(ram), "FreeRTOS image exceeds region")
ASSERT(heap_start < heap_end, "invalid FreeRTOS heap")
```

如果 PMP/domain 粒度允许，应进一步落实不可写代码区和不可执行数据区。

### 6.8 改进构建规则

- 保留源文件相对路径生成 object，避免同名冲突；
- 提供 `minimal`、`debug`、`release` 三种配置；
- 最小启动配置不链接 mailbox、NOR 和 shell；
- 对 `trusted_fw.elf` 执行入口、段地址、大小和未解析符号检查；
- 将 FreeRTOS Kernel/port 版本明确记录在构建产物中。

## 7. 推荐的分步移植方法

### 第一步：只验证入口和串口

- 配置 hart4 OpenSBI domain；
- SPL 将一个最小裸机 S-mode 程序复制到 `0x6e800000`；
- `_start` 初始化栈和 BSS；
- UART2 polling 输出 hart ID 和入口地址；
- 不启用 PLIC，不启动 scheduler。

成功判据：hart4 稳定输出，Linux 仍可由其他 hart 启动。

### 第二步：验证 FreeRTOS 调度器和 timer tick

- 接入 FreeRTOS Kernel、`FreeRTOSConfig.h` 和 S-mode port；
- 创建两个只使用 `vTaskDelay()` 的测试任务；
- 通过 SBI timer 产生 STIP；
- 暂不接入 mailbox、NOR、shell 和中断式 UART。

成功判据：两个任务按预期周期持续切换，tick 周期与真实时间一致。

### 第三步：验证 SSIP yield 和临界区

- 验证同 hart `portYIELD()`；
- 验证任务临界区和 ISR mask 保存/恢复；
- 验证高优先级任务唤醒后的上下文切换；
- 检查栈对齐和栈溢出 hook。

成功判据：高频 yield 和任务切换不产生寄存器损坏或异常。

### 第四步：接入 PLIC 和 UART2 外部中断

- 使用 hart4 S-mode context 8；
- 只启用 UART2 IRQ34；
- ISR 只收发必要数据并唤醒任务；
- 在任务上下文处理日志或命令。

成功判据：UART2 连续收发不会出现 `Instruction Access Fault`、`sepc=0` 或任务卡死。

### 第五步：验证 Linux/FreeRTOS 并行资源隔离

- Linux 不枚举 hart4；
- Linux PLIC 不包含 hart4 context；
- Linux 不使用 UART2；
- Linux 保留 FreeRTOS 内存；
- 长时间运行调度和串口压力测试。

成功判据：Linux 初始化和运行期间不会破坏 FreeRTOS 的代码、上下文、中断或串口。
