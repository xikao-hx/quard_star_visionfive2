## 2. 先区分三个启动阶段的职责

### 2.1 SPL：准备运行环境，不承担 Mailbox 服务

SPL 运行时 FreeRTOS 尚未启动，因此当前 SPL 没有编译
`quard_ipi_mailbox`、`quard_mbox_router` 或 NOR client。它的职责是：

- 从启动介质加载包含 OpenSBI 和 U-Boot proper 的 AMP payload；
- 从 payload 中找到 FreeRTOS 镜像并复制到 `0x6E800000`；
- 启用 FreeRTOS 使用的 UART2 基础时钟和引脚；
- 把 AMP 设备树交给 OpenSBI，使其建立 Linux domain 与 RT domain；
- 在 FreeRTOS 启动前继续直接使用物理 QSPI 完成早期加载。

因此 SPL 对 Mailbox 的作用是“把通信双方和固件监督层准备好”，不是自己发送
Mailbox 请求。

### 2.2 OpenSBI：跨 hart IPI/SSIP 通知层

共享内存只能保存数据和状态，不能主动唤醒另一个 hart。OpenSBI 位于 M-mode，负责：

- 接收 U-Boot、Linux 或 FreeRTOS 发起的 SBI ecall；
- 在目标 hart 的 AMP pending bitmap 中设置消息类型位；
- 向目标 hart 发送 Supervisor IPI，使其产生 SSIP；
- 在目标 hart 处理中原子取走 pending bitmap，并正确清除 SSIP。

OpenSBI 不解析 28 字节 Mailbox payload，也不理解日志、vshell 或 NOR 服务。它只负责
“哪个 hart 有哪一类 IPI 待处理”。

### 2.3 U-Boot proper：Mailbox 客户端和服务消费端

进入 U-Boot proper 时 FreeRTOS 已经运行，并拥有物理 QSPI。U-Boot proper 负责：

- 使用共享内存和 SBI AMP IPI 实现 Mailbox provider；
- 使用 Router 按 service ID 复用同一组物理通道；
- 通过 NOR client 把 FreeRTOS NOR agent 暴露成 `quard-nor` MTD；
- 让 `mtd` 命令、A/B bootctrl 和 environment 都复用这条 Mailbox Flash 链路；
- 在 proper 的设备树副本中禁用物理 QSPI，避免形成第二条直访路径。

## 3. 完整架构与数据流

### 3.1 分层关系

```text
U-Boot command / environment / bootctrl
                  |
                  v
          quard_nor_client          service ID = 2
                  |
                  v
          quard_mbox_router         添加/匹配 service ID
                  |
                  v
       quard_ipi_mailbox provider   28 B payload + 4 B state
                  |
          shared memory + SBI ecall
                  |
                  v
               OpenSBI              AMP bit + Supervisor IPI
                  |
                  v
       FreeRTOS IPI mailbox ISR      确认/复制/唤醒
                  |
                  v
       FreeRTOS mailbox router       任务上下文分发 service ID
                  |
                  v
          FreeRTOS NOR agent         实际访问物理 QSPI
```

依赖方向必须保持为：

```text
U-Boot NOR client -> U-Boot router -> U-Boot IPI mailbox
                                            |
                                    共享内存 + SBI IPI
                                            |
FreeRTOS NOR agent <- FreeRTOS router <- FreeRTOS IPI mailbox
```

NOR client 不应直接操作共享内存，Router 不应直接访问 QSPI，OpenSBI 也不应理解
NOR 命令。每层只处理自己的协议。

### 3.2 共享内存通道

当前 Mailbox 起始地址为 `0x6E402000`。协议实际使用两个 32 字节通道：

| 通道 | U-Boot/FreeRTOS 方向 | 内容 |
| --- | --- | --- |
| channel 1 | U-Boot proper -> FreeRTOS | 请求 |
| channel 0 | FreeRTOS -> U-Boot proper | 响应或反向消息 |

每个通道布局为：

```text
offset +0x00 : payload[28]
offset +0x1C : state[4]
```

状态机为：

```text
IDLE(0) -> DATA_READY(1) -> ACK(2) -> IDLE(0)
```

共享内存保存业务数据和 ACK 状态；OpenSBI 管理的 per-hart AMP bitmap 保存“哪个
IPI 类型到达”。两者是不同的数据结构，不能互相替代。

### 3.3 Router 服务编号

Router 将 28 字节 payload 的头部用于 service ID，当前约定为：

| service ID | 服务 |
| --- | --- |
| `0` | 日志 |
| `1` | vshell |
| `2` | NOR agent |

U-Boot proper 当前主要使用 service `2`。一个 service ID 只能由一个 consumer 注册，
避免多个客户端同时解释同一响应。

## 4. 第一阶段：SPL 和 AMP 镜像准备修改

### 4.1 AMP payload 为什么需要特殊布局

AMP 镜像不是简单的单个 U-Boot binary。当前打包关系是：

```text
fw_payload.bin
  +-- OpenSBI（从 0x40000000 执行）
  +-- 0x200000 后嵌入 U-Boot AMP image
                         +-- U-Boot 原始内容补齐到 0x330000
                         +-- FreeRTOS trusted_fw.bin
```

因此 FreeRTOS 在最终 `fw_payload.bin` 内的 offset 是：

```text
0x200000 + 0x330000 = 0x530000
```

如果 SPL 仍按 U-Boot 原始镜像中的 `0x330000` 取 FreeRTOS，就会从 OpenSBI payload
中的错误位置复制数据，hart4 跳转后无法执行正确入口。

### 4.2 SPL 的实际执行步骤

[spl.c](../../u-boot/board/starfive/visionfive2/spl.c) 中的
`spl_perform_fixups()` 完成以下工作：

1. 从 SPL 使用的 DT config 读取 `amp,rtos-code-base` 和 `amp,rtos-offset`；
2. `amp,rtos-offset=0x530000`，`amp,rtos-code-base=0x6E800000`；
3. 启用 UART2 时钟和 pinmux，为 hart4 FreeRTOS 的早期输出准备硬件；
4. 从 `CONFIG_SPL_OPENSBI_LOAD_ADDR + rtos_offset` 复制 FreeRTOS；
5. 把 FreeRTOS 放到 OpenSBI RT domain 的 `next-addr=0x6E800000`。

配置位于
[starfive_jh7110-amp-u-boot.dtsi](../../u-boot/arch/riscv/dts/starfive_jh7110-amp-u-boot.dtsi)。

### 4.3 AMP domain 和共享内存描述

[starfive_jh7110-amp.dts](../../u-boot/arch/riscv/dts/starfive_jh7110-amp.dts)
定义：

- `u-domain` 使用 hart0～hart3，boot hart 为 hart1，下一阶段地址为
  `0x40200000`；
- `rt-domain` 只使用 hart4，下一阶段地址为 `0x6E800000`，S-mode 启动；
- `0x6E400000` 起的共享区域供 AMP 两端访问；
- `0x6E402000-0x6E403FFF` 作为 IPI Mailbox reserved-memory；
- `0x6E500000-0x6E6FFFFF` 作为 NOR 大块数据交换区；
- Mailbox 节点指定 `rtos-hart-id=<4>`；
- Router 使用 channel 1 发送、channel 0 接收，Flash 子节点使用 service `2`。

为什么必须由 DTS 描述：SPL、OpenSBI 和 U-Boot proper 必须对 hart 归属、下一阶段
地址、共享内存和设备依赖得出同一解释。若地址只写在某一个驱动中，其他阶段无法
建立一致的启动和访问边界。

### 4.4 SPL/打包相关文件与修改原因

| 文件 | 作用 | 为什么需要 |
| --- | --- | --- |
| [spl.c](../../u-boot/board/starfive/visionfive2/spl.c) | 复制 RTOS 到运行地址并准备 UART2 | OpenSBI 只能跳转到已放置好的 FreeRTOS 镜像 |
| [starfive_jh7110-amp-u-boot.dtsi](../../u-boot/arch/riscv/dts/starfive_jh7110-amp-u-boot.dtsi) | 定义 RTOS 在 payload 中的 offset 和运行地址 | 消除打包 offset 与 SPL 复制地址不一致 |
| [starfive_jh7110-amp.dts](../../u-boot/arch/riscv/dts/starfive_jh7110-amp.dts) | 定义 domain、共享内存、Mailbox、Router 和 NOR client | 给 OpenSBI及 U-Boot proper 提供统一硬件描述 |
| [顶层 Makefile](../../Makefile) | 构建 FreeRTOS、补齐 U-Boot、生成 OpenSBI AMP payload | 保证最终镜像包含通信双方和监督层 |
| [visionfive2-uboot-amp-fit-image.its](../../conf/visionfive2-uboot-amp-fit-image.its) | 把 OpenSBI `fw_payload.bin` 放到 `0x40000000` | 让 SPL 按预期地址加载和进入 OpenSBI |

### 4.5 SPL 阶段明确没有做什么

- 不注册 Mailbox provider；
- 不执行 Router service 分发；
- 不通过 Mailbox 访问 NOR；
- 不编译 proper-only 的 Mailbox、Router、NOR client 和 MTD environment；
- 不在 FreeRTOS 启动前放弃 QSPI，因为此时必须靠 SPL 从 Flash 加载 payload。

这也是 U-Boot Mailbox 相关 Makefile 使用 `ifndef CONFIG_SPL_BUILD` 的原因。

## 5. 第二阶段：OpenSBI IPI 扩展修改

### 5.1 为什么共享内存之外还需要 OpenSBI

U-Boot proper 和 FreeRTOS 都运行在 S-mode，且分属不同 hart/domain。写完共享内存后，
发送端仍需要一种受 M-mode 管理的方式通知目标 hart。当前实现复用 SBI IPI extension
ID，并增加三个 function ID：

| function ID | 名称 | 作用 |
| --- | --- | --- |
| `0x100` | `SBI_EXT_IPI_SEND_EXT_DOMAIN` | 设置目标 hart 的 AMP 消息位并发送 Supervisor IPI |
| `0x101` | `SBI_EXT_IPI_SET_AMP_DATA_ADDR` | 注册 per-hart AMP pending bitmap 地址 |
| `0x102` | `SBI_EXT_IPI_CLEAR_IPI` | 清除本 hart SSIP并原子取走 AMP 消息位 |

接口定义在
[sbi_ecall_interface.h](../../opensbi/include/sbi/sbi_ecall_interface.h)，ecall 分发位于
[sbi_ecall_ipi.c](../../opensbi/lib/sbi/sbi_ecall_ipi.c)。

### 5.2 发送过程

[sbi_ipi.c](../../opensbi/lib/sbi/sbi_ipi.c) 中的发送逻辑是：

1. 调用方先通过 `SET_AMP_DATA_ADDR` 注册 pending bitmap；
2. `SEND_EXT_DOMAIN` 接收目标 hart ID 和消息类型 bit；
3. `atomic_raw_set_bit()` 在 `amp_data_addr[hartid]` 中置位；
4. 通过 OpenSBI 原有 `ipi_smode_event` 向目标 hart 发送 IPI；
5. 目标 hart 的 OpenSBI IPI handler 设置 `MIP_SSIP`，S-mode 收到 SSIP。

消息类型参数是 bit 编号。例如发送 type `1` 后，接收方取出的 pending bitmap 中是
`1UL << 1`。

### 5.3 接收和清除顺序为什么修改

Mailbox IPI 和 FreeRTOS 调度器的 yield IPI 共用 SSIP。早期实现曾出现两个问题：

1. FreeRTOS 只调用 AMP clear，没有保留标准 `sbi_clear_ipi()`，导致调度 SSIP
   可能一直 pending；
2. OpenSBI 先取走 AMP bit、再清 SSIP，新的 IPI 如果恰好在两步之间到达，其消息位
   虽然存在，SSIP 却可能被旧处理流程清掉，造成消息无中断唤醒。

提交 `75fb1ab56` 将 OpenSBI 正式顺序调整为：

```text
先清当前 SSIP
  -> 再 atomic_raw_xchg_ulong() 取走当前 hart 的全部 AMP bits
```

这个顺序覆盖三种时序：

- 新 IPI 在清 SSIP前到达：本次原子交换取走消息位；
- 新 IPI 在清 SSIP后、原子交换前到达：本次仍取走消息位；
- 新 IPI 在原子交换后到达：新消息位和新 SSIP 留给下一次 trap。

FreeRTOS 侧还会在标准 `sbi_clear_ipi()` 之后第二次读取 AMP bits，并将两次结果按位
或合并，进一步覆盖 AMP clear 与标准 clear 之间的新消息竞态。

### 5.4 OpenSBI 修改文件与原因

| 文件 | 改了什么 | 为什么需要 |
| --- | --- | --- |
| [sbi_ecall_interface.h](../../opensbi/include/sbi/sbi_ecall_interface.h) | 增加三个 AMP IPI function ID | 给 S-mode 两端提供稳定 ecall 编号 |
| [sbi_ecall_ipi.c](../../opensbi/lib/sbi/sbi_ecall_ipi.c) | 分发 send/set-address/clear 请求 | 把 ecall 参数接入 OpenSBI IPI 内核逻辑 |
| [sbi_ipi.h](../../opensbi/include/sbi/sbi_ipi.h) | 声明 AMP IPI 内部 API | 约束 ecall 层与 IPI 实现层接口 |
| [sbi_ipi.c](../../opensbi/lib/sbi/sbi_ipi.c) | 保存 pending bitmap、原子置位/取位、发送和清除 SSIP | 在不同 hart/domain 间可靠传递通知并关闭并发竞态 |

OpenSBI 只传递通知位。28 字节 payload、channel state 和 service ID 都由 S-mode
Mailbox/Router 代码处理。

## 6. 第三阶段：U-Boot proper Mailbox 修改

### 6.1 设备树与硬件所有权切换

[starfive_jh7110-amp.dts](../../u-boot/arch/riscv/dts/starfive_jh7110-amp.dts)
为 U-Boot proper 描述 Mailbox、Router、Flash consumer 和共享内存，同时给物理 QSPI
增加 `quard,rtos-owned` 标记。

[starfive_visionfive2.c](../../u-boot/board/starfive/visionfive2/starfive_visionfive2.c)
中的 `board_fix_fdt()` 在 proper 驱动模型扫描前：

1. 查找 `cdns,qspi-nor` 节点；
2. 确认存在 `quard,rtos-owned`；
3. 将控制器及其子节点的 `status` 改为 `disabled`。

这样既不会影响此前 SPL 直接从 QSPI 加载，又能阻止 U-Boot proper probe 物理 QSPI
并绕过 FreeRTOS NOR agent。

### 6.2 IPI Mailbox provider

[quard_ipi_mailbox.c](../../u-boot/drivers/mailbox/quard_ipi_mailbox.c) 实现 U-Boot
Driver Model 的 `UCLASS_MAILBOX` provider：

1. 从 DTS 读取共享内存地址和 `rtos-hart-id=4`；
2. 准备 per-hart `starfive_amp_bits[]`，通过 SBI `0x101` 注册；
3. `send()` 只允许 channel 1，检查 `IDLE` 后复制 28 字节请求；
4. 使用内存屏障后设置 `DATA_READY`，通过 SBI `0x100` 通知 hart4；
5. 轮询等待 `ACK`，成功后恢复 `IDLE`；
6. 等待过程中定期重新 kick，补偿通知丢失；总等待时间受 timeout 限制；
7. `recv()` 只允许 channel 0，复制响应、清空 payload、设置 `ACK` 并通知对端。

内存屏障的目的，是保证对端不会先观察到 `DATA_READY`，却仍读到尚未完成写入的旧
payload。

### 6.3 Mailbox Router

[quard_mbox_router.c](../../u-boot/drivers/mailbox/quard_mbox_router.c) 位于物理
Mailbox 与业务 consumer 之间：

- 从 DTS 获取名为 `router-tx` 和 `router-rx` 的 channel；
- 从 consumer 的 `mbox-router-server` phandle 读取 service ID；
- 拒绝超出 8 bit 的 service ID；
- 拒绝同一 service ID 被重复注册；
- 发送前在消息 header 中写入 service ID；
- 接收后把响应交给相应 consumer callback；
- 对 consumer 提供同步 send/receive API，而不暴露共享内存细节。

公共接口和 28 字节 consumer 消息结构位于
[quard_mbox_router.h](../../u-boot/include/quard_mbox_router.h)。

### 6.4 Mailbox-backed NOR MTD

[quard_nor_client.c](../../u-boot/drivers/mtd/quard_nor_client.c) 注册 service `2`，
把 FreeRTOS NOR agent 转换成 U-Boot MTD：

- `NOR_GET_INFO`：查询 NOR 容量、page/erase 几何和 GPT 分区；
- `NOR_READ`：通过 Mailbox 发送控制消息，通过 2 MiB 共享区搬运大块数据；
- `NOR_WRITE`：分块传输数据并由 FreeRTOS 执行 Page Program；
- `NOR_ERASE`：检查范围和擦除对齐后请求 FreeRTOS 擦除；
- 将 master 注册为 `quard-nor`，并注册六个 GPT 分区。

Mailbox payload 只有 28 字节，不能直接装下大块 Flash 数据。因此控制面走 28 字节
Router 消息，数据面走 `0x6E500000` 的 reserved-memory，这是为何 DTS 还要单独保留
2 MiB NOR agent 区域。

### 6.5 Environment 为什么改为 MTD backend

原来的 `ENV_IS_IN_SPI_FLASH` 会让 U-Boot proper 直接 probe 和访问物理 QSPI，与
FreeRTOS 独占资源的设计冲突。提交 `44ca8cf7e` 增加
[env/mtd.c](../../u-boot/env/mtd.c)，使环境变量访问变成：

```text
load/saveenv/eraseenv
  -> environment core
  -> MTD environment backend
  -> quard-nor
  -> NOR client
  -> Router
  -> IPI Mailbox
  -> FreeRTOS NOR agent
```

配套修改包括：

- [env/Kconfig](../../u-boot/env/Kconfig)：增加 `ENV_IS_IN_MTD` 和
  `ENV_MTD_NAME`；
- [env/Makefile](../../u-boot/env/Makefile)：只在 U-Boot proper 编译 MTD backend；
- [env/env.c](../../u-boot/env/env.c) 和
  [env_internal.h](../../u-boot/include/env_internal.h)：注册 `ENVL_MTD`；
- [nvedit.c](../../u-boot/cmd/nvedit.c)：承认 MTD 是合法 environment device；
- [starfive_visionfive2_defconfig](../../u-boot/configs/starfive_visionfive2_defconfig)：
  启用 Mailbox、Router、MTD、NOR client 和 MTD environment。

当前 environment 位于 `quard-nor` master 的 `0xD00000`，大小和擦除区均为
`0x10000`。它位于 GPT 六分区之后的 reserved 区，不占用 recovery。

### 6.6 构建配置为什么必须 proper-only

[Mailbox Makefile](../../u-boot/drivers/mailbox/Makefile) 和
[MTD Makefile](../../u-boot/drivers/mtd/Makefile) 使用配置开关并限制 SPL build。
原因是：

- SPL 此时没有运行中的 FreeRTOS NOR agent 可调用；
- SPL 必须直接访问 QSPI 才能加载 OpenSBI/U-Boot/FreeRTOS payload；
- 把同步 Router、MTD 和 environment 带入 SPL会增加体积并制造错误依赖；
- proper-only 隔离可以防止 SPL 意外放弃启动介质所有权。

### 6.7 U-Boot proper 文件分类

| 类别 | 主要文件 | 解决的问题 |
| --- | --- | --- |
| 设备描述 | `u-boot/arch/riscv/dts/starfive_jh7110-amp.dts` | 描述共享内存、通道、hart 和 consumer 关系 |
| 所有权切换 | `u-boot/board/starfive/visionfive2/starfive_visionfive2.c` | proper 禁用 FreeRTOS 独占的物理 QSPI |
| 底层传输 | `u-boot/drivers/mailbox/quard_ipi_mailbox.c` | 共享内存状态机和 SBI IPI 通知 |
| 服务复用 | `u-boot/drivers/mailbox/quard_mbox_router.c`、`u-boot/include/quard_mbox_router.h` | 用 service ID 隔离多个业务 consumer |
| Flash consumer | `u-boot/drivers/mtd/quard_nor_client.c` | 把远端 NOR agent注册成标准 MTD |
| MTD 框架适配 | `u-boot/drivers/mtd/mtd_uboot.c` | 避免空 `mtdids/mtdparts` 阻断动态 MTD 探测 |
| 环境变量 | `u-boot/env/mtd.c` 及 environment core 文件 | 让环境 load/save/erase 不再直接访问 QSPI |
| 构建开关 | Mailbox/MTD/environment Kconfig、Makefile、defconfig | 显式控制依赖且只进入 proper |

## 7. FreeRTOS 对端为何也必须配套修改

虽然本文主线是 SPL、OpenSBI 和 U-Boot，但没有 FreeRTOS 对端，U-Boot Mailbox 只会
等待超时。

### 7.1 SBI wrapper

[trusted_domain/riscv/sbi.c](../../trusted_domain/riscv/sbi.c) 增加：

- `sbi_send_ipi_amp(hartid, msg_type)`：调用 OpenSBI `0x100`；
- `sbi_clear_ipi_amp(&msg_type)`：调用 OpenSBI `0x102`；
- 保留标准 `sbi_clear_ipi()`，处理 FreeRTOS 调度器使用的普通 SSIP。

### 7.2 FreeRTOS IPI Mailbox

[ipi_mailbox.c](../../trusted_domain/driver/mailbox/ipi_mailbox.c) 实现对端状态机：

- channel 1 接收 U-Boot/Linux 请求；
- channel 0发送响应；
- ISR/trap 路径只复制消息、修改 ACK、给 semaphore/queue 并唤醒任务；
- Router 和 NOR 访问在任务上下文完成；
- 通过内存屏障保证 payload 与 state 的观察顺序。

### 7.3 SSIP 双重清除

`quard_ipi_mailbox_handle()` 当前执行：

```text
第一次 sbi_clear_ipi_amp() 获取 AMP bits
  -> 标准 sbi_clear_ipi() 清 FreeRTOS 调度 SSIP
  -> 第二次 sbi_clear_ipi_amp() 获取竞态窗口内的新 bits
  -> 合并两次 bits
  -> 处理 channel 1 请求或 channel 0 ACK
```

这一流程不能简化为只调用 AMP clear，也不能在中断上下文执行 service 分发、日志输出
或 SPI NOR 访问。

## 8. 一次 U-Boot NOR 读取的分步骤过程

以 U-Boot proper 执行 `mtd read recovery ...` 为例：

1. MTD core 找到 `quard-nor` 的 `recovery` 分区。
2. `quard_nor_client` 检查 offset、长度和共享数据区边界。
3. NOR client 构造 service `2` 的 `NOR_READ` 请求。
4. Router 把 service ID 写入 28 字节消息头。
5. U-Boot IPI Mailbox 将请求写入 channel 1，将 state 设为 `DATA_READY`。
6. U-Boot 通过 OpenSBI `SEND_EXT_DOMAIN` 为 hart4 设置 AMP bit 并触发 SSIP。
7. FreeRTOS SSIP handler 清中断、复制消息并唤醒 Router task。
8. FreeRTOS Router task 按 service ID `2` 分发给 NOR agent。
9. NOR agent 在任务上下文读取 SPI NOR，将数据写入 `0x6E500000` 共享区。
10. FreeRTOS 通过 channel 0 返回状态，并用 OpenSBI IPI 通知 U-Boot 所在 hart。
11. U-Boot Mailbox 收到响应并 ACK，Router 把响应交回 NOR client。
12. NOR client 从大块共享区复制数据给 MTD 调用者。

控制消息与大块数据分离，使固定 28 字节 Mailbox 协议不需要随 Flash 请求长度扩展。

## 9. 推荐的实现和调试顺序

### 步骤 1：先固定资源归属

- hart4、UART2 和物理 QSPI 归 FreeRTOS；
- Linux/U-Boot proper 不初始化 hart4 PLIC context，不直接访问 QSPI；
- SPL 仅在 FreeRTOS 启动前临时承担 QSPI 早期加载；
- 共享内存必须从 Linux/通用内存分配中保留。

### 步骤 2：验证 AMP 启动，不急于接业务服务

- 确认 SPL 从正确的 `0x530000` payload offset 复制 FreeRTOS；
- 确认 OpenSBI 把 hart1 交给 Linux/U-Boot domain，把 hart4 交给 RT domain；
- 确认 FreeRTOS 实际从 `0x6E800000` 运行。

### 步骤 3：先打通 SBI IPI

- 注册 AMP pending bitmap；
- 单独验证 type bit 与目标 hart；
- 同时验证标准 SSIP 与 AMP SSIP 的清除；
- 连续发送而不是只做单次 ping，暴露清除竞态。

### 步骤 4：实现两通道共享内存状态机

- 固定 28 字节 payload、4 字节 state 和通道方向；
- 写 payload 后再发布 `DATA_READY`；
- 收到 ACK 后才恢复 `IDLE`；
- 加 timeout、`-EBUSY` 和内存屏障。

### 步骤 5：增加 Router

- 先验证一个 service；
- 再引入 service ID 注册、唯一性检查和 callback；
- ISR 只投递任务，服务处理保持在任务上下文。

### 步骤 6：接入 NOR consumer 和 MTD

- 先做 `GET_INFO` 和只读；
- 再做范围受控的 write/erase；
- 大数据使用独立共享区；
- proper 禁用 QSPI 后，只通过 `mtd` 命令验证。

### 步骤 7：最后迁移 environment 和 A/B bootctrl

- 确认 `quard-nor` 稳定注册后再切换 environment backend；
- 将 environment 放到不与 GPT 分区重叠的 reserved 区；
- 再让 A/B bootctrl 通过 recovery MTD 读取槽位状态。

这种顺序可以把“AMP 启动错误”“IPI通知错误”“共享内存状态机错误”和“业务协议
错误”逐层分开。

## 10. 常见误区与边界

### 10.1 不要把 SPL 和 U-Boot proper 当成同一硬件所有权阶段

SPL 使用 `spi_flash` 是启动前提；U-Boot proper 使用 `sf probe/read/update` 则会绕过
FreeRTOS NOR agent。两个阶段的命令和驱动不能混用。

### 10.2 OpenSBI 的 AMP bit 不是 Mailbox payload

AMP bit 只表示 channel 类型到达；实际 28 字节消息仍在 `0x6E402000`。只看到 SSIP
不能证明 payload、state 和 Router service 正确。

### 10.3 一次通信成功不能证明 SSIP 没有竞态

必须连续双向请求，确认 ACK 能反复从 `ACK` 清回 `IDLE`，且没有 timeout、`-EBUSY`
或消息位残留。

### 10.4 ISR 中不能处理耗时服务

IPI/SSIP handler 只能确认或复制消息并唤醒任务。禁止在其中打印日志、阻塞等待、
分发完整服务或访问 SPI NOR。

### 10.5 测试 client 与生产 Router 不能共占通道

`amp-virtio-rpmsg`、`starfive_rpmsg` 和直接访问通道的 Mailbox test client 必须保持
禁用。它们与 `quard_mbox_router` 同时申请 channel 0/1 会破坏状态机和 ACK 归属。

## 11. 验证证据与当前边界

现有文档记录过以下等价成功证据：

```text
FreeRTOS IPI mailbox init successful: base=0x6e402000
router server mbox_c2 started
mailbox router ready
registered 6 GPT partitions
```

这些日志分别证明 FreeRTOS Mailbox 初始化、Flash service 启动、U-Boot Router probe
和 NOR MTD 分区注册。完整验证还应确认：

- OpenSBI domain 中 hart1/hart4 归属正确；
- U-Boot proper 的物理 QSPI 节点为 `disabled`；
- `mtd list` 显示 `quard-nor` 和六个分区；
- 重复请求能够清除 ACK，没有 timeout 或 `-EBUSY`；
- `saveenv` 走 MTD backend，且不会修改 recovery；
- 部署固件的版本、时间戳和哈希与本次构建一致。
