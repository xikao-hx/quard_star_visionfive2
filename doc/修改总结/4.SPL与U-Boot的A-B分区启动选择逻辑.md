## 2. 先理解两个启动阶段

本项目存在两层 A/B 选择，二者选择的是不同存储介质上的不同对象：

```text
BootROM
  |
  v
SPI NOR 中的 SPL
  | 读取 GPT + recovery.target_bank
  | 选择 fw_payload_a 或 fw_payload_b
  | 必要时同步 recovery.current_bank
  v
对应槽位的 fw_payload（OpenSBI + U-Boot proper + FreeRTOS）
  |
  | U-Boot proper 通过 mailbox-backed MTD 读取 recovery.current_bank
  | 选择 SD 的 boot_a/rootfs_a 或 boot_b/rootfs_b
  v
SD boot 分区中的 starfiveu.fit
  |
  | bootargs 携带所选 rootfs 的 PARTUUID
  v
Linux initramfs -> 最终 rootfs
```

这两个阶段不能合并理解：

- SPL 决定从 SPI NOR 的哪个 `fw_payload` 启动；
- U-Boot proper 决定从 SD 卡的哪个 boot 分区加载 Linux，并给 Linux 指定哪个
  rootfs；
- SPL 直接访问 QSPI，因为此时 FreeRTOS 尚未接管硬件；
- U-Boot proper 不直接访问物理 QSPI，而是通过
  `quard-nor` mailbox-backed MTD 访问 recovery；
- Linux 最终是否挂载了正确 rootfs，还要由 `/proc/cmdline` 和 `findmnt /`
  共同证明，不能只看 U-Boot 打印的槽位。

## 3. A/B 状态与分区映射

### 3.1 `target_bank` 与 `current_bank`

recovery v2 的公共 ABI 定义在
[quard_recovery_config.h](../../common_inc/bsp/quard_recovery_config.h)：

- `target_bank`：下一次启动希望切换到的目标槽位；
- `current_bank`：SPL 本次实际采用并同步下来的槽位；
- `RECOVERY_BANK_A=0`，`RECOVERY_BANK_B=1`；
- recovery 记录固定为 200 字节，`header_crc32` 位于偏移 196；
- `_Static_assert` 固定关键字段偏移和结构大小，防止各组件对同一 NOR 数据产生
  不兼容解释。

两阶段使用不同字段是有意设计：

1. OTA 在 Linux 用户态完成非活动槽镜像写入和校验后，最后提交
   `target_bank`；
2. 重启后 SPL 根据 `target_bank` 选择 NOR payload；
3. SPL 把实际选择同步到 `current_bank`；
4. U-Boot proper 只消费 `current_bank`，从而使 NOR payload、SD boot 和 SD
   rootfs 保持同槽。

当前 SPL 基础实现没有引入 bootcount、版本比较、自动回滚或完整性策略；这些内容
不能从字段名称推断为已经实现。

### 3.2 NOR 与 SD 分区映射

SPI NOR 布局的唯一来源是
[visionfive2-nor-layout.json](../../conf/visionfive2-nor-layout.json)，生成的 C 常量位于
[quard_nor_layout.h](../../common_inc/bsp/quard_nor_layout.h)。与选择逻辑直接有关的
区域如下：

| 对象 | A 槽 | B 槽 |
| --- | --- | --- |
| SPL | `spl_a@0x00000000` | `spl_b@0x00040000` |
| fw_payload | `fw_payload_a@0x00100000` | `fw_payload_b@0x00700000` |
| NOR GPT | `gpt@0x00080000` | 两槽共用 |
| recovery | `recovery@0x000C0000` | 两槽共用 |

当前基础启动选择只切换 `fw_payload_a/b`；BootROM 如何选择或恢复 `spl_a/b` 不属于
这段 SPL bootctrl 的职责。

SD 卡映射如下：

| bank | boot `PARTLABEL` | rootfs `PARTLABEL` | 兼容分区号 | `active_system` |
| --- | --- | --- | --- | --- |
| A | `boot_a` | `rootfs_a` | p3 / p4 | `0` |
| B | `boot_b` | `rootfs_b` | p5 / p6 | `1` |

`PARTLABEL`、分区号和 `PARTUUID` 的用途不同：

- U-Boot 优先用 `PARTLABEL` 把逻辑名称解析为当前磁盘上的分区号；
- p3/p4 和 p5/p6 只是兼容旧镜像的回退映射；
- U-Boot 再查询 rootfs 分区的 `PARTUUID`，通过 `bootargs` 交给 Linux；
- `PARTUUID` 避免把可能变化的 `/dev/mmcblkXpN` 写死在启动参数中。

## 4. 第一阶段：在 SPL 中选择 NOR fw_payload

### 4.1 接入点为什么放在 SPI loader

入口位于 [spl_spi.c](../../u-boot/common/spl/spl_spi.c)。原始 SPI 启动路径先通过
`spi_flash_probe()` 获得 flash，再从固定的 `payload_offs` 读取镜像头和完整镜像。
A/B 扩展在“flash 已可访问、payload 尚未读取”的位置调用：

```c
quard_bootctrl_select_payload(flash, &payload_offs, NULL);
```

这样设计有三个好处：

1. 只替换 payload offset，不复制 FIT 解析和加载代码；
2. GPT、recovery 和 payload 都复用同一个已经 probe 成功的 `spi_flash`；
3. bootctrl 关闭时仍保留原来的固定 offset/DTS offset 路径。

### 4.2 SPL 的完整选择步骤

核心实现位于
[SPL quard_bootctrl.c](../../u-boot/common/spl/quard_bootctrl.c)：

1. `gpt_validate()` 从 `gpt@0x00080000` 读取保护 MBR、GPT Header 和 128 个
   Entry。
2. 校验 MBR 签名、GPT 签名、版本、Header 大小、LBA、Header CRC 和 Entry
   Array CRC。
3. 核对六个预期分区的名称、类型 GUID、offset、size 和 attributes，拒绝多余的
   非空 Entry。
4. 只有 GPT 完整合法时，才从 GPT 条目取得 recovery、`fw_payload_a` 和
   `fw_payload_b` 的实际 offset。
5. 从 recovery 所在位置读入完整的 4 KiB 擦除块，校验 magic、结构版本、bank
   范围和 CRC32。
6. recovery 有效时，以 `target_bank` 作为选中槽位。
7. 如果 `current_bank != target_bank`，修改 `current_bank`、重算 recovery CRC，
   擦除并回写完整 4 KiB，最后读回逐字节比较。
8. 将选中槽位对应的 payload offset 返回给 `spl_spi_load_image()`，由原生 SPL
   路径继续解析和加载 FIT。

回写完整 4 KiB 而不是只写 200 字节，是因为 SPI NOR 需要先按擦除粒度擦除；先把
整个 sector 读入 RAM 可以保留同一擦除块内 recovery 记录之外的数据。

### 4.3 SPL 的失败策略

当前代码的失败语义需要区分：

- GPT 无效：使用 canonical A offset `0x00100000`；
- recovery 读取失败、CRC 错误或 bank 越界：选择 A；
- `current_bank` 写回失败：打印 warning，但继续加载已经按 `target_bank` 选中的
  payload；
- SPI/FIT 后续读取失败：交还原 SPL loader 报错。

因此“回退 A”是元数据损坏时的确定性选择，不等于已经实现运行失败后的自动回滚。

### 4.4 SPL 修改文件与原因

| 文件 | 改了什么 | 为什么需要 |
| --- | --- | --- |
| [quard_bootctrl.c](../../u-boot/common/spl/quard_bootctrl.c) | 新增 GPT/recovery 校验、bank 选择、recovery 同步和 payload offset 输出 | 把板级 A/B 策略与通用 SPI/FIT loader 分离 |
| [quard_bootctrl.h](../../u-boot/common/spl/quard_bootctrl.h) | 暴露 `quard_bootctrl_select_payload()` | 为 `spl_spi.c` 提供最小接口 |
| [spl_spi.c](../../u-boot/common/spl/spl_spi.c) | 在读取 payload 之前调用 bootctrl | 让原生加载流程使用动态 offset，而不重复 loader |
| [SPL Kconfig](../../u-boot/common/spl/Kconfig) | 增加默认关闭的 `SPL_QUARD_BOOTCTRL` | 可选功能必须显式启用，避免影响其他板卡 |
| [SPL Makefile](../../u-boot/common/spl/Makefile) | 条件编译 `quard_bootctrl.o` 并加入公共头路径 | 确保实现只进入启用它的 SPL |
| [VisionFive 2 defconfig](../../u-boot/configs/starfive_visionfive2_defconfig) | 设置 `CONFIG_SPL_QUARD_BOOTCTRL=y` | 只为当前目标板打开功能 |
| [quard_recovery_config.h](../../common_inc/bsp/quard_recovery_config.h) | 固定 recovery v2 ABI、bank 定义、CRC 范围和结构断言 | 让 SPL、U-Boot proper、Linux/OTA 对同一持久化记录达成一致 |
| [quard_nor_layout.h](../../common_inc/bsp/quard_nor_layout.h) | 提供由 canonical JSON 派生的 NOR 常量 | 避免在 bootctrl 中维护第二套地址 |

`u-boot/common/spl/Makefile` 使用 `CONFIG_SPL_QUARD_BOOTCTRL`，而 proper 的实现位于
板级目录并由 `ifndef CONFIG_SPL_BUILD` 隔离。这保证直接访问 QSPI 的 SPL 代码不会
被错误编译进 U-Boot proper。

## 5. 第二阶段：在 U-Boot proper 中选择 SD boot/rootfs

### 5.1 为什么 U-Boot proper 使用 MTD 而不是 `sf`

此项目中 FreeRTOS 独占物理 QSPI 控制器。进入 U-Boot proper 后，recovery 通过
以下链路读取：

```text
U-Boot quard_bootctrl
  -> quard-nor MTD
  -> U-Boot mailbox router/IPI
  -> FreeRTOS NOR agent
  -> SPI NOR recovery 分区
```

因此 [proper quard_bootctrl.c](../../u-boot/board/starfive/visionfive2/quard_bootctrl.c)
调用 `mtd_probe_devices()`、`get_mtd_device_nm("recovery")` 和 `mtd_read()`，而不是
执行 `sf probe/read`。这既符合硬件资源归属，也让 bootctrl 只关心名为
`recovery` 的逻辑分区。

### 5.2 U-Boot proper 的选择步骤

`board_late_init()` 中的调用点位于
[starfive_visionfive2.c](../../u-boot/board/starfive/visionfive2/starfive_visionfive2.c)：

1. 先把 `sd_ab_enabled` 清零，防止持久化环境中残留的旧槽位标记直接生效。
2. 仅在 `bootmode=flash` 或 `bootmode=sd` 时调用 `quard_bootctrl_apply()`。
3. bootctrl 先用 `sd_ab_env_version` 检查持久化脚本版本；版本不匹配时，只恢复它
   管理的默认环境变量，而不是清空整个环境。
4. 先把 boot/root 默认值设为旧的 p3/p4，并标记当前不是 A/B SD 启动。
5. 通过 mailbox-backed `recovery` MTD 读取 200 字节 recovery 记录并校验。
6. recovery 有效时读取 `current_bank`；元数据内容无效时确定性回退 A。
7. 导出 `active_bank`、`active_system`、`sd_bootlabel`、`sd_rootlabel`、
   `sd_bootpart` 和 `sd_rootpart`。
8. 最后才设置 `sd_ab_enabled=1`，避免环境变量只更新一半时脚本消费到不完整映射。

如果 MTD transport 本身失败，`board_late_init()` 将 `bootdelay` 设为 `-1`，停止
自动启动并留在 U-Boot shell；它不会把“无法读取状态”悄悄解释为某个可启动槽位。

### 5.3 默认环境脚本如何消费槽位

默认环境定义在
[starfive-visionfive2.h](../../u-boot/include/configs/starfive-visionfive2.h)：

- `use_sd_ab_parts` 优先用 `part number mmc ... boot_a/rootfs_a` 或
  `boot_b/rootfs_b` 解析分区号；
- 如果旧磁盘镜像没有对应 `PARTLABEL`，才回退 `sd_bootpart/sd_rootpart` 中的
  3/4 或 5/6；
- `mmc_test_and_boot` 只对 SD 设备启用 A/B 映射，eMMC 和 NVMe 保持 legacy
  路径；
- 从选中的 boot 分区加载并导入 `vf2_uEnv.txt` 后，再次执行
  `use_sd_ab_parts`，防止导入的环境覆盖已解析分区；
- 选中槽位的启动链失败后执行 `sd_ab_fail`，本次启动停止继续 fallback，避免又从
  legacy/NVMe 路径启动另一个系统而造成状态与实际系统不一致。

`sd_ab_env_version` 从 1 升为 2，是因为 `cbf7c1fae` 把固定分区号方案扩展为
`PARTLABEL` 优先方案。版本门禁使已经 `saveenv` 的旧脚本能够从新版固件默认环境中
刷新，而不必要求用户手工逐项删除变量。

### 5.4 `vf2_uEnv.txt` 如何生成 Linux 启动参数

[vf2_uEnv.txt](../../conf/vf2_uEnv.txt) 完成最后一段 bootloader 工作：

1. 对所选 `${rootpart}` 执行 `part uuid`，取得 GPT `PARTUUID`；
2. A/B SD 启动时生成：

   ```text
   root=PARTUUID=${rootuuid} rw active_bank=${active_system}
   ```

3. 从所选 `${bootpart}` 加载当前约定名称 `starfiveu.fit`；
4. 依次执行 `bootm start`、FDT/initramfs 设置、`bootm loados` 和 `booti`；
5. 任一步失败都会使 `boot2` 返回失败，由外层 `sd_ab_fail` 停止错误 fallback。

这里的 `vf2_uEnv.txt` 可以理解为“固定启动命令模板 + 运行时环境变量”。例如下面的
命令结构写在文件中：

```sh
part uuid ${bootdev} ${devnum}:${rootpart} rootuuid
fatload ${bootdev} ${devnum}:${bootpart} ${loadaddr} ${fitfile}
```

其中 `${bootdev}`、`${devnum}`、`${bootpart}` 和 `${rootpart}` 并不是固定值。
U-Boot proper 的 bootctrl、默认环境脚本以及前序命令会在当前启动过程中设置这些
变量；执行 `run boot2` 时，U-Boot 才把变量展开成实际命令。

#### 5.4.1 `part uuid` 如何得到 rootfs 标识

以 B 槽为例，前面的选择过程已经得到：

```ini
active_bank=b
active_system=1
bootpart=5
rootpart=6
```

此时 `bootargs_ext` 中的命令：

```sh
part uuid ${bootdev} ${devnum}:${rootpart} rootuuid
```

可能展开为：

```sh
part uuid mmc 1:6 rootuuid
```

各参数含义如下：

| 参数 | 含义 |
| --- | --- |
| `part uuid` | 查询分区表中已有的 GPT `PARTUUID` |
| `mmc` | 存储设备类型 |
| `1:6` | MMC 设备 1 的第 6 分区，即当前布局中的 `rootfs_b` |
| `rootuuid` | 保存查询结果的 U-Boot 环境变量名 |

需要注意，`part uuid` 不会创建新的 UUID，也不会修改 SD 卡分区表；它只是读取 p6
分区项中已经存在的 `PARTUUID`，再把结果保存到当前 U-Boot 环境。例如查询结果为：

```ini
rootuuid=8852481a-92d5-492a-b7bb-436998efe31a
```

这个变量通常只服务于本次启动。除非用户另外执行 `saveenv`，否则查询动作本身不会
把它持久化到 U-Boot 环境存储。

#### 5.4.2 `bootargs_ext` 如何把结果传给 Linux

`bootargs_ext` 使用 `${rootuuid}` 和 `${active_system}` 拼出内核命令行。B 槽示例：

```text
root=PARTUUID=8852481a-92d5-492a-b7bb-436998efe31a rw active_bank=1
```

这几个参数的职责不同：

- `root=PARTUUID=...`：真正指定 Linux 应挂载哪个分区作为根文件系统 `/`；
- `rw`：要求以可读写方式挂载根文件系统；
- `active_bank=1`：向 Linux 用户态和 OTA 工具说明本次选择了 B 槽。项目约定 A 为
  `0`、B 为 `1`，但该参数本身不负责选择或挂载 rootfs。

随后 `setupfdt2` 把完整的 `bootargs` 写入设备树 `/chosen/bootargs`。Linux 启动后，
initramfs 的 `/init` 解析 `root=PARTUUID=...`，使用 `blkid` 找到对应块设备。例如：

```text
PARTUUID=8852481a-92d5-492a-b7bb-436998efe31a
  -> /dev/mmcblk1p6
  -> 挂载为 /rootfs
  -> run-init 切换为最终根文件系统 /
```

完整的数据传递关系是：

```text
recovery.current_bank=B
  -> U-Boot 导出 rootpart=6、active_system=1
  -> part uuid mmc 1:6 rootuuid
  -> rootuuid=<rootfs_b 的 PARTUUID>
  -> bootargs 包含 root=PARTUUID=<rootuuid> active_bank=1
  -> initramfs 将 PARTUUID 解析为 /dev/mmcblk1p6
  -> Linux 使用 rootfs_b 作为根文件系统
```

这里不直接写死 `root=/dev/mmcblk1p6`，是因为 `/dev/mmcblkX` 的编号可能随设备探测
顺序变化；GPT `PARTUUID` 与具体 Linux 设备节点名称解耦，更适合跨 bootloader 和
Linux 传递根分区身份。

提交 `4d5f4ad68` 最初把镜像名改为 `image.fit`，随后 `932839773` 根据 SDK 的
VFAT 产物约定改为当前的 `starfiveu.fit`。学习提交历史时应以当前文件为准，不能只
照抄中间提交中的文件名。

## 6. 第三阶段：Linux 为什么还需要修改 initramfs

U-Boot 能生成 `root=PARTUUID=...` 并不代表根文件系统一定能挂载。这个项目由
initramfs 的 `/init` 手工查找并挂载最终 rootfs，旧实现把 `root=` 一律当作
`/dev/...` 路径，因此无法直接处理 GPT `PARTUUID`。

[buildroot/system/skeleton/init](../../buildroot/system/skeleton/init) 在提交
`31298cc87` 中增加了以下逻辑：

1. 解析内核命令行中的 `root=`；
2. 遇到 `PARTUUID=...` 时调用 util-linux
   `blkid -t "$ROOT" -o device`；
3. 等待解析结果对应的块设备出现；
4. 将真实设备挂载到 `/rootfs`，再通过 `run-init` 切换根文件系统。

这里使用 util-linux `blkid`，因为项目当时的 BusyBox `blkid` 不报告所需的 GPT
PARTUUID。这个修改虽然不在 bootloader 源码中，却是 A/B 启动闭环不可缺少的一步。

### 6.1 Linux 启动闭环的配套文件

提交 `31298cc87` 除修改 `/init` 外，还修改了以下配套文件：

## 7. 按开发顺序理解这些改动

如果从零学习或重新实现同类功能，建议按以下顺序推进。

### 步骤 1：先固定持久化 ABI 和存储布局

- 定义 A/B bank 编码、recovery 结构版本、字段偏移和 CRC 覆盖范围；
- 用一个 canonical 布局生成 NOR 地址常量；
- 明确谁能写 `target_bank`、谁同步 `current_bank`；
- 在实现启动选择前，先保证 GPT/recovery 可独立生成和校验。

原因：启动早期无法容忍格式歧义。只要 SPL、U-Boot 和 Linux 对结构偏移或地址理解
不同，就可能选择错误镜像或破坏 NOR 擦除块。

### 步骤 2：让 SPL 只负责“选择 offset”

- 在介质已经初始化、镜像尚未读取的 loader 节点接入；
- 把 GPT/recovery 策略封装在独立 helper；
- 返回 payload offset，继续复用 U-Boot 原生 FIT loader；
- 为无效元数据定义确定的安全默认值。

原因：对通用 loader 的修改越小，越容易跟随上游 U-Boot 更新，也越不容易破坏其他
启动介质。

### 步骤 3：跨重启传递“实际选择”

- SPL 采用 `target_bank` 后同步 `current_bank`；
- 写 NOR 时遵守 4 KiB 擦除粒度，保留同块其他数据并读回校验；
- 明确写回失败是停止启动还是带 warning 继续。本项目选择后者。

原因：U-Boot proper 需要知道本次实际加载了哪个 fw_payload，而不能重新独立解释
一次“目标意图”。

### 步骤 4：在 U-Boot proper 中转换为 SD 选择

- 通过 proper 阶段拥有的抽象访问 recovery；本项目必须是 mailbox-backed MTD；
- 将 bank 一次性转换为 boot/root label、兼容分区号和 Linux 槽位编号；
- 在所有变量成功导出后再发布 enabled 标志；
- transport 失败时停止自动启动，内容无效时执行明确定义的 A 回退。

原因：硬件所有权、错误类型和恢复方式在 SPL 与 proper 阶段不同，不能复用同一套
底层 NOR 访问实现。

### 步骤 5：让启动脚本完成可移植寻址

- 用 `PARTLABEL` 找逻辑分区；
- 用 `PARTUUID` 告诉 Linux 根分区；
- 保留有限的旧分区号兼容路径，并打印明确日志；
- 导入外部环境后重新应用关键选择，防止变量被覆盖；
- 失败后停止跨介质 fallback，避免启动到与 recovery 状态不一致的系统。

### 步骤 6：闭环到 Linux 实际挂载

- initramfs 必须识别 bootloader 传入的 root 标识；
- 验证时同时核对 U-Boot 的 boot 分区、`/proc/cmdline`、rootfs `PARTUUID` 和
  `findmnt /`；
- A/B 两个 boot 分区中的 FIT 必须与各自 rootfs 和本次构建产物对应。

## 8. 如何继续扩展而不破坏现有边界

### 8.1 增加启动失败自动回滚

当前实现只在元数据无效时回退 A，没有“尝试 N 次失败后回到上一槽”的状态机。若要
扩展，应先定义：

- 哪个阶段递增尝试次数；
- Linux 在什么成功条件下清零计数或设置 `boot_success`；
- 掉电发生在计数写回、payload 加载或 Linux 确认之间时如何恢复；
- A、B 都不可启动时进入 shell、recovery 还是固定维护镜像。

不要只在 `spl_spi.c` 中加入零散条件。策略应继续封装在 bootctrl，loader 仍只消费
最终 offset。

### 8.2 增加 payload 完整性校验

GPT/recovery CRC 只能证明元数据未损坏，不能证明 `fw_payload` 可启动。后续可以在
选择 offset 后、交给 loader 前增加尺寸、hash 或签名策略，但必须区分：

- 元数据损坏；
- payload 内容损坏；
- FIT 自带的 hash/signature 校验失败；
- 运行到 Linux 后才失败。

不同故障对应的回退时机和可用证据不同，不应统一打印成“slot failed”。

### 8.3 扩展 SPL A/B

当前文件名和布局包含 `spl_a/spl_b`，但本 bootctrl 不负责 BootROM 级 SPL 选择。
扩展前必须先确认 JH7110 BootROM 的加载规则、硬件恢复通道和断电安全更新顺序。
U-Boot proper 中的 SPL 更新仍必须经 mailbox-backed MTD，不能为了方便改用 `sf`。

### 8.4 维护环境脚本兼容性

如果默认环境脚本的语义发生变化，应同步：

1. 提升 `QUARD_BOOTCTRL_ENV_VERSION` 和默认 `sd_ab_env_version`；
2. 把新增或改名的受管变量加入 `managed_vars[]`；
3. 检查持久化环境升级后是否会留下旧变量；
4. 保证只刷新 bootctrl 管理的变量，不覆盖用户网络参数等无关配置。

## 9. 调试时按阶段取证

### 9.1 SPL 阶段

关注以下日志及其先后关系：

```text
SPL bootctrl: target=b current=a
SPL bootctrl: use slot b
SPL bootctrl: selected payload slot b @ 0x700000
```

它们分别证明 recovery 被解析、选择结果为 B、返回的 NOR offset 为
`fw_payload_b`。仅出现 fallback 日志不能证明 B 选择成功。

### 9.2 U-Boot proper 阶段

当前代码在 B 槽预期打印：

```text
SD bootctrl: current=b target=b
SD bootctrl: slot b uses SD boot_b/rootfs_b (fallback 5/6)
SD A/B resolved boot_b/rootfs_b by PARTLABEL
```

还应检查：

```sh
printenv active_bank active_system
printenv sd_bootlabel sd_rootlabel bootpart rootpart
part uuid mmc 1:${rootpart} rootuuid
printenv rootuuid bootargs
```

### 9.3 Linux 阶段

```sh
cat /proc/cmdline
findmnt /
ota_info read current_bank
ota_info read target_bank
```

B 槽闭环至少应同时满足：FIT 来自 `boot_b`、`root=` 指向 `rootfs_b` 的
PARTUUID、实际根挂载为对应分区、`current_bank=b` 且 `target_bank=b`。

## 10. 当前实现与验证边界

从当前源码可以静态确认：

- SPL bootctrl 只消费 `target_bank/current_bank`，未实现 bootcount、版本选择和
  自动回滚；
- SPL 直接通过 `spi_flash` 访问 NOR，U-Boot proper 通过 mailbox-backed MTD
  访问 recovery；
- U-Boot proper 以 `current_bank` 统一映射 SD boot/rootfs；
- SD 分区优先按 `PARTLABEL` 定位，Linux rootfs 按 `PARTUUID` 定位；
- 当前自动启动脚本加载的文件名是 `starfiveu.fit`。

历史调试文档记录了 U-Boot proper 选择 B、PARTUUID 解析为 p6 和 p6 rootfs 挂载的
板端证据；memory-bank 的 Step 6 记录则明确标注 SPL A/B payload 选择当轮只完成了
源码和静态检查，未执行 U-Boot/完整 AMP 构建或板端验证。两类记录证明的范围不同，
不应合并成“整条 SPL 到 Linux 链路已经由同一次构建完整验证”。
