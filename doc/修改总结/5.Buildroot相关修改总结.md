# Buildroot 相关修改总结

## 1. 文档目的与结论

本文根据当前仓库源码、配置文件和 Git 提交记录，整理 VisionFive2 AMP SDK 中
Buildroot 相关改动，重点回答以下问题：

- Buildroot 在整个启动和发布链路中承担什么职责；
- initramfs 与最终 ext4 rootfs 分别改了什么；
- 为什么 A/B 启动需要修改 initramfs，而不只是修改 U-Boot；
- 网络、NFS、SSH、Minicom、`userdata` 和 OTA 文件如何进入 rootfs；
- 为何需要补充 Makefile 依赖，避免增量构建继续使用旧文件；
- 当前实现中还有哪些限制和待确认项。

本项目中的 Buildroot 实际承担三类职责：

1. 生成 SDK 使用的 RISC-V Linux 交叉工具链；
2. 生成随 FIT 一起启动的早期 initramfs；
3. 生成安装到 SD 卡 `rootfs_a`/`rootfs_b` 的 ext4 根文件系统。

因此，Buildroot 的改动处于如下完整链路中：

```text
U-Boot 选择 A/B bank
        |
        | bootargs: root=PARTUUID=<所选 rootfs 的 PARTUUID>
        v
FIT 中的 Linux + initramfs
        |
        | /init 使用 util-linux blkid 解析 PARTUUID
        v
/dev/mmcblk...p4 或 p6
        |
        | 挂载并执行 run-init
        v
Buildroot ext4 rootfs
        |
        +-- 网络、Dropbear、Minicom、NFS 开发挂载
        +-- /userdata 持久分区挂载
        `-- OTA 程序、脚本、配置和公钥
```

## 3. Buildroot 输出及其区别

### 3.1 交叉工具链

默认工具链位于：

```text
work/buildroot_initramfs/host/
```

项目使用的 Linux 交叉编译前缀为：

```text
work/buildroot_initramfs/host/bin/riscv64-buildroot-linux-gnu-
```

顶层 [build.sh](../../build.sh) 会设置 `RVROOT`、`RISCV`、`CROSS_COMPILE` 和
`PATH`。Linux、U-Boot、外部内核模块以及 Linux 用户态程序都应使用这套工具链，
不能用主机上另一个 `riscv64-linux-gnu-` 工具链替代。

### 3.2 initramfs

主要配置文件为：

- [conf/buildroot_initramfs_config](../../conf/buildroot_initramfs_config)
- [conf/buildroot_initramfs_config_debug](../../conf/buildroot_initramfs_config_debug)
- [conf/initramfs.txt](../../conf/initramfs.txt)

Buildroot 先生成 `work/buildroot_initramfs/images/rootfs.tar`，顶层 Makefile 再将其
解包到 `work/buildroot_initramfs_sysroot`，复制内核模块等内容，最终生成：

```text
work/initramfs.cpio.gz
```

该文件被打包进 `image.fit`。它不是最终业务 rootfs，而是负责早期挂载和切换根文件
系统的过渡环境。

### 3.3 完整 ext4 rootfs

主要配置文件为：

- [conf/buildroot_rootfs_config](../../conf/buildroot_rootfs_config)
- [conf/amp_rootfs_post_build.sh](../../conf/amp_rootfs_post_build.sh)

生成文件为：

```text
work/buildroot_rootfs/images/rootfs.ext4
```

当前 Buildroot 配置中的 ext4 文件系统大小是 `500M`。AMP SD 镜像布局为
`rootfs_a` 和 `rootfs_b` 各预留 `2048M` 分区；这里要区分“ext4 镜像本身的文件
系统大小”和“GPT 分区预留大小”，不能将二者混为一谈。

## 4. initramfs 的 A/B 根分区适配

### 4.1 原问题

U-Boot 根据 bank 选择 `rootfs_a` 或 `rootfs_b`，并将目标分区的 GPT PARTUUID
写入内核命令行，例如：

```text
root=PARTUUID=<rootfs_b 的实际 PARTUUID> rw active_bank=1
```

但本项目不是由内核直接完成最终根文件系统挂载，而是先进入 initramfs，由
`/init` 手工执行 `mount` 和 `run-init`。原 `/init` 只把 `root=` 的值当作
`/dev/...` 设备路径检查：

```text
[ -e "$ROOT" ]
mount "$ROOT" /rootfs
```

当 `ROOT=PARTUUID=...` 时，它不是实际文件路径，因此即使 U-Boot 传入了正确
PARTUUID，initramfs 仍无法找到并挂载 p4 或 p6。

### 4.2 `/init` 修改

[buildroot/system/skeleton/init](../../buildroot/system/skeleton/init) 增加了以下逻辑：

1. 从 `/proc/cmdline` 提取 `root=`、`nfsroot=` 和 `init=`；
2. `root=/dev/nfs` 时启动网络并按 `nfsroot=` 挂载；
3. `root=PARTUUID=...` 时执行：

   ```sh
   /sbin/blkid -t "$ROOT" -o device
   ```

4. 最多等待 100 次，每次 0.1 秒，等待块设备枚举完成；
5. 只有解析结果存在且为块设备时才挂载；
6. 找不到设备或挂载失败时输出明确错误并退出；
7. 挂载最终 rootfs 后移动 `/proc`、`/sys`、`/run`、`/tmp` 和 `/dev`，再执行
   `run-init`。

`devtmpfs` 的 `/dev` 被整体移动时，其 `/dev/pts` 和 `/dev/shm` 子挂载也随之移动，
因此删除了对这两个子目录的重复 `mount --move`，避免切根阶段产生错误。

### 4.3 为什么引入 util-linux `blkid`

现场排查发现，当前 BusyBox `blkid` 不能提供这条链路需要的 GPT PARTUUID 查询。
因此修改了：

- [buildroot/package/util-linux/Config.in](../../buildroot/package/util-linux/Config.in)
- [buildroot/package/util-linux/util-linux.mk](../../buildroot/package/util-linux/util-linux.mk)

新增 `BR2_PACKAGE_UTIL_LINUX_BLKID` 选项，使精简 initramfs 可以安装 `blkid` 和所需
`libblkid`，不必为了一个查询工具无目的地启用所有 util-linux 程序。普通和 debug
initramfs 配置都显式启用了该能力。

完整 rootfs 当前启用了 `BR2_PACKAGE_UTIL_LINUX_BINARIES=y`，因此包含完整的一组
util-linux 工具；这与精简 initramfs 的按需选择方式不同。

### 4.4 A/B 映射结果

| bank | boot 分区 | rootfs 分区 | initramfs 最终解析目标 |
| --- | --- | --- | --- |
| A，`active_bank=0` | p3，`PARTLABEL=boot_a` | p4，`PARTLABEL=rootfs_a` | p4 对应的 `/dev/mmcblk...p4` |
| B，`active_bank=1` | p5，`PARTLABEL=boot_b` | p6，`PARTLABEL=rootfs_b` | p6 对应的 `/dev/mmcblk...p6` |

这里的 Linux 设备号可能随启动介质枚举变化，因此正式逻辑使用 PARTUUID，表中的
p4/p6 表示 GPT 分区号，而不是要求长期写死 `/dev/mmcblk1p4` 或
`/dev/mmcblk1p6`。

## 5. 网络、NFS、SSH 和串口开发能力

### 5.1 Buildroot 配置

相关配置增加或明确启用了：

- `BR2_PACKAGE_BUSYBOX_CONFIG_FRAGMENT_FILES=.../busybox-nfs.config`；
- `CONFIG_FEATURE_MOUNT_NFS=y`；
- `BR2_PACKAGE_LIBTIRPC=y`；
- `BR2_PACKAGE_DROPBEAR=y`；
- `BR2_PACKAGE_MINICOM=y`；
- `BR2_SYSTEM_DHCP="eth0"` 和双网口相关配置。

[conf/busybox-nfs.config](../../conf/busybox-nfs.config) 只补充 BusyBox 的 NFS mount
能力。Dropbear 用于 SSH 登录，Minicom 用于板端串口调试。

### 5.2 post-build 生成网络配置

[conf/amp_rootfs_post_build.sh](../../conf/amp_rootfs_post_build.sh) 在目标 rootfs 中
生成 `/etc/network/interfaces`，当前开发配置为：

```text
eth0: 192.168.5.9/24
```

这是一组项目开发环境中的固定地址，不是可移植的产品默认值。换网络环境时需要同步
调整板端地址、NFS 服务器地址和导出目录。

### 5.3 NFS 自动挂载服务

post-build 脚本生成 `/etc/init.d/S41nfs-root`，当前目标是：

```text
服务器：192.168.5.11
导出目录：/home/xikao/VisionFive2_6.6/nfs_rootfs
板端挂载点：/mnt/
```

早期实现会在 SysV `rcS` 中前台重复挂载。如果 NFS 服务器不可达，启动流程就会停在
网络阶段，后续 Dropbear 和串口登录也无法及时启动。后续修改为：

- 后台执行 NFS 重试，不阻塞 `rcS`；
- 使用 `/run/nfs-root.pid` 防止重复启动；
- 最多重试 30 次；
- 使用 `nolock,vers=3,soft,timeo=10,retrans=1` 给请求设置边界；
- `stop` 时终止后台任务并卸载挂载点。

该 NFS 挂载是开发辅助目录，不等同于 `/init` 支持的 `root=/dev/nfs` 网络根文件
系统模式。

## 6. `userdata` 持久分区集成

`cbf7c1fae` 同时修改镜像布局和 Buildroot rootfs 内容：

1. [conf/genimage-vf2-amp.cfg](../../conf/genimage-vf2-amp.cfg) 建立
   `boot_a`、`rootfs_a`、`boot_b`、`rootfs_b` 和 `userdata` 的 PARTLABEL；
2. 顶层 [build.sh](../../build.sh) 使用 Buildroot host 目录中的 `mkfs.ext4`
   生成 `work/userdata.ext4`，卷标为 `userdata`；
3. post-build 脚本创建 `/userdata`；
4. post-build 脚本以幂等方式向 `/etc/fstab` 添加：

   ```fstab
   PARTLABEL=userdata  /userdata  ext4  defaults,noatime  0  2
   ```

这样 A/B rootfs 更新时，下载包、升级状态和日志可以留在独立 p7 中，不随
`rootfs_a`/`rootfs_b` 被覆盖。`PARTLABEL=userdata` 也避免将挂载配置绑定到易变化的
`/dev/mmcblkXp7` 名称。

## 7. OTA 运行环境进入 rootfs

`53d7d5516` 将 OTA 安装过程接入
[conf/amp_rootfs_post_build.sh](../../conf/amp_rootfs_post_build.sh)。post-build 阶段会：

1. 检查 OTA 客户端配置、设备身份配置、公钥和目标 sysroot 中的
   `libcrypto.so.1.1`；
2. 使用 Buildroot 工具链构建并安装 `ota_info`；
3. 使用完整 rootfs 的 target sysroot 构建并安装 `ota_package`；
4. 安装 shell 实现的 `ota_client`；
5. 安装启动脚本、测试脚本、配置、公钥和版本信息。

主要安装结果为：

| rootfs 路径 | 来源/作用 |
| --- | --- |
| `/bin/ota_info` | 查询或更新 A/B OTA 元数据 |
| `/bin/ota_package` | 校验并应用 OTA 包 |
| `/lib/libbh_ota.so*` | OTA 公共库 |
| `/lib/libcrypto.so.1.1` | OTA 签名校验依赖 |
| `/usr/libexec/ota-client/` | OTA client 的远程、设备和包处理脚本 |
| `/etc/init.d/S94ota-prepare.sh` | 启动阶段准备 OTA 运行目录和链接 |
| `/etc/init.d/S95ota-stage2.sh` | OTA stage2 启动处理 |
| `/etc/ota/client.conf` | 服务端和客户端策略配置 |
| `/etc/ota/device_identity.conf` | 设备身份配置 |
| `/etc/ota/keys/ota_public.pem` | OTA 包验签公钥 |
| `/etc/version` | 由受控版本文件生成的系统版本 |

Buildroot 最终 ext4 目标在 Makefile 中显式使用：

```make
AMP_ROOTFS_INCLUDE_OTA=1
```

并将 `ota_info`、`ota_package`、`ota_client`、`target_root_script` 和版本处理脚本列为
`rootfs.ext4` 的输入依赖。这样相关源码或配置变化后，目标 rootfs 应重新生成，而不是
继续发布旧 OTA 文件。

## 8. 增量构建问题与修复

### 8.1 skeleton `/init` 不会自动刷新

Buildroot 增量构建不会因为 skeleton 中单个文件变化就必然重新复制整个 skeleton。
实际出现过源码 `/init` 已支持 PARTUUID，但以下中间目录仍保留旧版本的情况：

```text
work/buildroot_initramfs/target/init
work/buildroot_initramfs_sysroot/init
```

为此 post-build 脚本在每次生成 rootfs 时强制执行：

```sh
install -m 0755 buildroot/system/skeleton/init <target>/init
```

### 8.2 util-linux 配置变化未触发重建

仅修改 Buildroot package 配置不一定使已经构建的 util-linux 自动重配。Makefile
增加 `.buildroot_initramfs_partuuid` stamp，在 initramfs 配置或 util-linux 规则变化
后执行 `util-linux-dirclean`，再生成 stamp，使 `blkid` 能真正进入新产物。

### 8.3 补齐文件级依赖

当前 Makefile 将以下文件列为 initramfs/rootfs 的显式依赖：

- Buildroot defconfig；
- `conf/amp_rootfs_post_build.sh`；
- `conf/busybox-nfs.config`；
- `buildroot/system/skeleton/init`；
- util-linux 的 `Config.in` 和 `util-linux.mk`；
- OTA 源码、安装输入和版本脚本；
- 内核模块、`perf` 和版本文件等打包输入。

核心目的不是“每次全量重编”，而是保证真正影响产物的文件变化时，正确的目标会重建。

## 9. 构建入口和发布产物整理

顶层 [build.sh](../../build.sh) 统一了 SDK、BSP、应用和 OTA 的入口。与 Buildroot
直接相关的 SDK 命令为：

```sh
# 主机，构建 normal 镜像
./build.sh sdk build normal

# 主机，构建 AMP 镜像；默认 RTOS=freertos
./build.sh sdk build amp

# 主机，同时构建 normal 和 AMP 镜像
./build.sh sdk build all
```

顶层 Makefile 将发布结果整理到：

```text
work/target/normal/
work/target/amp/
```

其中 Buildroot 生成的 `rootfs.ext4` 会复制到对应发布目录。提交
`90f63001c` 将整张 SD 卡镜像从 publish 目标中移除，所以“发布组件镜像”和
“使用 genimage 生成整盘 SD 镜像”是两套不同动作，不能因为发布目录没有
`sdcard_amp.img` 就认为 rootfs 没有生成。

依据本仓库工作规则，当前完整 AMP 构建应使用：

```sh
# 主机
make ampfit RTOS=freertos -j$(nproc)
```

旧参数 `AMP_RTOS` 已停用。

## 11. 正常启动时序

1. SPL/OpenSBI/U-Boot proper 启动；
2. U-Boot 根据 bootctrl 状态选择 bank；
3. U-Boot 从 `boot_a` p3 或 `boot_b` p5 加载 `starfiveu.fit`；
4. U-Boot 查询对应 `rootfs_a` p4 或 `rootfs_b` p6 的 PARTUUID；
5. U-Boot 生成 `root=PARTUUID=... active_bank=...`；
6. Linux 启动 FIT 中的 initramfs；
7. initramfs `/init` 使用 util-linux `blkid` 将 PARTUUID 解析成实际块设备；
8. `/init` 挂载 Buildroot ext4 rootfs，并通过 `run-init` 切换根文件系统；
9. SysV 启动网络，NFS 开发挂载在后台重试，Dropbear 和串口登录继续启动；
10. `/etc/fstab` 按 `PARTLABEL=userdata` 挂载 p7；
11. OTA 服务使用 rootfs 中的程序、配置和公钥，并把持久数据保存到 `/userdata`。

## 12. 已知限制和待确认项

### 12.1 OTA 默认开关也会影响 initramfs

initramfs 和完整 rootfs 都配置了同一个
`BR2_ROOTFS_POST_BUILD_SCRIPT=.../amp_rootfs_post_build.sh`。脚本当前判断为：

```sh
if [ "${AMP_ROOTFS_INCLUDE_OTA:-1}" = 1 ]; then
    install_ota_runtime
fi
```

Makefile 只在完整 rootfs 规则中显式传入 `AMP_ROOTFS_INCLUDE_OTA=1`，initramfs 规则
没有显式传入 `0`。按当前默认值，initramfs 的 post-build 也可能尝试构建和安装 OTA
运行文件。这与“OTA 只安装到最终 rootfs”的目标并不完全一致，属于当前源码中需要
进一步确认或修正的边界，不能视为已经隔离完成。

建议后续将默认值改为关闭，并仅在完整 rootfs 目标中显式开启，或者拆分两个
post-build 脚本。

### 12.2 开发网络参数写死

静态 IP、NFS 服务器和导出路径直接写在 post-build 脚本中，只适用于当前开发环境。
若作为产品配置，应改为板级配置、Buildroot overlay 或可覆盖的构建变量。

### 12.3 ext4 文件系统与 GPT 分区大小不同

Buildroot 生成的 rootfs 文件系统当前为 500 MiB，而 A/B GPT 分区各预留 2 GiB。
如果需要使用整个分区剩余空间，应明确增加首次启动扩容或制镜阶段扩容流程；当前总结
不假设已经自动扩容。

### 12.4 生产与调试内容需要继续分离

当前 rootfs 配置包含较多开发、调试和厂商测试工具。后续若形成生产镜像，应继续区分
普通、debug 和生产配置，并确保 mailbox 测试客户端、旧 mailbox 传输和 RPMsg 测试
链路不会与生产 `quard_mbox_router` 同时启用。
